Call Blocker, from an empty directory

A build-along Kotlin Multiplatform tutorial. Nine steps, each ending in something you can run and look at.

What this is, and how it differs from the other course

The Corta Spam course documents a finished app: 28 chapters written after the code shipped, tracing subsystems and post-mortems. It is a reference. You cannot follow it and end up with a working app, because it never asks you to type anything.

This is the other document. You start with an empty directory and end with an Android app that is your phone's dialer, sees an incoming call before it rings, and refuses the calls you told it to refuse. Every step has a CHECKPOINT — a command to run and a specific thing you must see. If you do not see it, stop; the next step will not save you.

Honesty about provenance. Steps 1–4 were executed from an empty directory on a Pixel 8 Pro emulator (API 36) while this was written, and the traps in them are the ones that actually happened, in the order they happened. Steps 5–9 are lifted from Corta Spam, which is a shipping app with 571 tests and a device suite — that code is proven, but the from-zero path through it is reconstructed rather than re-executed. Each step says which it is.

What you need

  • JDK 17. Everything here sets jvmToolchain(17); a different JDK is the most common first failure.
  • Android SDK with API 36 installed, and sdk.dir in local.properties.
  • An emulator, or a phone you are willing to make the default dialer. Emulator strongly preferred — from step 3 onwards you need to place real calls, and adb emu gsm call is the only way to do that without a second phone.
  • A Gradle wrapper. Copy gradlew, gradlew.bat and gradle/wrapper/ from any recent project, or run gradle wrapper --gradle-version 8.14.3 if you have Gradle installed.
Step 01

01An empty directory that compiles

No app yet, no UI, nothing to look at. The goal is a green build, because every later failure is easier to read when you know the build itself is sound.

Learning Objectives

  • Lay out a two-module KMP project: a shared module and an Android app
  • Pin every version in one place with a version catalog
  • Understand why the root build file declares plugins it does not apply

Beginner Five files

Create these, and nothing else. Paths are relative to your project root.

gradle/libs.versions.toml

[versions]
kotlin = "2.2.20"
agp = "8.13.2"

[plugins]
kotlin-multiplatform = { id = "org.jetbrains.kotlin.multiplatform", version.ref = "kotlin" }
android-application = { id = "com.android.application", version.ref = "agp" }
android-library = { id = "com.android.library", version.ref = "agp" }

The catalog is the single place a version number appears. Without it you get versions scattered across build files, and the failure mode is not a clear error — it is two modules resolving different copies of the same library and a cryptic crash at runtime.

settings.gradle.kts

rootProject.name = "CallBlocker"

pluginManagement {
    repositories { google(); gradlePluginPortal(); mavenCentral() }
}

dependencyResolutionManagement {
    repositories { google(); mavenCentral() }
}

include(":shared")
include(":androidApp")

build.gradle.kts (root)

plugins {
    alias(libs.plugins.kotlin.multiplatform) apply false
    alias(libs.plugins.android.application) apply false
    alias(libs.plugins.android.library) apply false
}

WHY apply false. The root project is not itself a Kotlin or Android module — it has no source. Declaring the plugins here puts them on the classpath once, at a single version, so the module build files can alias(...) them without repeating a version. Applying them at the root would try to make the root an Android module, which it is not.

shared/build.gradle.kts

plugins {
    alias(libs.plugins.kotlin.multiplatform)
    alias(libs.plugins.android.library)
}

kotlin {
    jvmToolchain(17)
    androidTarget()
}

android {
    namespace = "dev.example.callblocker.shared"
    compileSdk = 36
    defaultConfig { minSdk = 26 }
}

SCOPE One target, androidTarget(). A real KMP project adds iosArm64() and friends here, and Corta Spam does. Adding iOS now buys you nothing and costs you a Kotlin/Native toolchain download plus a second class of build error to debug while you are still trying to get one platform running.

shared/src/commonMain/kotlin/dev/example/callblocker/Greeting.kt

GOTCHA — "plugin not found" on the first sync

Almost always pluginManagement missing google(). The Android Gradle Plugin does not live on Maven Central, and the error names the plugin rather than the repository, so it reads like a version problem.

Step 02

02A Composable you can actually see

One line of text, on a device. This step has three traps in it and every one of them produced a build or a screen that looked fine.

Learning Objectives

  • Wire Compose Multiplatform into a shared module and consume it from an Android app
  • Know which Kotlin plugin the app module wants, and what it costs to pick the other one
  • Learn the difference between "the build is green" and "the feature works"

Beginner Adding Compose to the catalog

Add to [versions]: compose-multiplatform = "1.11.1" and androidx-activityCompose = "1.9.3". Add the plugins compose-multiplatform (org.jetbrains.compose) and compose-compiler (org.jetbrains.kotlin.plugin.compose, version.ref kotlin), plus the library androidx-activity-compose. Declare both new plugins apply false in the root build file.

WHY two Compose plugins. org.jetbrains.compose supplies the multiplatform artifacts — the compose.runtime, compose.material3 accessors. kotlin.plugin.compose is the compiler plugin that rewrites your @Composable functions. Since Kotlin 2.0 the second is versioned with Kotlin, not with Compose, which is why its version.ref is kotlin. Getting this pair wrong produces "This version of the Compose Compiler requires Kotlin version ...", which names versions that both look correct.

shared/build.gradle.kts — add to the existing file

kotlin {
    sourceSets {

GOTCHA 1 — the app module is not a KMP module

Using kotlin.multiplatform here instead of kotlin.android is the obvious-looking choice and it fails like this:

A problem was found with the configuration of task ':androidApp:processDebugMainManifest'.
  property 'mainManifest' specifies file '.../androidApp/src/androidMain/AndroidManifest.xml'
  which doesn't exist.

With the KMP plugin, AGP expects the Android source set layout — src/androidMain/, not src/main/. Either layout works, but you must pick one knowingly. This tutorial uses kotlin.android and src/main/, which is what Corta Spam does: the app module is one platform's shell, all the shared code is in :shared, and there is nothing multiplatform about it to justify the extra ceremony.

GOTCHA 3 — the checkpoint that passes while the screen is blank

Without NoActionBar in the manifest above, all of this is true at once: BUILD SUCCESSFUL, the install succeeds, and:

$ adb shell dumpsys activity activities | grep ResumedActivity:
  ResumedActivity: ActivityRecord{... dev.example.callblocker/.MainActivity}

…and the screen shows an empty page with a title bar. Every signal says it works. Ask the device what it is actually drawing:

$ adb shell uiautomator dump /sdcard/ui.xml && adb shell cat /sdcard/ui.xml
text="Call blocker — nothing blocked yet" ... bounds="[0,0][777,72]"
resource-id="android:id/action_bar_container" ... bounds="[0,0][1344,319]" drawing-order="2"

Your text is at y=0–72. The platform's action bar covers y=0–319 and is drawn after it. The content was never missing; it was underneath. uiautomator dump is the tool to reach for whenever a screen is wrong in a way a screenshot cannot explain — it is the difference between "Compose is broken" and "one theme attribute".

Still wrong, and deliberately left

With the theme fixed, the text now draws under the status bar clock. That is edge-to-edge display without insets handling, and the fix (enableEdgeToEdge() plus a windowInsets-aware layout) belongs with real layout work rather than here. Noting it and moving on is a deliberate choice — but noting it is not optional, because an unrecorded known-wrong thing is indistinguishable from an unnoticed one.

Step 03

03Becoming the phone app

This is the step that decides whether the project is possible. Android does not let an ordinary app watch incoming calls. To see a call before it rings you must be the dialer, and taking that role costs you the whole in-call experience — you now owe the user an answer screen, a ringtone, and a call log. Do it now, while there is nothing to lose.

Learning Objectives

  • Know what ROLE_DIALER actually requires of your manifest
  • Bind an InCallService and confirm Telecom is talking to yours
  • Grant the role from adb so you can iterate without tapping through system dialogs

Intermediate Eligibility is decided by your manifest

The role is not something you ask for and receive. AOSP's roles.xml lists required components, and an app missing any of them is not offered in the "Phone app" picker at all — with no error explaining why. You need both ACTION_DIAL activity filters (with and without the tel scheme) and an InCallService.

androidApp/src/main/AndroidManifest.xml — inside <application>

<activity android:name=".MainActivity" android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
    </intent-filter>
    <intent-filter>
        <action android:name="android.intent.action.DIAL" />
        <category android:name="android.intent.category.DEFAULT" />
    </intent-filter>
    <intent-filter>
        <action android:name="android.intent.action.DIAL" />
        <category android:name="android.intent.category.DEFAULT" />
        <data android:scheme="tel" />
    </intent-filter>
</activity>

<service
    android:name=".ScreeningInCallService"
    android:permission="android.permission.BIND_INCALL_SERVICE"
    android:exported="true">
    <meta-data android:name="android.telecom.IN_CALL_SERVICE_UI" android:value="true" />
    <intent-filter>
        <action android:name="android.telecom.InCallService" />
    </intent-filter>
</service>

WHY exported="true" on a service you never want another app to call: Telecom is another process and must be able to bind it. The android:permission line is what makes that safe — only a caller holding BIND_INCALL_SERVICE, which is system-only, can connect.

androidApp/src/main/kotlin/dev/example/callblocker/ScreeningInCallService.kt

class ScreeningInCallService : InCallService() {
    override fun onCallAdded(call: Call) {
        super.onCallAdded(call)
        val number = call.details?.handle?.schemeSpecificPart.orEmpty()
        Log.i(TAG, "onCallAdded number=$number state=${call.state}")
    }

    override fun onCallRemoved(call: Call) {
        super.onCallRemoved(call)
        Log.i(TAG, "onCallRemoved")
    }

    private companion object { const val TAG = "CallBlocker" }
}

Also declare the hardware you now depend on: <uses-feature android:name="android.hardware.telephony" android:required="true" />. A device with no telephony has no calls to screen.

Advanced Taking the role without touching the screen

In the finished app you request the role properly, through RoleManager.createRequestRoleIntent(ROLE_DIALER), because that is the only way a real user can grant it. While developing, do it from adb:

adb shell cmd role add-role-holder android.app.role.DIALER dev.example.callblocker
adb shell cmd role get-role-holders android.app.role.DIALER

CHECKPOINT 3

adb logcat -c
adb emu gsm call 5551234567
sleep 6 && adb emu gsm cancel 5551234567
adb logcat -d -s CallBlocker:I

What must appear:

I CallBlocker: onCallAdded number=5551234567 state=2
I CallBlocker: onCallRemoved

state=2 is Call.STATE_RINGING. You are now seeing a call before the user does, which is the entire premise of the app.

GOTCHA — the role says you, the calls go elsewhere

There are two mechanisms and they can disagree. cmd role get-role-holders can name your package while Telecom keeps binding a different app, because telecom set-default-dialer sets a separate override that wins. Symptom: no log line, and Telecom's own log naming somebody else:

$ adb logcat -d | grep ComponentInfo | grep InCallService
InCallController: ... ComponentInfo{some.other.app/....PassthroughInCallService}

Set both, and read Telecom's log rather than the role list when they disagree: adb shell telecom set-default-dialer dev.example.callblocker.

What you now owe the user

Declaring IN_CALL_SERVICE_UI means the platform dialer's in-call screen no longer appears — yours is expected instead, and you do not have one yet. Until step 7 the emulator will ring with no answer UI. That is the debt this step takes on deliberately, and it is why taking the role early is right: discovering it after building a settings screen would mean rebuilding around it.

Step 04

04The number, and what it is not

You have a number in a log line. Before building anything on it, be clear about what it is: a string chosen by the network, in whatever format the network felt like, which may be empty.

Learning Objectives

  • Read the handle off a Call safely
  • Know the three shapes an incoming handle really arrives in
  • Reject the assumption that two numbers are the same when their strings are equal

Beginner Reading the handle

private fun Call.handleNumber(): String =
    details?.handle?.schemeSpecificPart.orEmpty()

Both details and handle are genuinely nullable. A withheld or private caller arrives with no handle at all, and orEmpty() turning that into "" is a decision you are making — that an unknown caller is a caller with an empty number, not a crash and not a null to thread through everything downstream.

Intermediate Three shapes, one subscriber

The same person can reach you as any of these:

+34611998877     international, states its country
0034611998877    international via the European access code
611998877        national — the network dropped the country entirely

CONTRAST The obvious move is to strip everything that is not a digit and compare. It is wrong, and the wrongness is not academic: +34611998877 becomes 34611998877, the national form stays 611998877, and they are not equal — so a person in your contacts is treated as a stranger. Corta Spam shipped that bug, fixed it in the comparison function, and then shipped it again three days later because one caller normalised its input before handing it over.

The whole of step 8 is this problem. For now, only take away the rule: never compare phone numbers with ==.

CHECKPOINT 4

Place three calls and confirm your log prints each handle as the network gave it:

adb emu gsm call 5551234567
adb emu gsm call +34611998877
adb emu gsm call 611998877

Cancel each with adb emu gsm cancel <number>. You are looking for the strings to come back differently shaped, which is the fact step 8 exists to deal with.

Step 05

05A blocklist that survives a restart

Two tables and a repository. The interesting decision is not SQLDelight; it is that precedence between rules is not expressed in SQL.

Learning Objectives

  • Generate type-safe Kotlin from .sq files
  • Supply a driver per platform through expect/actual
  • Keep rule precedence in code where it can be tested

shared/src/commonMain/sqldelight/<package path>/AppDatabase.sq

CREATE TABLE BlockedNumber (
    id INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    number TEXT NOT NULL,
    label TEXT,
    created_at INTEGER NOT NULL DEFAULT (CAST(strftime('%s', 'now') AS INTEGER)),
    UNIQUE(number)
);

selectAllBlockedNumbers:
SELECT * FROM BlockedNumber ORDER BY created_at DESC;

insertBlockedNumber:
INSERT OR IGNORE INTO BlockedNumber(number, label) VALUES (?, ?);

WHY the precedence comment at the top of Corta Spam's schema — "evaluated in code, not SQL" — is the load-bearing decision. A single clever query joining blocklist, allowlist, patterns and countries would be untestable without a database and unreadable when a rule is added. In code it is a pure function over data you can construct in a test, and every rule in this app is now covered by unit tests that never touch SQLite.

shared/src/commonMain/kotlin/.../DriverFactory.kt

expect class DriverFactory {
    fun createDriver(): SqlDriver
}

The Android actual returns AndroidSqliteDriver. In unit tests you swap it for the JDBC driver and get a real SQLite engine in a headless JVM — which is how Corta Spam tests its persistence layer without an emulator.

CHECKPOINT 5

Insert a number at startup, kill the app (adb shell am force-stop dev.example.callblocker), relaunch, and read it back. Then look at the file itself — the strongest confirmation is the one that does not go through your own code:

GOTCHA — run-as only works on a debug build

On a release build it fails with "not debuggable", so every database-inspection habit you build here stops working exactly when you most want it — while checking a migration on the build you are about to ship. Step 06

06Your first blocked call

Everything so far has been observation. Now the app acts, and the cost of being wrong changes completely: a missed spam call is an annoyance, a missed real one can be an emergency.

Learning Objectives

  • Reject a call through Telecom
  • Decide what happens when your own decision code throws
  • Understand why the ringtone starts before the decision
override fun onCallAdded(call: Call) {
    super.onCallAdded(call)
    if (call.state == Call.STATE_RINGING) ringer.start()   // ring first

    serviceScope.launch {
        try {
            val decision = evaluate(call.handleNumber())
            if (decision.isBlocked) {
                ringer.stop()
                call.reject(false, null)
            }
        } catch (e: CancellationException) {
            throw e
        } catch (e: Exception) {
            // Fail open. The call is already ringing and stays ringing.
            Log.e(TAG, "Call evaluation failed, failing open", e)
        }
    }
}

WHY ring first, decide second. Evaluation touches a database and possibly the contacts provider. If you wait for it before ringing, a slow query drops a legitimate caller into silence. Ringing immediately and stopping a few hundred milliseconds later is the right trade: the worst case is a blocked spammer producing a quarter-second of ringtone.

WHY fail open, and why CancellationException is rethrown. Swallowing cancellation breaks structured concurrency — the coroutine keeps running after its scope is gone. Every other exception must not block the call: an unblocked nuisance is recoverable, a silently dropped emergency is not.

CHECKPOINT 6

Insert 5551234567 into BlockedNumber, then adb emu gsm call 5551234567. The call must end on its own, quickly. Then call a number that is not on the list and confirm it keeps ringing — a blocker that blocks everything passes the first half of this test and is completely broken.

GOTCHA — testing only the blocked path

Corta Spam's device suite has 14 scenarios and more than half assert that a call is allowed. The bugs that reach users are rarely "it failed to block"; they are "it blocked my mother". Step 8 is one of those.

Step 07

07Ringing, because now you must

The debt from step 3 comes due. Add IN_CALL_SERVICE_RINGING and Telecom stops ringing entirely, trusting you to do it.

<meta-data android:name="android.telecom.IN_CALL_SERVICE_RINGING" android:value="true" />

GOTCHA — the failure mode with no error anywhere

Corta Spam declared this meta-data and had no ringtone code at all. Telecom dutifully stood down; the app rang for nothing. As the default dialer it took every call in silence for months. Nothing crashed, no log line complained, and every unit test passed — there was no code to test.

A screenshot cannot catch this either. Three independent signals can, and all three are machine-readable:

# 1. Telecom confirms it handed ringing over
adb logcat -d | grep "letDialerHandleRinging=true"

# 2. YOUR uid owns a started player with the ringtone usage
adb shell dumpsys audio | grep -A3 "AudioPlaybackConfiguration"

# 3. the vibration running is attributed to your package
adb shell dumpsys vibrator_manager

Signal 1 alone is not enough: it proves the system stopped, not that you started. A ringtone you hear while testing signal 1 is missing proves nothing at all — that was the system ringing.

Honour the ringer mode exactly as the platform dialer does: silent does not ring, vibrate rings only through the vibrator, normal plays the user's chosen ringtone. Getting this wrong means your app rings in a meeting after the user silenced their phone.

CHECKPOINT 7

An unmatched number rings and all three signals agree. A blocked number produces no started player at all. Both halves matter; only asserting the first is how the silent-ringer bug survived.

Step 08

08Phone numbers are not strings

The step that decides whether your app is usable. Everything else can be wrong and merely annoying; this one blocks people the user knows.

Learning Objectives

  • Compare two numbers without guessing a region
  • See why a digit-suffix match is a security problem, not a shortcut
  • Understand how a correct comparison is disarmed by one careless caller

Beginner The problem, concretely

contact saved:  611 99 88 77        call arrives:  +34611998877     must match
contact saved:  +34611998877        call arrives:  611998877        must match
contact saved:  +34611998877        call arrives:  +51611998877     must NOT match

The third line is why this is hard. Spain's 611998877 and Peru's 611998877 are different people who share a national number.

Intermediate Two approaches that look right

CONTRAST 1 — compare the last 7–9 digits. This is what PhoneNumberUtils.compare does, and it is tempting because it makes all three lines above pass. It also makes a stranger who happens to share a tail match your allowlist. This function guards blocking; trading a correctness bug for a security-shaped one is a bad trade.

CONTRAST 2 — canonicalise everything to E.164 with a default region. Now you need the SIM or locale region, an ISO-to-dialling-code table, and a trunk-prefix rule that differs per country: dropping a leading zero is right for the UK and wrong for Italy, whose E.164 form keeps it. Three new failure modes for a guess you did not need to make.

Advanced Let the number state its own country

An international number already carries its country code, so stripping it yields the national significant number — exactly the form a contact card holds. No region guess required. The rule that makes the third line work is an asymmetry:

fun sameNumber(a: String, b: String): Boolean {
    if (digits(a) == digits(b)) return true

    val aIntl = toE164OrNull(a) != null
    val bIntl = toE164OrNull(b) != null
    if (aIntl && bIntl) {
        // Both state a country. Those are facts, not hints — only full E.164 equality.
        return toE164OrNull(a) == toE164OrNull(b)
    }
    // At least one is silent about its country, so the national form may bridge them.
    return comparisonKeys(b).any { it in comparisonKeys(a) }
}

WHY candidate sets rather than one canonical string per side: the trunk zero has to be available both stripped and intact, because the UK drops it in E.164 and Italy keeps it. Reducing each side to a single string satisfies one country and breaks the other.

GOTCHA — the fix that was only half applied

Corta Spam got this function right, tested it, shipped it — and users kept reporting that contacts were blocked. The function was never called with what it needed:

// the address-book scan, three days after the "fix"
numbers.add(normalizeForComparison(raw))   // digits only — the '+' is gone

A contact saved +34611998877 reached sameNumber as 34611998877, which states no country — so the asymmetry above could no longer split off 611998877, and a domestic call stopped matching. The contact's name still displayed correctly, because the name lookup used a different key set and was never wrong, which made the symptom look impossible.

The rule this leaves you with: a comparison function that depends on the shape of its input must say so where its callers will read it, and any normalisation upstream disables it silently. Put it on the interface.

CHECKPOINT 8

A table test over all four saved/incoming combinations, plus the cross-country pair that must not match. Then prove the test can fail: revert the fix, watch it go red, restore it. A regression test never seen failing is a test of nothing.

Step 09

09Proving it, on calls a machine places

You now have a call blocker. What you do not have is any reason to believe it works, because every check so far was you watching one call at a time.

Learning Objectives

  • Drive real calls from a script
  • Assert on the database rather than the screen
  • Recognise the two ways a green suite lies

Intermediate The harness

The emulator's fake modem is the whole reason this is automatable:

adb emu gsm call +34900111222     # place

Seed the rules by writing the database directly, place the call, then poll for a new call-log row and assert its action and rule type. Advanced Two ways a green suite lies

1. It asserts absence. A test that a blocked call produces no ringtone passes against an app with no ringtone code whatsoever. Corta Spam had six such tests and a ringer that never rang. Prefer positive assertions: assert the player started, not that nothing happened.

2. It never reaches the state. Every call test in that project covered calls that ring, get blocked, or get missed — never one that was answered. An Android 14 restriction crashed the app the instant any call was answered, and the suite stayed green because nothing had ever entered that state.

Both are the same defect: not in the assertions, but in the state space they cover. When a suite is green and a user is unhappy, ask which state the suite has never entered.

Where to go next

You have an app that is your phone's dialer, sees calls before they ring, blocks by rule, rings when it should and stays silent when it should not. What it does not have: an in-call screen worth using, a call log, notifications, quiet hours, contacts integration, more than one language, or an iOS target.
