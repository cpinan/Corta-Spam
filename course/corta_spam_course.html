Module 1: Gradle & The Build System

Learn how the project compiles, links dependencies, and packages into an APK.

Learning Objectives

  • Understand Kotlin DSL build files vs Groovy
  • Read version catalogs and plugin declarations
  • Grasp multi-module Gradle projects
  • See how dependency resolution prevents version conflicts

Beginner What is a build system?

Think of a recipe. You have ingredients (source files, libraries) and steps (compile Kotlin, link resources, sign APK). Gradle orchestrates every step. Before Gradle, developers ran javac, aapt, dx manually. Gradle automates this so one command — ./gradlew :androidApp:assembleDebug — produces a working APK.

Beginner The four build files you need to know

Every KMP Android project has this structure:

settings.gradle.kts    — "Here are my modules"
build.gradle.kts      — "Here are my shared plugins & config"
shared/build.gradle.kts   — "The KMP shared module"
androidApp/build.gradle.kts — "The Android app shell"

Intermediate Version Catalogs — libs.versions.toml

Single source of truth for all dependency versions. Without it, you'd have version numbers scattered across multiple files — upgrade one, forget another, get cryptic runtime crashes.

gradle/libs.versions.toml

[versions]
kotlin = "2.2.20"
agp = "8.7.3"
compose-multiplatform = "1.11.1"
sqldelight = "2.3.2"
koin = "4.2.0"

[libraries]
sqldelight-runtime = { module = "app.cash.sqldelight:runtime", version.ref = "sqldelight" }
koin-core = { module = "io.insert-koin:koin-core", version.ref = "koin" }

[plugins]
kotlin-multiplatform = { id = "org.jetbrains.kotlin.multiplatform", version.ref = "kotlin" }

Why this pattern: Upgrade Kotlin from 2.2.20 to 2.3.0? Change one line. All 8 plugins and libraries that reference kotlin update automatically. No hunting through Gradle files.

Intermediate Root build.gradle.kts — Plugin declarations

build.gradle.kts

plugins {
    alias(libs.plugins.kotlin.multiplatform) apply false
    alias(libs.plugins.compose.multiplatform) apply false
    alias(libs.plugins.android.application) apply false
}

Why apply false? These plugins are declared at the root level (so all subprojects know about them) but only applied in the modules that need them. The shared module applies kotlin.multiplatform; the Android app applies android.application. Without apply false, every subproject would get every plugin.

Intermediate settings.gradle.kts — Module registry

settings.gradle.kts

rootProject.name = "BloqueaLlamadas"

include(":shared")
include(":androidApp")

Gradle needs to know which directories are subprojects. Each include points to a directory with its own build.gradle.kts. The root project can configure them all at once in allprojects { } or subprojects { } blocks.

Advanced Dependency resolution strategy

Sometimes libraries pull in incompatible transitive dependencies. Koin 4.2.0 pulls androidx.activity-ktx 1.12.4 which needs AGP 8.9.1+. We're on 8.7.3 — crash.

build.gradle.kts (root)

allprojects {
    configurations.all {
        resolutionStrategy {
            force(
                "androidx.activity:activity:1.9.3",
                "androidx.activity:activity-ktx:1.9.3",
            )
        }
    }
}

Why: force() overrides whatever version any library requests. We pin to 1.9.3 which works with AGP 8.7.3. Koin only touches baseline ComponentActivity APIs present since 1.9.3 — safe downgrade.

Trade-off

Forcing versions is a hammer — use sparingly. If Koin 4.3.0 removes the need, remove the force block. Document why each force exists (see the comment in the real build file) so future maintainers know when it can be dropped.

Key Takeaways

  • Kotlin DSL (.kts) replaces Groovy — type-safe, IDE autocomplete
  • Version catalogs centralize dependency versions — one-line upgrades
  • apply false declares plugin availability without forcing it on all modules
  • resolutionStrategy.force() is a last resort for transitive dependency conflicts
Check your understanding (4 questions)

1. What happens if you remove apply false from a plugin in the root build.gradle.kts?

Every subproject would apply that plugin, even the shared module which doesn't need android.application. The build would fail because the shared module isn't an Android app.

2. Why use version.ref in the version catalog instead of hardcoding version numbers in build.gradle.kts?

Single source of truth. Upgrade Kotlin from 2.2.20 to 2.3.0 and all 8+ dependencies that reference kotlin update automatically. Prevents version-mismatch bugs.

3. What does resolutionStrategy.force() do, and when should you use it?

It overrides whatever version any transitive dependency requests. Use only as a last resort when a library demands a version incompatible with your build tools. Document the reason.

4. How does settings.gradle.kts connect to the other build files?

include(":shared") tells Gradle to look for shared/build.gradle.kts. Without the include, Gradle doesn't know the directory is a subproject module.

Module 2: KMM Architecture

How Kotlin Multiplatform shares code between Android and iOS without sacrificing platform APIs.

Learning Objectives

  • Understand the source set hierarchy
  • Master the expect/actual pattern
  • See how platform modules inject platform-specific dependencies
  • Compare KMP to alternatives (Flutter, React Native)

Beginner What is Kotlin Multiplatform?

KMP lets you write business logic once in Kotlin and compile it to JVM (Android), Native (iOS), JS (web), and Wasm. The key insight: you don't share UI code between platforms — each platform renders its own UI. But with Compose Multiplatform, even the UI can be shared.

In this project, commonMain holds all the logic: rule engine, repositories, ViewModels, Compose screens. androidMain and iosMain are thin layers (~4 files each) that provide platform-specific implementations.

Intermediate Source set hierarchy

shared/build.gradle.kts (source sets)

kotlin {
    androidTarget()
    iosArm64()
    iosSimulatorArm64()

    sourceSets {
        commonMain.dependencies {
            implementation(compose.runtime)
            implementation(libs.sqldelight.runtime)
            implementation(libs.koin.core)
        }
        androidMain.dependencies {
            implementation(libs.sqldelight.android.driver)
        }
        iosMain.dependencies {
            implementation(libs.sqldelight.native.driver)
        }
    }
}

Key insight: commonMain depends on sqldelight.runtime (pure Kotlin). androidMain adds the Android-specific driver; iosMain adds the Native driver. The expect/actual pattern bridges these at compile time.

Intermediate The expect/actual pattern

Declare an interface (or expect declaration) in commonMain. Each platform provides an actual implementation:

commonMain — ContactsGateway.kt

interface ContactsGateway {
    suspend fun contactNumbers(): Set<String>
    fun hasPermission(): Boolean
}

androidMain — AndroidContactsGateway.kt

class AndroidContactsGateway(private val context: Context) : ContactsGateway {
    override suspend fun contactNumbers(): Set<String> =
        withContext(Dispatchers.IO) {
            // Read from ContactsContract provider
            context.contentResolver.query(ContactsContract.CommonDataKinds.Phone.CONTENT_URI, ...)
        }
}

Why interfaces over expect class: expect class has Beta compiler limitations and can't accept constructor parameters that differ by platform. A plain interface in commonMain with platform actual implementations is the idiomatic KMP pattern.

Advanced Platform modules — wiring DI per platform

commonMain — KoinInit.kt

fun initKoin(appDeclaration: KoinAppDeclaration = {}) {
    startKoin {
        appDeclaration()
        modules(platformModule(), sharedModule)
    }
}

platformModule() is an expect fun — each platform returns its module with platform-specific bindings (Android Context, iOS NSApplication). The sharedModule is pure Kotlin, identical on all platforms.

KMP vs Alternatives

  • Flutter: Dart language (new skill), custom rendering engine (not native UI), no access to Telecom APIs without plugins
  • React Native: JavaScript bridge (performance overhead), platform modules needed for native APIs
  • KMP: Native Android APIs accessible with zero bridging. Same Kotlin skills as Android dev.

Key Takeaways

  • Put business logic in commonMain — it compiles everywhere
  • Use interfaces (not expect class) for platform abstractions — avoids Beta compiler issues
  • Platform modules inject platform-specific types via Koin
  • KMP is the most "Android-native" cross-platform option — no new language, no bridge
Check your understanding (3 questions)

1. Why use an interface in commonMain instead of expect class for DriverFactory?

expect class has Beta compiler limitations, can't have platform-specific constructor parameters, and triggers compiler warnings. A plain interface with platform actual implementations is the idiomatic and stable KMP pattern.

2. Can androidMain code use iOS APIs?

No. androidMain compiles only for the JVM/Android target. It can use Android SDK APIs (Context, ContactsContract). iosMain uses iOS frameworks. They never mix.

3. What happens if you put an Android-specific API call in commonMain?

Compilation fails for iOS. commonMain compiles for ALL targets simultaneously, so it can only use APIs available on all platforms (pure Kotlin, Compose Multiplatform, kotlinx libraries).

Module 3: Jetpack Compose — Declarative UI

Build native Android UI with pure Kotlin — no XML, no findViewById, no View hierarchy.

Learning Objectives

  • Understand declarative vs imperative UI
  • Master @Composable functions and recomposition
  • Use StateFlow and ViewModel for reactive state
  • Apply Material3 theming and Modifier chains

Beginner Imperative vs Declarative

Imperative (old XML way): "Find the TextView with ID 'title'. Set its text to 'Hello'. When data changes, find it again and update."

Declarative (Compose): "Here's a Text composable showing state.title. When state.title changes, the UI automatically re-renders."

No more findViewById, no more manual view updates, no more "my RecyclerView shows stale data" bugs. The UI is a function of state — UI = f(state).

Intermediate The @Composable function

CallScreen.kt (fragment)

@Composable
fun CallScreen(
    number: String,
    phase: CallUiPhase,
    onAnswer: () -> Unit,
    onDecline: () -> Unit,
) {
    MaterialTheme {
        Surface(modifier = Modifier.fillMaxSize()) {
            Column(modifier = Modifier.fillMaxSize().safeDrawingPadding().padding(24.dp)) {
                Text(
                    text = when (phase) {
                        CallUiPhase.RINGING -> "Incoming call"
                        CallUiPhase.ACTIVE -> "In call"
                        else -> ""
                    }, style = MaterialTheme.typography.labelLarge)
                Text(text = number, style = MaterialTheme.typography.headlineMedium)
            }
        }
    }
}

Every @Composable function:

  • Has no return value — it emits UI into the composition tree
  • Can call other @Composable functions
  • Re-executes ("recomposes") when its state inputs change
  • Runs on the main thread (unless explicitly shifted)

Intermediate State management — ViewModel + StateFlow

HomeViewModel.kt (fragment)

class HomeViewModel(
    private val callLogRepository: CallLogRepository,
    private val settingsRepository: SettingsRepository,
) : ViewModel() {
    private val _state = MutableStateFlow(HomeUiState())
    val state: StateFlow<HomeUiState> = _state.asStateFlow()

    val blockingEnabled: StateFlow<Boolean> =
        settingsRepository.blockingEnabled
            .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), true)

    init { refresh() }

    fun refresh() {
        viewModelScope.launch {
            val stats = callLogRepository.blockedStats()
            _state.value = HomeUiState(blockedToday = stats.today)
        }
    }
}

In the Composable:

val state by homeViewModel.state.collectAsState()
Text(text = "${state.blockedToday}")  // auto-updates when StateFlow emits

Why StateFlow over LiveData: LiveData is Android-only. StateFlow is pure Kotlin — works in KMP commonMain, works with Compose's collectAsState(), and integrates with coroutines naturally.

Advanced Modifier chains — order matters

// Padding added OUTSIDE the clickable area
Modifier.clickable { ... }.padding(16.dp)

// Padding added INSIDE — clickable area extends to padded bounds
Modifier.padding(16.dp).clickable { ... }

// Chaining: fill → safe drawing padding → content padding
Modifier.fillMaxSize().safeDrawingPadding().padding(24.dp)

Modifiers are applied outside-in: the leftmost modifier wraps everything to its right. safeDrawingPadding() must come before padding() to ensure the system bars inset is handled before the content padding is applied.

Key Takeaways

  • Compose is declarative: describe what the UI should be, not how to update it
  • @Composable functions re-execute when State reads change — this is recomposition
  • StateFlow + collectAsState() is the idiomatic state bridge in KMP
  • Modifier order determines layout behavior — always test your chains
Check your understanding (4 questions)

1. What triggers recomposition in Compose?

When a State object read by a @Composable function changes value. The Compose runtime tracks which composables read which states and re-executes only those that need updating.

2. Why use StateFlow instead of LiveData in KMP?

LiveData is an Android-only API. StateFlow is pure Kotlin (kotlinx.coroutines) and works in commonMain, making it available on iOS, JVM, and JS targets.

3. What happens if you call .padding(16.dp) before .clickable {} vs after?

Padding first: padding is INSIDE the clickable area — the entire padded region is tappable. Clickable first: only the inner (non-padded) area is tappable; the padding sits outside the clickable region.

4. What does stateIn(viewModelScope, WhileSubscribed(5000), true) do?

Converts a cold Flow to a hot StateFlow. WhileSubscribed(5000) keeps the upstream active for 5 seconds after the last subscriber disappears (prevents restart on config changes). The last argument (true) is the initial value.

Module 4: Navigation Compose

Move between screens while keeping state, passing arguments, and managing the back stack.

Learning Objectives

  • Define routes with typed arguments
  • Build a NavHost with composable destinations
  • Use launchSingleTop and popUpTo for correct navigation
  • Handle section-based navigation for bottom bars

Beginner Routes — String-based screen identifiers

object Routes {
    const val HOME = "home"
    const val CALL_LOG = "call_log/{filter}"
    const val STATS = "stats"
    const val SETTINGS = "settings"
    fun callLogRoute(filter: String = "all") = "call_log/$filter"
}

{filter} is a path parameter — it gets substituted at runtime. call_log/today, call_log/week, call_log/all all match the same route template.

Intermediate NavHost wiring

AppNavHost.kt (core pattern)

@Composable
fun AppNavHost(navController: NavHostController, ...) {
    NavHost(navController = navController, startDestination = Routes.HOME) {
        composable(Routes.HOME) {
            HomeScreen(onNavigateToCallLog = {
                navController.navigate(Routes.callLogRoute())
            })
        }
        composable(
            route = Routes.CALL_LOG,
            arguments = listOf(navArgument("filter") { type = NavType.StringType })
        ) { backStackEntry ->
            val filter = backStackEntry.arguments?.getString("filter") ?: "all"
            CallLogScreen(filter = filter)
        }
    }
}

Each composable() block registers a screen. When the navController navigates to that route, Compose creates (or reuses) the composable. The backStackEntry.arguments bundle contains the parsed route parameters.

Advanced Navigation options — preventing reload

The bug: User taps "Call Log" in the bottom bar repeatedly. Each tap navigates call_log/all → popUpTo(home) → navigate(call_log/all), which destroys and recreates the screen.

AppNavHost.kt — the fix

val navBackStackEntry by navController.currentBackStackEntryAsState()
val currentRoute = navBackStackEntry?.destination?.route
val selectedSection = routeSection(currentRoute)

onNavigate = { index ->
    val destination = sectionRoutes.getOrElse(index) { Routes.HOME }
    val isRoot = currentRoute in sectionRoutes ||
        (currentRoute?.startsWith("call_log") == true && destination.startsWith("call_log"))
    if (index == selectedSection && isRoot) return@AdaptiveScaffold // already here, skip
    navController.navigate(destination) {
        popUpTo(Routes.HOME)
        launchSingleTop = true
    }
}

Why two checks: launchSingleTop alone isn't enough — it prevents duplicate instances but popUpTo can still destroy the existing screen. The explicit isRoot check prevents any navigation when already on the section root. The call_log pattern check handles route templates where "call_log/{filter}" ≠ "call_log/all".

Key Takeaways

  • navArgument() with NavType enables type-safe argument passing
  • launchSingleTop = true reuses existing screen instead of creating duplicates
  • popUpTo(ROOT) clears the back stack when switching sections
  • Explicit route comparison prevents screen reload on same-tab taps
Check your understanding (3 questions)

1. What does launchSingleTop = true do?

If a destination matching the route already exists at the top of the back stack, it reuses it instead of creating a new instance. Prevents "screen stacking" when tapping the same nav item.

2. Why use popUpTo(Routes.HOME) when switching bottom nav tabs?

Without it, tapping between tabs would stack screens: [Home, CallLog, Home, BlockList, Home]. The back stack would grow indefinitely. popUpTo(HOME) clears everything and makes each tab feel like a fresh start.

3. How are route arguments like {filter} passed and retrieved?

They're part of the route string: "call_log/today". Navigation Compose parses them into the arguments bundle. The composable retrieves them via backStackEntry.arguments?.getString("filter").

Module 5: Adaptive Form Factors

Make the app look great on phones (portrait/landscape), foldables, and tablets with zero platform-specific code.

Learning Objectives

  • Detect WindowSizeClass at runtime
  • Switch between BottomBar and NavigationRail
  • Cap content width and center on wide screens
  • Implement two-pane list-detail on Expanded

Beginner Why adaptive?

Android apps run on everything from 4" phones to 14" tablets. A layout built for 360dp-wide phones looks absurdly stretched on 840dp+ tablets. The WindowSizeClass system gives three tiers so you can build one layout that works everywhere.

Intermediate WindowSizeClass detection

WindowSizeClass.kt

enum class WindowSizeClass { Compact, Medium, Expanded }

@Composable
fun rememberWindowSizeClass(): WindowSizeClass {
    val widthDp = LocalConfiguration.current.screenWidthDp
    return when {
        widthDp < 600 -> WindowSizeClass.Compact   // phone portrait
        widthDp < 840 -> WindowSizeClass.Medium    // phone landscape, small tablet
        else -> WindowSizeClass.Expanded               // tablet, desktop
    }
}

600dp and 840dp are Material Design canonical breakpoints. Respect them, don't invent your own — users recognize the pattern.

Intermediate AdaptiveScaffold — two scaffold modes

AdaptiveScaffold.kt (structure, ~150 lines)

when (windowSizeClass) {
    WindowSizeClass.Compact -> {
        Column {
            Box(modifier = Modifier.weight(1f)) { content() }
            NavigationBar {
                NavigationBarItem(selected = ..., onClick = { onNavigate(i) })
            }
        }
    }
    WindowSizeClass.Medium, WindowSizeClass.Expanded -> {
        Row {
            NavigationRail {
                NavigationRailItem(selected = ..., onClick = { onNavigate(i) })
            }
            Box(modifier = Modifier.weight(1f)) { content() }
        }
    }
}

NavigationBar (bottom) for Compact and NavigationRail (side) for Medium/Expanded. The content area is identical — only the chrome changes.

Advanced AdaptiveContent + two-pane layout

On wide screens, content looks best capped at 600dp and centered. Otherwise, a single-column form stretches across a 14" tablet looking absurd.

// CallLogScreen — one pane on phone, two panes on tablet
if (windowSizeClass == WindowSizeClass.Expanded) {
    Row {
        CallLogListPane(modifier = Modifier.width(340.dp).fillMaxHeight())
        CallLogDetailPane(modifier = Modifier.weight(1f).fillMaxHeight())
    }
} else {
    AdaptiveContent(windowSizeClass = windowSizeClass) {
        // single column, capped at 600dp
        LazyColumn { ... }
    }
}

340dp for the list pane is a Goldilocks width: wide enough for readable text, narrow enough that the detail pane has room on an 840dp screen (840 - 340 = 500dp remaining). On larger screens the detail pane grows via weight(1f).

Edge-to-edge

Android 15+ (targetSdk 36) enforces edge-to-edge — your content draws behind the status bar and navigation bar. WindowInsets.safeDrawing.only(Top + Horizontal) adds padding only where needed so content isn't hidden behind system chrome.

Key Takeaways

  • WindowSizeClass uses 600dp and 840dp Material Design breakpoints
  • NavigationBar (bottom) for Compact, NavigationRail (side) for larger
  • AdaptiveContent caps at 600dp — content looks silly stretched to 1400dp
  • Two-pane on Expanded: 340dp fixed list + weight(1f) detail — test on actual tablet
Check your understanding (3 questions)

1. Why 600dp and 840dp specifically?

These are Google's canonical Material Design breakpoints. 600dp is where a phone landscape or small tablet has room for a nav rail. 840dp is where a full-size tablet can support two-pane layouts.

2. What happens if you use NavigationBar on an Expanded screen?

It would work but look wrong — a bottom bar stretches across the full tablet width while your eyes track a completely different focal point than on a phone. The nav rail keeps navigation near your thumb/pointer in landscape.

3. Why weight(1f) on the detail pane instead of a fixed width?

A fixed width would work on exactly one screen size. weight(1f) means "take all remaining space" — it grows/shrinks with the window, working on 840dp and 1200dp tablets alike.

Module 6: SQLDelight — Type-Safe SQL for KMP

Persist rules, call logs, and settings with a database that works identically on Android and iOS.

Learning Objectives

  • Write .sq files with valid SQL and named queries
  • Design schema with migrations (5 versions)
  • Implement the Repository pattern over SQLDelight
  • Handle platform-specific drivers via DriverFactory

Beginner Why SQLDelight over Room?

Room is Android-only (uses annotation processing, ties to Android lifecycle). SQLDelight generates Kotlin from .sq files — works on JVM, Native, JS. For KMP, it's the standard choice.

Intermediate Schema design

AppDatabase.sq (7 tables)

CREATE TABLE BlockedNumber (
    id INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    number TEXT NOT NULL,
    label TEXT,
    created_at INTEGER NOT NULL DEFAULT (CAST(strftime('%s','now') AS INTEGER)),
    UNIQUE(number)
);

-- Named query → generates Kotlin function
selectAllBlockedNumbers:
SELECT * FROM BlockedNumber ORDER BY created_at DESC;

insertBlockedNumber:
INSERT OR IGNORE INTO BlockedNumber(number, label) VALUES (?, ?);

Pattern: each table gets CRUD queries: selectAll, insert, deleteById, toggle. The CallLogEntry table uses CHECK constraints for type safety on the action column.

Advanced Migrations & timestamp portability

The app has 5 migration files (1.sqm through 5.sqm). Each adds columns or tables without breaking existing data:

-- 1.sqm: initial schema
ALTER TABLE BlockedNumber ADD COLUMN label TEXT;

Critical decision: timestamps use strftime('%s', 'now') instead of unixepoch(). Why? unixepoch() needs SQLite 3.38+ — not available on older Android devices (confirmed crash on API 33 emulator). strftime() has been available since SQLite 3.0.

Advanced Repository pattern — interface + SQL impl

RuleRepository (interface in commonMain)

interface RuleRepository {
    fun blockedNumbers(): Flow<List<BlockedNumberEntry>>
    suspend fun addBlockedNumber(number: String)
    suspend fun removeBlockedNumber(id: Long)
}

SqlRuleRepository (SQLDelight implementation)

class SqlRuleRepository(private val db: AppDatabase) : RuleRepository {
    override fun blockedNumbers() = db.appDatabaseQueries
        .selectAllBlockedNumbers()
        .asFlow().mapToList()
}

Why Flow: SQLDelight's asFlow() emits on every database change. ViewModels collect these flows and the UI auto-updates — no polling, no manual refresh.

Key Takeaways

  • SQLDelight is the KMP-standard database — Room is Android-only
  • Named queries in .sq files generate type-safe Kotlin functions
  • asFlow().mapToList() gives reactive query results — UI auto-updates on writes
  • Use strftime() not unixepoch() for portable timestamp handling
Check your understanding (4 questions)

1. How does a named query like selectAllBlockedNumbers become a Kotlin function?

SQLDelight's Gradle plugin reads the .sq file at compile time and generates a Kotlin function with the same name, typed parameters for WHERE clauses, and typed return values.

2. Why Flow as the return type for list queries?

asFlow() triggers a re-emission whenever the underlying table changes. A ViewModel collecting this Flow automatically gets fresh data after any insert/delete — no manual refresh calls needed.

3. Why not use unixepoch() for timestamps?

unixepoch() requires SQLite 3.38+ which isn't bundled on older Android versions (confirmed crash on API 33). strftime('%s', 'now') works on all SQLite versions since 3.0.

4. What does INSERT OR IGNORE do?

If a row with the same UNIQUE constraint already exists, the insert is silently skipped (no error). Used here for number which has a UNIQUE constraint — prevents duplicate entries.

Module 7: Koin — Dependency Injection

Wire up repositories, ViewModels, and platform services without annotation processing or code generation.

Learning Objectives

  • Define modules with single, factory, get()
  • Inject dependencies in Activity, Service, and ViewModel
  • Split modules into shared and platform-specific
  • Compare Koin to Dagger/Hilt

Beginner Why DI matters

Without DI, every class creates its own dependencies:

class HomeViewModel() {
    private val repo = SqlRuleRepository(createDatabase(AndroidDriverFactory(context)))
    // hard to test — can't swap the database for a fake
}

With DI, dependencies are passed in:

class HomeViewModel(
    private val callLogRepository: CallLogRepository, // interface!
) : ViewModel()

Tests pass a fake CallLogRepository. Production passes the SQL one. Koin decides which at startup.

Intermediate Module definitions

SharedModule.kt

val sharedModule = module {
    single { createDatabase(get()) }                // one DB instance for app lifetime
    single<RuleRepository> { SqlRuleRepository(get()) }   // bound to interface
    single<CallLogRepository> { SqlCallLogRepository(get()) }
    factory { HomeViewModel(get(), get()) }            // new VM each time
    factory { CallLogViewModel(get()) }
}

single = one instance for the application lifetime (database, repositories). factory = new instance each time requested (ViewModels — they're scoped by the platform).

Advanced Platform module composition

KoinInit.kt (commonMain)

fun initKoin(appDeclaration: KoinAppDeclaration = {}) {
    startKoin {
        appDeclaration()
        modules(platformModule(), sharedModule)   // platform first!
    }
}

PlatformModule.android.kt (androidMain)

actual fun platformModule(): Module = module {
    single<DriverFactory> { AndroidDriverFactory(androidContext()) }
    single<DefaultDialerGateway> { AndroidDefaultDialerGateway(androidContext()) }
    factory { DialerOnboardingViewModel(get()) }
}

Why platform first: sharedModule needs DriverFactory (from platformModule) to create the database. Platform module registers the concrete implementation; shared module uses it via get().

Koin vs Dagger/Hilt

  • Dagger/Hilt: Compile-time DI with annotation processing. Faster at runtime, catches mistakes at build time. But generates code (longer builds), Java-only patterns, Android-specific Hilt.
  • Koin: Runtime DI with a DSL. No code generation, works in KMP, simpler mental model. Trade-off: misconfigurations crash at runtime instead of compile time.
  • Why Koin here: KMP compatibility. Dagger/Hilt don't work in Kotlin/Native (iOS). Koin's pure-Kotlin approach works everywhere.

Key Takeaways

  • single = app lifetime (DB, repos). factory = new per request (ViewModels)
  • Platform module provides platform-specific types (DriverFactory with Android Context)
  • Shared module consumes them via get() — always binds to interfaces, never concrete types
  • Koin is the KMP-compatible DI choice — Dagger/Hilt don't work on iOS
Check your understanding (3 questions)

1. What's the difference between single and factory in Koin?

single creates one instance and reuses it for the app lifetime (like a singleton). factory creates a new instance every time it's requested — appropriate for ViewModels which have their own scoping.

2. Why must platformModule be registered before sharedModule?

sharedModule uses get() to resolve DriverFactory, which is registered in platformModule. If sharedModule tried to resolve it before platformModule registered it, Koin would throw a definition-not-found error at startup.

3. Why bind to interfaces (single<RuleRepository>) instead of concrete types?

Testing. Tests can provide a fake RuleRepository implementation that returns predictable data. If code depended on SqlRuleRepository directly, you'd need a real SQLite database for every test — slow and fragile.

Beginner Permission types

1. What's the difference between a dangerous permission and a system role?

Dangerous permissions (READ_CONTACTS) show a simple Allow/Deny dialog. System roles (ROLE_DIALER) launch a full-system dialog that makes the app the default handler for that capability. Roles are higher-privilege and more intrusive to the user.

2. Why use ActivityResultContracts instead of onRequestPermissionsResult?

The old API could miss callbacks on configuration changes (rotation). The new contract-based API registers before the Activity starts, surviving configuration changes. It's also type-safe — each contract has typed inputs/outputs.

3. What happens if the user denies READ_CONTACTS but auto-allow contacts is enabled?

The contacts list is never populated (hasPermission() returns false). Calls from contacts won't be auto-allowed. The app still works — it just can't use that feature. This is graceful degradation, not a crash.

4. Why re-check isDefaultDialer() in onResume()?

The user can change the default dialer from Android Settings at any time while the app is in the background. onResume detects this change and updates the onboarding screen accordingly.

Module 9: Telecom & InCallService

Intercept incoming calls, evaluate them against rules, and show custom ring/reject UI — all in real time.

Learning Objectives

  • Implement InCallService as the default dialer's call handler
  • Evaluate calls synchronously but show UI instantly
  • Handle lock screen and keyguard for incoming call UI
  • Implement auto-responder with TTS and custom audio

Beginner What is InCallService?

Android's Telecom framework manages the phone stack. When your app is the default dialer, InCallService is the callback that fires on every incoming and outgoing call. You get a Call object with the phone number, state (ringing/active/disconnected), and methods to answer() or reject().

Intermediate Service manifest + lifecycle

AndroidManifest.xml (service declaration)

<service
    android:name=".telecom.PassthroughInCallService"
    android:permission="android.permission.BIND_INCALL_SERVICE"
    android:exported="true">
    <meta-data android:name="android.telecom.IN_CALL_SERVICE_UI" android:value="true" />
    <meta-data android:name="android.telecom.IN_CALL_SERVICE_RINGING" android:value="true" />
    <intent-filter>
        <action android:name="android.telecom.InCallService" />
    </intent-filter>
</service>

IN_CALL_SERVICE_UI = true: "I will show the call UI myself — don't show the system UI." IN_CALL_SERVICE_RINGING = true: "I handle ringing calls." Without these metadata flags, Android shows its own incoming call screen on top of yours.

Advanced Show UI instantly — the race condition

PassthroughInCallService.kt (critical flow)

override fun onCallAdded(call: Call) {
    val number = call.details?.handle?.schemeSpecificPart.orEmpty()

    // STEP 1: Show UI IMMEDIATELY — don't wait for rule evaluation
    InCallState.attach(call)   // sets ringing state for InCallActivity to read
    startActivity(Intent(this, InCallActivity::class.java)
        .addFlags(Intent.FLAG_ACTIVITY_NEW_TASK))

    // STEP 2: Evaluate rules asynchronously
    serviceScope?.launch {
        val decision = evaluateCall(number)
        if (decision.isBlocked) {
            val autoConfig = autoResponderRepository.config.first()
            if (autoConfig.enabled) {
                call.registerCallback(callCallback)
                call.answer(VideoProfile.STATE_AUDIO_ONLY)  // answer for auto-responder
            } else {
                call.reject(false, null)           // silent reject
            }
        }
        // If allowed: InCallActivity already showing — user decides answer/decline
    }
}

Why show UI first, evaluate later: If you evaluate before showing UI and the evaluation takes 500ms (DB queries, contact lookup), Android shows its own system incoming-call UI because it thinks you're not responding. By showing InCallActivity immediately, the system sees your UI and stays out of the way. If the call turns out to be blocked, call.reject() dismisses it.

Advanced InCallState — the singleton bridge

InCallState.kt

object InCallState {
    private val _state = MutableStateFlow<UiState?>(null)
    val state: StateFlow<UiState?> = _state.asStateFlow()

    fun attach(call: Call) {
        _state.value = UiState(number = ..., phase = call.state.toPhase())
        call.registerCallback(callback)  // track state changes
    }

    fun answer() = call?.answer(0)
    fun decline() = call?.reject(false, null)
}

Uses object (Kotlin singleton) because there's only ever one active call at a time (by design). The StateFlow bridges the Service (where the Call object lives) to the Activity (where the UI runs) — they're in separate processes/contexts.

Advanced Lock screen & keyguard

InCallActivity.kt

override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    setShowWhenLocked(true)           // show even if device is locked
    setTurnScreenOn(true)              // wake screen if off

    val kgm = getSystemService(Context.KEYGUARD_SERVICE) as? KeyguardManager

Without setShowWhenLocked(true), the incoming call UI would be hidden behind the lock screen — you'd hear ringing but see nothing. requestDismissKeyguard lets the user answer without unlocking first.

Key Takeaways

  • IN_CALL_SERVICE_UI and IN_CALL_SERVICE_RINGING metadata tells Android to use your UI
  • Show the InCallActivity FIRST, evaluate rules SECOND — wins the race against system UI
  • InCallState as a singleton bridges the Service (has Call object) to the Activity (shows UI)
  • setShowWhenLocked + requestDismissKeyguard are mandatory for incoming call UX
Check your understanding (4 questions)

1. Why start InCallActivity before rule evaluation?

If you delay while evaluating rules, the system sees your InCallService as unresponsive and shows its own incoming call UI instead. Starting the activity first preempts this race condition.

2. What does IN_CALL_SERVICE_RINGING = true do?

It tells Android that your InCallService handles the ringing state. Without it, the system shows its own ringing notification alongside your UI — the user sees two overlapping call screens.

3. Why use a singleton object for InCallState instead of a regular class?

There's only one active call at a time by design. A singleton provides simplicity — the Service writes to it, the Activity reads from it. Both access the same StateFlow without needing to coordinate instances.

4. What's the difference between call.reject(false, null) and calling finish() on the Activity?

call.reject() tells Telecom to reject the call — the caller gets a busy signal. finish() only closes your Activity; the call would continue ringing in the background. You must use Telecom APIs to actually control the call.

Module 10: Rule Precedence Engine

Design a decision system that evaluates every incoming call against 7 rule types in strict order — pure, testable, fast.

Learning Objectives

  • Design a stateless ResolveContext pattern
  • Implement strict precedence ordering
  • Normalize phone numbers for cross-format matching
  • Build glob-style pattern matching

Beginner What does a call blocker decide?

Every incoming call needs one of three outcomes: BLOCK (reject), ALLOW (let through), or AUTO_RESPOND (answer with greeting). The rule engine checks 7 rule types in fixed order and returns the first match. If nothing matches, the "default action" setting takes over.

Intermediate ResolveContext — stateless input

RulePrecedenceResolver.kt

data class ResolveContext(
    val allowlistedNumbers: Set<String>,
    val contactNumbers: Set<String> = emptySet(),
    val blockedNumbers: Set<String>,
    val enabledPatterns: List<PatternRule>,
    val enabledCountryCodes: Set<String>,
    val defaultAction: DefaultAction = DefaultAction.ALLOW,
    // ... plus spam provider, action rules, schedule rules
)

Why a data class, not global state: The resolver is a pure function: evaluate(number, context) → Decision. All inputs are in the data class. No mutable state. This makes it trivially testable — create a context, check the output. No mock servers, no database setup, no race conditions.

Intermediate Precedence order (7 levels)

The order is deliberate and tested at each step:

// 1. MANUAL BLOCK — user explicitly chose to block this exact number
if (normalized in context.blockedNumbers) return RuleDecision.ManualBlock

// 2. ALLOWLIST — contacts + manual allowlist override everything below
if (normalized in mergedAllowlist) return RuleDecision.Allowlist

// 3. PATTERN — glob match (prefix, suffix, contains)
for (pattern in context.enabledPatterns) { ... }

// 4. COUNTRY — country code from libphonenumber-style parsing
val countryCode = parseCountryCode(number)

// 5. SPAM → 6. ACTION → 7. SCHEDULE

// 8. DEFAULT — allow, block, or ask (based on user settings)

Why manual block overrides contacts: If a user explicitly added mom's number to the block list, they have a reason. Respecting that explicit choice is more important than the auto-allow-contacts convenience feature.

Advanced Phone number normalization

The problem: A contact is stored as "(555) 123-4567". The incoming call arrives as "+15551234567". Direct string comparison fails — contacts aren't auto-allowed.

PhoneNumberParser.kt — the fix

fun normalizeForComparison(number: String): String =
    number.filter { it.isDigit() }

Applied everywhere: incoming call number, contact numbers, blocked/allowlist numbers, pattern cores. All comparisons now use digit-only strings. "+1 (555) 123-4567" → "15551234567" matches "+15551234567" → "15551234567".

Where normalization happens:

  • AndroidContactsGateway — normalizes contact numbers when reading from ContactsContract
  • RulePrecedenceResolver.evaluate() — normalizes the incoming number AND all stored numbers from context before comparison
  • matchesPattern() — normalizes both the pattern core and the target number

Advanced Pattern matching

RulePrecedenceResolver.matchesPattern()

internal fun matchesPattern(number: String, pattern: String): Boolean {
    val normalizedCore = normalizeForComparison(core)
    val normalizedNumber = normalizeForComparison(number)
    return when {
        startsWithStar && endsWithStar -> normalizedNumber.contains(normalizedCore)
        startsWithStar -> normalizedNumber.endsWith(normalizedCore)
        endsWithStar -> normalizedNumber.startsWith(normalizedCore)
        else -> normalizedNumber == normalizedCore
    }
}

Simple glob, not full regex: Full regex would be impossible to expand into concrete numbers for iOS's CallDirectory extension. Simple prefix/suffix/contains globs can be pre-computed into static lists that iOS can consume.

Key Takeaways

  • ResolveContext is a pure data class — no mutable state, no side effects, fully testable
  • Manual block overrides contacts — user's explicit choice beats convenience
  • Normalize ALL numbers to digits-only before comparison — cross-format matching
  • Glob patterns (not regex) keep the engine simple and iOS-compatible
Check your understanding (5 questions)

1. Why does manual block (step 1) override allowlist (step 2)?

The user explicitly chose to block this number. If the allowlist overrode manual blocks, adding your ex to the block list would be pointless — they'd just get through because they're also in your contacts.

2. What problem does normalizeForComparison() solve?

Phone numbers arrive in different formats: contacts store "(555) 123-4567", incoming calls arrive as "+15551234567". Direct string comparison would say these are different numbers. Normalization strips everything except digits so they match.

3. Why pass all data in a ResolveContext instead of having the resolver access the database directly?

Pure functions are testable. You can create any ResolveContext in a test and verify the output — no database, no mocks. If the resolver accessed the database, tests would need a running SQLite instance.

4. What happens if no rule matches and defaultAction is BLOCK?

The call is blocked via DefaultBlock. But only AFTER all 7 rule levels failed to match. If any rule (including allowlist) matched, it would have short-circuited earlier — the default only activates when nothing else applies.

5. Why not use full regex for pattern matching?

iOS's CallDirectory extension takes a static list of concrete numbers — it can't evaluate regex at runtime. Simple prefix/suffix/contains patterns can be expanded into concrete number lists that iOS can consume. Regex patterns would be Android-only.

Module 11: Internationalization & Localization

Support 4 languages with zero code changes — just add an XML file per locale.

Learning Objectives

  • Structure Compose Multiplatform string resources
  • Add new locales by creating values-XX directories
  • Avoid common pitfalls with format strings
  • Design string keys for translator-friendliness

Beginner How Compose resources work

String resources live in composeResources/ with locale-qualified directories. At build time, a Gradle plugin generates type-safe Kotlin accessors:

// You write:
<string name="call_log_action_block">Block this number</string>

// The plugin generates:
val Res.string.call_log_action_block: StringResource

// In your @Composable:
stringResource(Res.string.call_log_action_block)  // → "Block this number" (or locale equivalent)

Your IDE autocompletes Res.string. — you can never misspell a resource key.

Intermediate Locale directory structure

The app supports 4 locales:

DirectoryLanguageSpeaker Base
values/English (default)~1.5B speakers
values-es/Spanish (LATAM)~500M speakers
values-pt/Portuguese (Brazil)~260M speakers
values-hi/Hindi~600M speakers

When a user's device is set to es-PE (Spanish Peru), the system falls back: es-PE → es → en. Since values-es/ exists, Spanish strings are used. If we only had values-es-rMX/ (Mexico), a Peruvian user would see English.

Advanced Format string pitfalls

The bug: We wrote <string name="stats_blocked_count">%d blocked</string> and called stringResource(Res.string.stats_blocked_count, day.count). The screen showed "%d blocked" literally.

The fix: Compose Multiplatform's stringResource() vararg format doesn't always work as expected. Solution: use string interpolation with a separate translatable label:

// Instead of: "%d blocked" with format arg
// Use: $count + translatable "blocked" label
Text(text = "${day.count} ${stringResource(Res.string.stats_blocked_label)}")

Lesson: Always test format strings on device. What works in the IDE preview doesn't always work at runtime, especially with Compose Multiplatform resources.

Key Takeaways

  • Use locale-qualified directories — no code changes needed for new languages
  • Resource keys are type-safe via generated Kotlin — no misspellings at runtime
  • Format strings can be unreliable in Compose Multiplatform — test on device
  • Broad locale codes (es, pt) cover regional variants (es-PE, pt-BR) via fallback
Check your understanding (3 questions)

1. How do you add a new language (e.g., French) to the app?

Create values-fr/strings.xml, copy all string keys from values/strings.xml, translate the values. The Compose plugin auto-generates the Kotlin accessors — no code changes.

2. What happens if a key exists in values/ but not in values-es/?

The system falls back to the default locale (values/). The user sees the English string for that key. This is why it's important to keep all locale files in sync — missing keys mean mixed-language UI.

3. Why avoid %d format strings in Compose Multiplatform?

stringResource() format args don't always work reliably in Compose Multiplatform (the literal %d text may appear). Use string interpolation with separate translatable label strings instead.

Check your understanding (4 questions)

1. Why use fakes instead of MockK for testing repositories?

MockK is JVM-only — it can't run in Kotlin/Native (iOS tests). Fakes are plain Kotlin classes implementing the interface — they work in commonTest, androidUnitTest, and iOS tests without any mocking framework.

2. What does runTest { } do?

It provides a coroutine scope with a test dispatcher that runs coroutines synchronously (no real delays) and auto-advances virtual time. Suspend functions execute immediately without actual multithreading.

3. How does Robolectric test Compose UI without a device?

Robolectric provides a fake Android runtime on the JVM — it intercepts Android framework calls and returns realistic responses. Compose's rendering is simulated. No emulator process, no device needed.

4. Where should you put a test that calls ContactsContract.Phone.CONTENT_URI?

In androidUnitTest with Robolectric. commonTest can't access Android APIs. Robolectric's shadow framework provides a fake ContentResolver that returns test contact data.
