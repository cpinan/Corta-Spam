01Gradle & The Build System

Learn how the project compiles, links dependencies, and packages into an APK.

Learning Objectives

  • Understand Kotlin DSL build files vs Groovy
  • Read version catalogs and plugin declarations
  • Grasp multi-module Gradle projects
  • See how dependency resolution prevents version conflicts

Beginner What is a build system?

Think of a recipe. You have ingredients (source files, libraries) and steps (compile Kotlin, link resources, sign APK). Gradle orchestrates every step. Before Gradle, developers ran javac, aapt, dx manually. Gradle automates this so one command — ./gradlew :androidApp:assembleDebug — produces a working APK.

Beginner The four build files you need to know

Every KMP Android project has this structure:

settings.gradle.kts    — "Here are my modules"
build.gradle.kts      — "Here are my shared plugins & config"
shared/build.gradle.kts   — "The KMP shared module"
androidApp/build.gradle.kts — "The Android app shell"

Intermediate Version Catalogs — libs.versions.toml

Single source of truth for all dependency versions. Without it, you'd have version numbers scattered across multiple files — upgrade one, forget another, get cryptic runtime crashes.

gradle/libs.versions.toml

[versions]
kotlin = "2.2.20"
agp = "8.7.3"
compose-multiplatform = "1.11.1"
sqldelight = "2.3.2"
koin = "4.2.0"

[libraries]
sqldelight-runtime = { module = "app.cash.sqldelight:runtime", version.ref = "sqldelight" }
koin-core = { module = "io.insert-koin:koin-core", version.ref = "koin" }

[plugins]
kotlin-multiplatform = { id = "org.jetbrains.kotlin.multiplatform", version.ref = "kotlin" }
Why this pattern

Upgrade Kotlin from 2.2.20 to 2.3.0? Change one line. All 8 plugins and libraries that reference kotlin update automatically. No hunting through Gradle files.

Intermediate Root build.gradle.kts — Plugin declarations

build.gradle.kts

plugins {
    alias(libs.plugins.kotlin.multiplatform) apply false
    alias(libs.plugins.compose.multiplatform) apply false
    alias(libs.plugins.android.application) apply false
}

Why apply false? These plugins are declared at the root level (so all subprojects know about them) but only applied in the modules that need them. The shared module applies kotlin.multiplatform; the Android app applies android.application. Without apply false, every subproject would get every plugin.

Intermediate settings.gradle.kts — Module registry

settings.gradle.kts

rootProject.name = "BloqueaLlamadas"

include(":shared")
include(":androidApp")

Gradle needs to know which directories are subprojects. Each include points to a directory with its own build.gradle.kts. The root project can configure them all at once in allprojects { } or subprojects { } blocks.

Advanced Dependency resolution strategy

Sometimes libraries pull in incompatible transitive dependencies. Koin 4.2.0 pulls androidx.activity-ktx 1.12.4 which needs AGP 8.9.1+. We're on 8.7.3 — crash.

build.gradle.kts (root)

allprojects {
    configurations.all {
        resolutionStrategy {
            force(
                "androidx.activity:activity:1.9.3",
                "androidx.activity:activity-ktx:1.9.3",
            )
        }
    }
}
Why

force() overrides whatever version any library requests. We pin to 1.9.3 which works with AGP 8.7.3. Koin only touches baseline ComponentActivity APIs present since 1.9.3 — safe downgrade.

Trade-off

Forcing versions is a hammer — use sparingly. If Koin 4.3.0 removes the need, remove the force block. Document why each force exists (see the comment in the real build file) so future maintainers know when it can be dropped.

Key Takeaways

  • Kotlin DSL (.kts) replaces Groovy — type-safe, IDE autocomplete
  • Version catalogs centralize dependency versions — one-line upgrades
  • apply false declares plugin availability without forcing it on all modules
  • resolutionStrategy.force() is a last resort for transitive dependency conflicts
Check your understanding (4 questions)

1. What happens if you remove apply false from a plugin in the root build.gradle.kts?

Every subproject would apply that plugin, even the shared module which doesn't need android.application. The build would fail because the shared module isn't an Android app.

2. Why use version.ref in the version catalog instead of hardcoding version numbers in build.gradle.kts?

Single source of truth. Upgrade Kotlin from 2.2.20 to 2.3.0 and all 8+ dependencies that reference kotlin update automatically. Prevents version-mismatch bugs.

3. What does resolutionStrategy.force() do, and when should you use it?

It overrides whatever version any transitive dependency requests. Use only as a last resort when a library demands a version incompatible with your build tools. Document the reason.

4. How does settings.gradle.kts connect to the other build files?

include(":shared") tells Gradle to look for shared/build.gradle.kts. Without the include, Gradle doesn't know the directory is a subproject module.

02KMM Architecture

How Kotlin Multiplatform shares code between Android and iOS without sacrificing platform APIs.

Learning Objectives

  • Understand the source set hierarchy
  • Master the expect/actual pattern
  • See how platform modules inject platform-specific dependencies
  • Compare KMP to alternatives (Flutter, React Native)

Beginner What is Kotlin Multiplatform?

KMP lets you write business logic once in Kotlin and compile it to JVM (Android), Native (iOS), JS (web), and Wasm. The key insight: you don't share UI code between platforms — each platform renders its own UI. But with Compose Multiplatform, even the UI can be shared.

In this project, commonMain holds all the logic: rule engine, repositories, ViewModels, Compose screens. androidMain and iosMain are thin layers (~4 files each) that provide platform-specific implementations.

Intermediate Source set hierarchy

shared/build.gradle.kts (source sets)

kotlin {
    androidTarget()
    iosArm64()
    iosSimulatorArm64()

    sourceSets {
        commonMain.dependencies {
            implementation(compose.runtime)
            implementation(libs.sqldelight.runtime)
            implementation(libs.koin.core)
        }
        androidMain.dependencies {
            implementation(libs.sqldelight.android.driver)
        }
        iosMain.dependencies {
            implementation(libs.sqldelight.native.driver)
        }
    }
}
Key insight

commonMain depends on sqldelight.runtime (pure Kotlin). androidMain adds the Android-specific driver; iosMain adds the Native driver. The expect/actual pattern bridges these at compile time.

Intermediate The expect/actual pattern

Declare an interface (or expect declaration) in commonMain. Each platform provides an actual implementation:

commonMain — ContactsGateway.kt

interface ContactsGateway {
    suspend fun contactNumbers(): Set<String>
    fun hasPermission(): Boolean
}

androidMain — AndroidContactsGateway.kt

class AndroidContactsGateway(private val context: Context) : ContactsGateway {
    override suspend fun contactNumbers(): Set<String> =
        withContext(Dispatchers.IO) {
            // Read from ContactsContract provider
            context.contentResolver.query(ContactsContract.CommonDataKinds.Phone.CONTENT_URI, ...)
        }
}

Why interfaces over expect class: expect class has Beta compiler limitations and can't accept constructor parameters that differ by platform. A plain interface in commonMain with platform actual implementations is the idiomatic KMP pattern.

Advanced Platform modules — wiring DI per platform

commonMain — KoinInit.kt

fun initKoin(appDeclaration: KoinAppDeclaration = {}) {
    startKoin {
        appDeclaration()
        modules(platformModule(), sharedModule)
    }
}

platformModule() is an expect fun — each platform returns its module with platform-specific bindings (Android Context, iOS NSApplication). The sharedModule is pure Kotlin, identical on all platforms.

KMP vs Alternatives

  • Flutter: Dart language (new skill), custom rendering engine (not native UI), no access to Telecom APIs without plugins
  • React Native: JavaScript bridge (performance overhead), platform modules needed for native APIs
  • KMP: Native Android APIs accessible with zero bridging. Same Kotlin skills as Android dev.

Common KMP iOS Pitfalls

iOS Kotlin/Native compilation often reveals issues hidden on JVM. The Corta Spam project hit several real-world gotchas:

  • Dispatchers.IO is marked @InternalCoroutinesApi on Kotlin/Native — crashes at compile time. Use Dispatchers.Default or an expect/actual dispatcher.
  • kotlinx.datetime.Clock.System may not resolve on all Native toolchains — platform-specific time providers (expect/actual) are more reliable.
  • Navigation Compose KMP Bundle.getString() doesn't compile for iOS — cast to Map<String, *> instead.
  • Koin must be initialized manually on iOS — Android's Application.onCreate() doesn't exist on iOS.
  • Compose Multiplatform Metal GPU rendering may hang on certain iOS simulators — restart the simulator or test on a different device model.

See Chapter 14 for full debugging procedures and real crash logs for each of these errors.

Key Takeaways

  • Put business logic in commonMain — it compiles everywhere
  • Use interfaces (not expect class) for platform abstractions — avoids Beta compiler issues
  • Platform modules inject platform-specific types via Koin
  • KMP is the most "Android-native" cross-platform option — no new language, no bridge
Check your understanding (3 questions)

1. Why use an interface in commonMain instead of expect class for DriverFactory?

expect class has Beta compiler limitations, can't have platform-specific constructor parameters, and triggers compiler warnings. A plain interface with platform actual implementations is the idiomatic and stable KMP pattern.

2. Can androidMain code use iOS APIs?

No. androidMain compiles only for the JVM/Android target. It can use Android SDK APIs (Context, ContactsContract). iosMain uses iOS frameworks. They never mix.

3. What happens if you put an Android-specific API call in commonMain?

Compilation fails for iOS. commonMain compiles for ALL targets simultaneously, so it can only use APIs available on all platforms (pure Kotlin, Compose Multiplatform, kotlinx libraries).

03Jetpack Compose — Declarative UI

Build native Android UI with pure Kotlin — no XML, no findViewById, no View hierarchy.

Learning Objectives

  • Understand declarative vs imperative UI
  • Master @Composable functions and recomposition
  • Use StateFlow and ViewModel for reactive state
  • Apply Material3 theming and Modifier chains

Beginner Imperative vs Declarative

Imperative (old XML way): "Find the TextView with ID 'title'. Set its text to 'Hello'. When data changes, find it again and update."

Declarative (Compose): "Here's a Text composable showing state.title. When state.title changes, the UI automatically re-renders."

No more findViewById, no more manual view updates, no more "my RecyclerView shows stale data" bugs. The UI is a function of state — UI = f(state).

Intermediate The @Composable function

CallScreen.kt (fragment)

@Composable
fun CallScreen(
    number: String,
    phase: CallUiPhase,
    onAnswer: () -> Unit,
    onDecline: () -> Unit,
) {
    MaterialTheme {
        Surface(modifier = Modifier.fillMaxSize()) {
            Column(modifier = Modifier.fillMaxSize().safeDrawingPadding().padding(24.dp)) {
                Text(
                    text = when (phase) {
                        CallUiPhase.RINGING -> "Incoming call"
                        CallUiPhase.ACTIVE -> "In call"
                        else -> ""
                    }, style = MaterialTheme.typography.labelLarge)
                Text(text = number, style = MaterialTheme.typography.headlineMedium)
            }
        }
    }
}

Every @Composable function:

  • Has no return value — it emits UI into the composition tree
  • Can call other @Composable functions
  • Re-executes ("recomposes") when its state inputs change
  • Runs on the main thread (unless explicitly shifted)

Intermediate State management — ViewModel + StateFlow

HomeViewModel.kt (fragment)

class HomeViewModel(
    private val callLogRepository: CallLogRepository,
    private val settingsRepository: SettingsRepository,
) : ViewModel() {
    private val _state = MutableStateFlow(HomeUiState())
    val state: StateFlow<HomeUiState> = _state.asStateFlow()

    val blockingEnabled: StateFlow<Boolean> =
        settingsRepository.blockingEnabled
            .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), true)

    init { refresh() }

    fun refresh() {
        viewModelScope.launch {
            val stats = callLogRepository.blockedStats()
            _state.value = HomeUiState(blockedToday = stats.today)
        }
    }
}

In the Composable:

val state by homeViewModel.state.collectAsState()
Text(text = "${state.blockedToday}")  // auto-updates when StateFlow emits
Why StateFlow over LiveData

LiveData is Android-only. StateFlow is pure Kotlin — works in KMP commonMain, works with Compose's collectAsState(), and integrates with coroutines naturally.

Advanced Modifier chains — order matters

// Padding added OUTSIDE the clickable area
Modifier.clickable { ... }.padding(16.dp)

// Padding added INSIDE — clickable area extends to padded bounds
Modifier.padding(16.dp).clickable { ... }

// Chaining: fill → safe drawing padding → content padding
Modifier.fillMaxSize().safeDrawingPadding().padding(24.dp)

Modifiers are applied outside-in: the leftmost modifier wraps everything to its right. safeDrawingPadding() must come before padding() to ensure the system bars inset is handled before the content padding is applied.

Key Takeaways

  • Compose is declarative: describe what the UI should be, not how to update it
  • @Composable functions re-execute when State reads change — this is recomposition
  • StateFlow + collectAsState() is the idiomatic state bridge in KMP
  • Modifier order determines layout behavior — always test your chains
Check your understanding (4 questions)

1. What triggers recomposition in Compose?

When a State object read by a @Composable function changes value. The Compose runtime tracks which composables read which states and re-executes only those that need updating.

2. Why use StateFlow instead of LiveData in KMP?

LiveData is an Android-only API. StateFlow is pure Kotlin (kotlinx.coroutines) and works in commonMain, making it available on iOS, JVM, and JS targets.

3. What happens if you call .padding(16.dp) before .clickable {} vs after?

Padding first: padding is INSIDE the clickable area — the entire padded region is tappable. Clickable first: only the inner (non-padded) area is tappable; the padding sits outside the clickable region.

4. What does stateIn(viewModelScope, WhileSubscribed(5000), true) do?

Converts a cold Flow to a hot StateFlow. WhileSubscribed(5000) keeps the upstream active for 5 seconds after the last subscriber disappears (prevents restart on config changes). The last argument (true) is the initial value.

04Navigation Compose

Move between screens while keeping state, passing arguments, and managing the back stack.

Learning Objectives

  • Define routes with typed arguments
  • Build a NavHost with composable destinations
  • Use launchSingleTop and popUpTo for correct navigation
  • Handle section-based navigation for bottom bars

Beginner Routes — String-based screen identifiers

object Routes {
    const val HOME = "home"
    const val CALL_LOG = "call_log/{filter}"
    const val STATS = "stats"
    const val SETTINGS = "settings"
    fun callLogRoute(filter: String = "all") = "call_log/$filter"
}

{filter} is a path parameter — it gets substituted at runtime. call_log/today, call_log/week, call_log/all all match the same route template.

Intermediate NavHost wiring

AppNavHost.kt (core pattern)

@Composable
fun AppNavHost(navController: NavHostController, ...) {
    NavHost(navController = navController, startDestination = Routes.HOME) {
        composable(Routes.HOME) {
            HomeScreen(onNavigateToCallLog = {
                navController.navigate(Routes.callLogRoute())
            })
        }
        composable(
            route = Routes.CALL_LOG,
            arguments = listOf(navArgument("filter") { type = NavType.StringType })
        ) { backStackEntry ->
            val filter = backStackEntry.arguments?.getString("filter") ?: "all"
            CallLogScreen(filter = filter)
        }
    }
}

Each composable() block registers a screen. When the navController navigates to that route, Compose creates (or reuses) the composable. The backStackEntry.arguments bundle contains the parsed route parameters.

Advanced Navigation options — preventing reload

The bug

User taps "Call Log" in the bottom bar repeatedly. Each tap navigates call_log/all → popUpTo(home) → navigate(call_log/all), which destroys and recreates the screen.

AppNavHost.kt — the fix

val navBackStackEntry by navController.currentBackStackEntryAsState()
val currentRoute = navBackStackEntry?.destination?.route
val selectedSection = routeSection(currentRoute)

onNavigate = { index ->
    val destination = sectionRoutes.getOrElse(index) { Routes.HOME }
    val isRoot = currentRoute in sectionRoutes ||
        (currentRoute?.startsWith("call_log") == true && destination.startsWith("call_log"))
    if (index == selectedSection && isRoot) return@AdaptiveScaffold // already here, skip
    navController.navigate(destination) {
        popUpTo(Routes.HOME)
        launchSingleTop = true
    }
}
Why two checks

launchSingleTop alone isn't enough — it prevents duplicate instances but popUpTo can still destroy the existing screen. The explicit isRoot check prevents any navigation when already on the section root. The call_log pattern check handles route templates where "call_log/{filter}" ≠ "call_log/all".

Key Takeaways

  • navArgument() with NavType enables type-safe argument passing
  • launchSingleTop = true reuses existing screen instead of creating duplicates
  • popUpTo(ROOT) clears the back stack when switching sections
  • Explicit route comparison prevents screen reload on same-tab taps
Check your understanding (3 questions)

1. What does launchSingleTop = true do?

If a destination matching the route already exists at the top of the back stack, it reuses it instead of creating a new instance. Prevents "screen stacking" when tapping the same nav item.

2. Why use popUpTo(Routes.HOME) when switching bottom nav tabs?

Without it, tapping between tabs would stack screens: [Home, CallLog, Home, BlockList, Home]. The back stack would grow indefinitely. popUpTo(HOME) clears everything and makes each tab feel like a fresh start.

3. How are route arguments like {filter} passed and retrieved?

They're part of the route string: "call_log/today". Navigation Compose parses them into the arguments bundle. The composable retrieves them via backStackEntry.arguments?.getString("filter").

05Adaptive Form Factors

Make the app look great on phones (portrait/landscape), foldables, and tablets with zero platform-specific code.

Learning Objectives

  • Detect WindowSizeClass at runtime
  • Switch between BottomBar and NavigationRail
  • Cap content width and center on wide screens
  • Implement two-pane list-detail on Expanded

Beginner Why adaptive?

Android apps run on everything from 4" phones to 14" tablets. A layout built for 360dp-wide phones looks absurdly stretched on 840dp+ tablets. The WindowSizeClass system gives three tiers so you can build one layout that works everywhere.

Intermediate WindowSizeClass detection

WindowSizeClass.kt

enum class WindowSizeClass { Compact, Medium, Expanded }

@Composable
fun rememberWindowSizeClass(): WindowSizeClass {
    val widthDp = LocalConfiguration.current.screenWidthDp
    return when {
        widthDp < 600 -> WindowSizeClass.Compact   // phone portrait
        widthDp < 840 -> WindowSizeClass.Medium    // phone landscape, small tablet
        else -> WindowSizeClass.Expanded               // tablet, desktop
    }
}

600dp and 840dp are Material Design canonical breakpoints. Respect them, don't invent your own — users recognize the pattern.

Intermediate AdaptiveScaffold — two scaffold modes

AdaptiveScaffold.kt (structure, ~150 lines)

when (windowSizeClass) {
    WindowSizeClass.Compact -> {
        Column {
            Box(modifier = Modifier.weight(1f)) { content() }
            NavigationBar {
                NavigationBarItem(selected = ..., onClick = { onNavigate(i) })
            }
        }
    }
    WindowSizeClass.Medium, WindowSizeClass.Expanded -> {
        Row {
            NavigationRail {
                NavigationRailItem(selected = ..., onClick = { onNavigate(i) })
            }
            Box(modifier = Modifier.weight(1f)) { content() }
        }
    }
}

NavigationBar (bottom) for Compact and NavigationRail (side) for Medium/Expanded. The content area is identical — only the chrome changes.

Advanced AdaptiveContent + two-pane layout

On wide screens, content looks best capped at 600dp and centered. Otherwise, a single-column form stretches across a 14" tablet looking absurd.

// CallLogScreen — one pane on phone, two panes on tablet
if (windowSizeClass == WindowSizeClass.Expanded) {
    Row {
        CallLogListPane(modifier = Modifier.width(340.dp).fillMaxHeight())
        CallLogDetailPane(modifier = Modifier.weight(1f).fillMaxHeight())
    }
} else {
    AdaptiveContent(windowSizeClass = windowSizeClass) {
        // single column, capped at 600dp
        LazyColumn { ... }
    }
}

340dp for the list pane is a Goldilocks width: wide enough for readable text, narrow enough that the detail pane has room on an 840dp screen (840 - 340 = 500dp remaining). On larger screens the detail pane grows via weight(1f).

Edge-to-edge

Android 15+ (targetSdk 36) enforces edge-to-edge — your content draws behind the status bar and navigation bar. WindowInsets.safeDrawing.only(Top + Horizontal) adds padding only where needed so content isn't hidden behind system chrome.

Key Takeaways

  • WindowSizeClass uses 600dp and 840dp Material Design breakpoints
  • NavigationBar (bottom) for Compact, NavigationRail (side) for larger
  • AdaptiveContent caps at 600dp — content looks silly stretched to 1400dp
  • Two-pane on Expanded: 340dp fixed list + weight(1f) detail — test on actual tablet
Check your understanding (3 questions)

1. Why 600dp and 840dp specifically?

These are Google's canonical Material Design breakpoints. 600dp is where a phone landscape or small tablet has room for a nav rail. 840dp is where a full-size tablet can support two-pane layouts.

2. What happens if you use NavigationBar on an Expanded screen?

It would work but look wrong — a bottom bar stretches across the full tablet width while your eyes track a completely different focal point than on a phone. The nav rail keeps navigation near your thumb/pointer in landscape.

3. Why weight(1f) on the detail pane instead of a fixed width?

A fixed width would work on exactly one screen size. weight(1f) means "take all remaining space" — it grows/shrinks with the window, working on 840dp and 1200dp tablets alike.

06SQLDelight — Type-Safe SQL for KMP

Persist rules, call logs, and settings with a database that works identically on Android and iOS.

Learning Objectives

  • Write .sq files with valid SQL and named queries
  • Design schema with migrations (5 versions)
  • Implement the Repository pattern over SQLDelight
  • Handle platform-specific drivers via DriverFactory

Beginner Why SQLDelight over Room?

Room is Android-only (uses annotation processing, ties to Android lifecycle). SQLDelight generates Kotlin from .sq files — works on JVM, Native, JS. For KMP, it's the standard choice.

Intermediate Schema design

AppDatabase.sq (7 tables)

CREATE TABLE BlockedNumber (
    id INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    number TEXT NOT NULL,
    label TEXT,
    created_at INTEGER NOT NULL DEFAULT (CAST(strftime('%s','now') AS INTEGER)),
    UNIQUE(number)
);

-- Named query → generates Kotlin function
selectAllBlockedNumbers:
SELECT * FROM BlockedNumber ORDER BY created_at DESC;

insertBlockedNumber:
INSERT OR IGNORE INTO BlockedNumber(number, label) VALUES (?, ?);

Pattern: each table gets CRUD queries: selectAll, insert, deleteById, toggle. The CallLogEntry table uses CHECK constraints for type safety on the action column.

Advanced Migrations & timestamp portability

Schema history lives in two places you probably expect — AppDatabase.sq holds the current CREATE TABLE statements, and numbered .sqm files describe how to bring an older database up to that shape — plus a third that is easy to forget: a snapshot baseline under src/commonMain/sqldelight/databases/, which only exists if you point the build at it:

// shared/build.gradle.kts
sqldelight {
    databases {
        create("AppDatabase") {
            packageName.set("org.carlospinan.bloqueador.app.db")
            verifyMigrations.set(true)
            schemaOutputDirectory.set(file("src/commonMain/sqldelight/databases"))
        }
    }
}

verifyMigrations takes the oldest snapshot in that directory, replays every later .sqm on top of it, and diffs the result against AppDatabase.sq. With no baseline it has nothing to replay from, so it builds the database from the current .sq — which already contains every column the migrations were going to add — and then dies on the first ADD COLUMN. A missing databases/ directory doesn't disable the check; it makes it fail for a reason that has nothing to do with your migrations.

Squashing while still pre-release: this app renamed its database file (bloquellamadas.db → cortaspam.db) before any public release. A new filename means every device opens a fresh, empty database, so the seven historical .sqm files had zero users left to migrate. They were deleted and the current schema was snapshotted as databases/1.db. Migration history is only worth carrying when somebody is actually still on the old version — otherwise it is untested code that can only cost you.

Critical decision: timestamps use strftime('%s', 'now') instead of unixepoch(). Why? unixepoch() needs SQLite 3.38+ — not available on older Android devices (confirmed crash on API 33 emulator). strftime() has been available since SQLite 3.0.

Advanced Repository pattern — interface + SQL impl

RuleRepository (interface in commonMain)

interface RuleRepository {
    fun blockedNumbers(): Flow<List<BlockedNumberEntry>>
    suspend fun addBlockedNumber(number: String)
    suspend fun removeBlockedNumber(id: Long)
}

SqlRuleRepository (SQLDelight implementation)

class SqlRuleRepository(private val db: AppDatabase) : RuleRepository {
    override fun blockedNumbers() = db.appDatabaseQueries
        .selectAllBlockedNumbers()
        .asFlow().mapToList()
}
Why Flow

SQLDelight's asFlow() emits on every database change. ViewModels collect these flows and the UI auto-updates — no polling, no manual refresh.

Key Takeaways

  • SQLDelight is the KMP-standard database — Room is Android-only
  • Named queries in .sq files generate type-safe Kotlin functions
  • asFlow().mapToList() gives reactive query results — UI auto-updates on writes
  • Use strftime() not unixepoch() for portable timestamp handling
Check your understanding (4 questions)

1. How does a named query like selectAllBlockedNumbers become a Kotlin function?

SQLDelight's Gradle plugin reads the .sq file at compile time and generates a Kotlin function with the same name, typed parameters for WHERE clauses, and typed return values.

2. Why Flow as the return type for list queries?

asFlow() triggers a re-emission whenever the underlying table changes. A ViewModel collecting this Flow automatically gets fresh data after any insert/delete — no manual refresh calls needed.

3. Why not use unixepoch() for timestamps?

unixepoch() requires SQLite 3.38+ which isn't bundled on older Android versions (confirmed crash on API 33). strftime('%s', 'now') works on all SQLite versions since 3.0.

4. What does INSERT OR IGNORE do?

If a row with the same UNIQUE constraint already exists, the insert is silently skipped (no error). Used here for number which has a UNIQUE constraint — prevents duplicate entries.

07Koin — Dependency Injection

Wire up repositories, ViewModels, and platform services without annotation processing or code generation.

Learning Objectives

  • Define modules with single, factory, get()
  • Inject dependencies in Activity, Service, and ViewModel
  • Split modules into shared and platform-specific
  • Compare Koin to Dagger/Hilt

Beginner Why DI matters

Without DI, every class creates its own dependencies:

class HomeViewModel() {
    private val repo = SqlRuleRepository(createDatabase(AndroidDriverFactory(context)))
    // hard to test — can't swap the database for a fake
}

With DI, dependencies are passed in:

class HomeViewModel(
    private val callLogRepository: CallLogRepository, // interface!
) : ViewModel()

Tests pass a fake CallLogRepository. Production passes the SQL one. Koin decides which at startup.

Intermediate Module definitions

SharedModule.kt

val sharedModule = module {
    single { createDatabase(get()) }                // one DB instance for app lifetime
    single<RuleRepository> { SqlRuleRepository(get()) }   // bound to interface
    single<CallLogRepository> { SqlCallLogRepository(get()) }
    factory { HomeViewModel(get(), get()) }            // new VM each time
    factory { CallLogViewModel(get()) }
}

single = one instance for the application lifetime (database, repositories). factory = new instance each time requested (ViewModels — they're scoped by the platform).

Advanced Platform module composition

KoinInit.kt (commonMain)

fun initKoin(appDeclaration: KoinAppDeclaration = {}) {
    startKoin {
        appDeclaration()
        modules(platformModule(), sharedModule)   // platform first!

}

PlatformModule.android.kt (androidMain)

    single<DriverFactory> { AndroidDriverFactory(androidContext()) }

Why platform first

sharedModule needs DriverFactory (from platformModule) to create the database. Platform module registers the concrete implementation; shared module uses it via get().

Koin vs Dagger/Hilt

  • Dagger/Hilt: Compile-time DI with annotation processing. Faster at runtime, catches mistakes at build time. But generates code (longer builds), Java-only patterns, Android-specific Hilt.
  • Koin: Runtime DI with a DSL. No code generation, works in KMP, simpler mental model. Trade-off: misconfigurations crash at runtime instead of compile time.
  • Why Koin here: KMP compatibility. Dagger/Hilt don't work in Kotlin/Native (iOS). Koin's pure-Kotlin approach works everywhere.

Key Takeaways

  • single = app lifetime (DB, repos). factory = new per request (ViewModels)
  • Platform module provides platform-specific types (DriverFactory with Android Context)
  • Shared module consumes them via get() — always binds to interfaces, never concrete types
  • Koin is the KMP-compatible DI choice — Dagger/Hilt don't work on iOS
Check your understanding (3 questions)

1. What's the difference between single and factory in Koin?

single creates one instance and reuses it for the app lifetime (like a singleton). factory creates a new instance every time it's requested — appropriate for ViewModels which have their own scoping.

2. Why must platformModule be registered before sharedModule?

sharedModule uses get() to resolve DriverFactory, which is registered in platformModule. If sharedModule tried to resolve it before platformModule registered it, Koin would throw a definition-not-found error at startup.

3. Why bind to interfaces (single<RuleRepository>) instead of concrete types?

Testing. Tests can provide a fake RuleRepository implementation that returns predictable data. If code depended on SqlRuleRepository directly, you'd need a real SQLite database for every test — slow and fragile.

Beginner What is InCallService?

Android's Telecom framework manages the phone stack. When your app is the default dialer, InCallService is the callback that fires on every incoming and outgoing call. You get a Call object with the phone number, state (ringing/active/disconnected), and methods to answer() or reject().

Intermediate Service manifest + lifecycle

IN_CALL_SERVICE_UI = true: "I will show the call UI myself — don't show the system UI." IN_CALL_SERVICE_RINGING = true: "I handle ringing calls." Without these metadata flags, Android shows its own incoming call screen on top of yours.

Advanced Show UI instantly — the race condition

PassthroughInCallService.kt (critical flow)

override fun onCallAdded(call: Call) {
    val number = call.details?.handle?.schemeSpecificPart.orEmpty()

    // STEP 1: Show UI IMMEDIATELY — don't wait for rule evaluation
    InCallState.attach(call)   // sets ringing state for InCallActivity to read
    startActivity(Intent(this, InCallActivity::class.java)
        .addFlags(Intent.FLAG_ACTIVITY_NEW_TASK))

    // STEP 2: Evaluate rules asynchronously
    serviceScope?.launch {
        val decision = evaluateCall(number)
        if (decision.isBlocked) {
            val autoConfig = autoResponderRepository.config.first()
            if (autoConfig.enabled) {
                call.registerCallback(callCallback)
                call.answer(VideoProfile.STATE_AUDIO_ONLY)  // answer for auto-responder
            } else {
                call.reject(false, null)           // silent reject
            }
        }
        // If allowed: InCallActivity already showing — user decides answer/decline
    }
}
Why show UI first, evaluate later

If you evaluate before showing UI and the evaluation takes 500ms (DB queries, contact lookup), Android shows its own system incoming-call UI because it thinks you're not responding. By showing InCallActivity immediately, the system sees your UI and stays out of the way. If the call turns out to be blocked, call.reject() dismisses it.

Advanced InCallState — the singleton bridge

InCallState.kt

    val state: StateFlow<UiState?> = _state.asStateFlow()

        _state.value = UiState(number = ..., phase = call.state.toPhase())

Uses object (Kotlin singleton) because there's only ever one active call at a time (by design). The StateFlow bridges the Service (where the Call object lives) to the Activity (where the UI runs) — they're in separate processes/contexts.

Key Takeaways

  • IN_CALL_SERVICE_UI and IN_CALL_SERVICE_RINGING metadata tells Android to use your UI
  • Show the InCallActivity FIRST, evaluate rules SECOND — wins the race against system UI
  • InCallState as a singleton bridges the Service (has Call object) to the Activity (shows UI)
  • setShowWhenLocked + requestDismissKeyguard are mandatory for incoming call UX
Check your understanding (4 questions)

1. Why start InCallActivity before rule evaluation?

If you delay while evaluating rules, the system sees your InCallService as unresponsive and shows its own incoming call UI instead. Starting the activity first preempts this race condition.

2. What does IN_CALL_SERVICE_RINGING = true do?

It tells Android that your InCallService handles the ringing state. Without it, the system shows its own ringing notification alongside your UI — the user sees two overlapping call screens.

3. Why use a singleton object for InCallState instead of a regular class?

There's only one active call at a time by design. A singleton provides simplicity — the Service writes to it, the Activity reads from it. Both access the same StateFlow without needing to coordinate instances.

4. What's the difference between call.reject(false, null) and calling finish() on the Activity?

call.reject() tells Telecom to reject the call — the caller gets a busy signal. finish() only closes your Activity; the call would continue ringing in the background. You must use Telecom APIs to actually control the call.

10Rule Precedence Engine

Design a decision system that evaluates every incoming call against 7 rule types in strict order — pure, testable, fast.

Learning Objectives

  • Design a stateless ResolveContext pattern
  • Implement strict precedence ordering
  • Normalize phone numbers for cross-format matching
  • Build glob-style pattern matching

Beginner What does a call blocker decide?

Every incoming call needs one of three outcomes: BLOCK (reject), ALLOW (let through), or AUTO_RESPOND (answer with greeting). The rule engine checks 7 rule types in fixed order and returns the first match. If nothing matches, the "default action" setting takes over.

Intermediate ResolveContext — stateless input

RulePrecedenceResolver.kt

data class ResolveContext(
    val allowlistedNumbers: Set<String>,
    val contactNumbers: Set<String> = emptySet(),
    val blockedNumbers: Set<String>,
    val enabledPatterns: List<PatternRule>,
    val enabledCountryCodes: Set<String>,
    val defaultAction: DefaultAction = DefaultAction.ALLOW,
    // ... plus spam provider, action rules, schedule rules
)
Why a data class, not global state

The resolver is a pure function: evaluate(number, context) → Decision. All inputs are in the data class. No mutable state. This makes it trivially testable — create a context, check the output. No mock servers, no database setup, no race conditions.

Intermediate Precedence order (7 levels)

The order is deliberate and tested at each step:

// 1. MANUAL BLOCK — user explicitly chose to block this exact number
if (normalized in context.blockedNumbers) return RuleDecision.ManualBlock

// 2. ALLOWLIST — contacts + manual allowlist override everything below
if (normalized in mergedAllowlist) return RuleDecision.Allowlist

// 3. PATTERN — glob match (prefix, suffix, contains)
for (pattern in context.enabledPatterns) { ... }

// 4. COUNTRY — country code from libphonenumber-style parsing
val countryCode = parseCountryCode(number)

// 5. SPAM → 6. ACTION → 7. SCHEDULE

// 8. DEFAULT — allow, block, or ask (based on user settings)
Why manual block overrides contacts

If a user explicitly added mom's number to the block list, they have a reason. Respecting that explicit choice is more important than the auto-allow-contacts convenience feature.

Intermediate Making "Ask" mean something

The default action has three settings: Allow, Block, Ask. For a long time, Ask silently behaved exactly like Allow — there was no way to build a real-time "should I let this through?" prompt, because by the time the resolver runs, the call is already ringing. Rather than ship a setting that lies about what it does, the fix makes Ask a genuinely distinct outcome:

RulePrecedenceResolver.kt — the default step

// 8. Default: honor the user's chosen default action.
return when (context.defaultAction) {
    DefaultAction.BLOCK -> RuleDecision.DefaultBlock
    DefaultAction.ASK -> RuleDecision.PendingReview
    DefaultAction.ALLOW -> RuleDecision.DefaultAllow
}

The call still goes through — you can't interrupt a live ring to ask the user anything — but PendingReview is logged with its own rule_type = 'REVIEW' tag instead of blending into ordinary allowed calls. Home shows a "Pending review" count; Call Log gets a matching filter and a distinct amber "Needs review" state.

An honest limitation, not a bug: the call log is an immutable, append-only history (Chapter 06) — there's no "resolved" flag. If the user later blocks a number that generated a REVIEW entry, that old entry stays tagged REVIEW forever. This is a filter over history, not a stateful inbox with read/unread state. Don't oversell it in the UI as more than it is.

Advanced Phone number normalization

The problem: A contact is stored as "(555) 123-4567". The incoming call arrives as "+15551234567". Direct string comparison fails — contacts aren't auto-allowed.

PhoneNumberParser.kt — the fix

fun normalizeForComparison(number: String): String =
    number.filter { it.isDigit() }

Applied everywhere: incoming call number, contact numbers, blocked/allowlist numbers, pattern cores. All comparisons now use digit-only strings. "+1 (555) 123-4567" → "15551234567" matches "+15551234567" → "15551234567".

Where normalization happens:

  • AndroidContactsGateway — normalizes contact numbers when reading from ContactsContract
  • RulePrecedenceResolver.evaluate() — normalizes the incoming number AND all stored numbers from context before comparison
  • matchesPattern() — normalizes both the pattern core and the target number

Advanced Pattern matching

RulePrecedenceResolver.matchesPattern()

internal fun matchesPattern(number: String, pattern: String): Boolean {
    val normalizedCore = normalizeForComparison(core)
    val normalizedNumber = normalizeForComparison(number)
    return when {
        startsWithStar && endsWithStar -> normalizedNumber.contains(normalizedCore)
        startsWithStar -> normalizedNumber.endsWith(normalizedCore)
        endsWithStar -> normalizedNumber.startsWith(normalizedCore)
        else -> normalizedNumber == normalizedCore
    }
}

Simple glob, not full regex: Full regex would be impossible to expand into concrete numbers for iOS's CallDirectory extension. Simple prefix/suffix/contains globs can be pre-computed into static lists that iOS can consume.

Key Takeaways

  • ResolveContext is a pure data class — no mutable state, no side effects, fully testable
  • Manual block overrides contacts — user's explicit choice beats convenience
  • Normalize ALL numbers to digits-only before comparison — cross-format matching
  • Glob patterns (not regex) keep the engine simple and iOS-compatible
  • Don't let a setting silently do something other than what it claims — Ask now produces a distinct, taggable decision instead of quietly aliasing Allow
Check your understanding (6 questions)

1. Why does manual block (step 1) override allowlist (step 2)?

The user explicitly chose to block this number. If the allowlist overrode manual blocks, adding your ex to the block list would be pointless — they'd just get through because they're also in your contacts.

2. What problem does normalizeForComparison() solve?

Phone numbers arrive in different formats: contacts store "(555) 123-4567", incoming calls arrive as "+15551234567". Direct string comparison would say these are different numbers. Normalization strips everything except digits so they match.

3. Why pass all data in a ResolveContext instead of having the resolver access the database directly?

Pure functions are testable. You can create any ResolveContext in a test and verify the output — no database, no mocks. If the resolver accessed the database, tests would need a running SQLite instance.

4. What happens if no rule matches and defaultAction is BLOCK?

The call is blocked via DefaultBlock. But only AFTER all 7 rule levels failed to match. If any rule (including allowlist) matched, it would have short-circuited earlier — the default only activates when nothing else applies.

5. Why not use full regex for pattern matching?

iOS's CallDirectory extension takes a static list of concrete numbers — it can't evaluate regex at runtime. Simple prefix/suffix/contains patterns can be expanded into concrete number lists that iOS can consume. Regex patterns would be Android-only.

6. Why does RuleDecision.PendingReview still let the call through instead of holding it?

There's no way to pause a live ring and wait for the user to decide — the call is already happening. PendingReview is a logging distinction, not a hold: the call proceeds like DefaultAllow, but gets tagged rule_type='REVIEW' so the user can look at it later in Call Log instead of it disappearing into ordinary allowed calls.

15Call Notifications & Permission UX

A default-dialer app has to show its own incoming-call UI — Android doesn't do it for you. Here's why the obvious approach silently fails on a locked phone, the notification design that actually works, and a real case study in a platform limitation no amount of app code can fix.

Learning Objectives

  • Understand background-activity-launch restrictions and why full-screen-intent notifications exist
  • Design notification channels by importance, not by feature
  • Use NotificationCompat.CallStyle — the same API real dialers use
  • Wire notification button actions back into app state via PendingIntent.getBroadcast
  • Detect and deep-link broken permission state instead of asking once and going silent
  • Recognize when a limitation is the platform's, not the app's

Beginner Why startActivity() alone isn't enough

The obvious way to show incoming-call UI is PassthroughInCallService.onCallAdded() calling startActivity(InCallActivity). That works — right up until the screen is off or locked. Since Android 10, apps can't launch activities from the background without an active user-interaction token, and a ringing call arriving while the phone is asleep is exactly the background case. The call silently never shows anything.

The fix isn't more permissions — it's a different mechanism. A notification with setFullScreenIntent() is the one OS-sanctioned way to launch UI over the lock screen from the background. Real dialers, alarm apps, and video-call apps all use this same escape hatch.

Intermediate Three channels, three importances

IncomingCallNotifier.kt — createChannel()

NotificationChannel("incoming_calls", ..., NotificationManager.IMPORTANCE_HIGH).apply {
    setBypassDnd(true)
    lockscreenVisibility = Notification.VISIBILITY_PUBLIC
}
NotificationChannel("ongoing_call", ..., NotificationManager.IMPORTANCE_LOW)
NotificationChannel("call_history", ..., NotificationManager.IMPORTANCE_DEFAULT)

One notification, one job each: the ringing alert needs HIGH + setBypassDnd + full-screen intent, because it's time-critical and has to interrupt. The "return to call" notification shown while active is deliberately LOW — silent, no heads-up, just a status-bar affordance, because the call is already answered and doesn't need to demand attention again. The post-call missed/blocked notification is DEFAULT — visible, but not urgent enough to bypass Do Not Disturb. Picking one importance for all three would either make the ringing alert too quiet or the post-call summary too loud.

Intermediate CallStyle — the API real dialers use

IncomingCallNotifier.kt

NotificationCompat.Builder(context, CHANNEL_ID)
    .setFullScreenIntent(fullScreenPendingIntent, true)
    .setStyle(
        NotificationCompat.CallStyle.forIncomingCall(caller, declinePendingIntent, answerPendingIntent),
    )
    .build()

CallStyle (androidx.core 1.10+) gives you the system's own big Answer/Decline layout — the same chrome the Phone app itself uses — instead of hand-rolling notification actions that look like a generic app alert. forOngoingCall() is the equivalent for the active-call notification, with a single Hang Up action.

Advanced Wiring notification buttons back into the call

Tapping Answer/Decline/Hang Up on a notification doesn't run inside an Activity — there's no UI to hold a click listener. The action has to travel through a PendingIntent to something that can run headless:

CallActionReceiver.kt

class CallActionReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        when (intent.action) {
            ACTION_ANSWER -> InCallState.answer()
            ACTION_DECLINE -> InCallState.decline()
            ACTION_HANG_UP -> InCallState.hangUp()
        }
        IncomingCallNotifier.cancel(context)
    }
}
Why this works without an Activity

InCallState is a plain Kotlin singleton holding the live android.telecom.Call reference — same process, same object, regardless of whether the caller is InCallActivity's buttons or this receiver. The BroadcastReceiver is just a second entry point into the same state.

Intermediate Permission UX: detect and deep-link, don't ask once and go quiet

A single requestPermission() call handles the happy path. It says nothing about what happens when the user taps Deny, or later revokes the permission from system Settings — both cases where the feature just silently stops working with zero signal. The fix tracks real state and surfaces it:

MainActivity.kt — refreshed on launch and on every resume

private fun refreshPermissionStatus() {
    notificationsPermissionGranted = ContextCompat.checkSelfPermission(...) == GRANTED
    fullScreenIntentAllowed = Build.VERSION.SDK_INT < UPSIDE_DOWN_CAKE ||
        getSystemService(NotificationManager::class.java).canUseFullScreenIntent()
    callPhonePermissionGranted = ContextCompat.checkSelfPermission(...) == GRANTED
}

Settings then shows a warning card per broken permission, each with a button to the specific system screen that fixes it — ACTION_APP_NOTIFICATION_SETTINGS, ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT (API 34+, since users can revoke this independently of notifications), or ACTION_APPLICATION_DETAILS_SETTINGS — instead of one generic "open Settings" link.

Case Study: The Auto-Responder Audio Ceiling

The auto-responder plays TTS/MediaPlayer audio with AudioAttributes.USAGE_VOICE_COMMUNICATION, hoping Android mixes it into the live call's uplink so the caller hears it. This is the exact same technique call-recorder and IVR/auto-attendant apps have used for years — and exactly what Google and OEMs have been hardening against at the audio-HAL level on newer Android versions, as an anti-wiretapping measure. Verified live on a Motorola razr running Android 16: this is a real, current-generation device where that hardening plausibly applies.

Why no code fix exists

there is no public Android API that grants a non-privileged third-party app guaranteed injection into a live cellular call's uplink. Forcing AudioManager.mode/routing calls during a Telecom-managed call is explicitly discouraged and risks breaking the user's actual call audio — a far worse failure than a silent auto-responder.

The right fix was honest UI, not more code: sharpen the existing experimental-badge string to explain why ("depends on your phone letting call audio through; many newer Android versions block it") instead of chasing a workaround that either doesn't exist or actively risks the live call. Recognizing a platform ceiling — and saying so in the UI — is sometimes the correct engineering deliverable.

Key Takeaways

  • Background-activity-launch restrictions mean a ringing call needs a full-screen-intent notification, not just startActivity()
  • Match notification importance to urgency per channel — HIGH only for what truly needs to interrupt
  • CallStyle gives you the system's own call UI chrome for free
  • Notification button actions need a BroadcastReceiver + PendingIntent — there's no Activity to hold the click
  • Track real permission state and deep-link to the specific fix — "ask once, go silent forever" is a UX bug
  • Some limitations are the platform's, not yours — recognize the ceiling instead of writing risky code to route around it

1. Why does startActivity() from onCallAdded() fail to show UI when the phone is locked?

2. Why are the three notification channels (incoming, ongoing, history) given different importance levels instead of all HIGH?

Only the ringing alert is time-critical enough to justify HIGH + bypassing Do Not Disturb. The ongoing-call notification is just a status affordance for an already-answered call (LOW, silent), and the post-call summary is informational (DEFAULT). Making them all HIGH would make routine notifications as disruptive as an actual ring.

The alternative — forcing AudioManager routing during a Telecom-managed call — risks breaking the user's real call audio, a worse outcome than a silent auto-responder. The honest fix was clearer in-app messaging about the limitation, not a workaround.

16Extending a Precedence Engine Safely

A feature request that sounds like one sentence — "let repeated callers through" — touches the resolver, the database schema, an async-to-sync UI handoff, and a notification, and every one of those layers has a wrong place to put the change. This module is a single feature traced end-to-end through all four, including a real migration-tooling gap discovered along the way.

Learning Objectives

  • Add a new branch to an existing precedence chain without reordering it
  • Recognize why "block after N attempts" and "allow after N attempts" need opposite scoping rules
  • Understand why SQLite can't ALTER a CHECK constraint, and the rebuild-table migration pattern that works around it
  • Thread a value computed asynchronously (a rule decision) into UI that's already showing
  • Prefer reusing an existing function's shape over inventing a new one
  • Know the difference between "the build is green" and "every dev-time safety net actually ran"

Beginner The problem with a binary default action

defaultAction = Block is one bit: match no rule, get blocked. That's fine for actual spam, but it can't distinguish a robocaller from an old friend calling from a number you never saved. The feature: if an otherwise-unrecognized number retries enough times, let the next attempt through — but only that number, only after real persistence, and never for a number the app has already positively identified as spam.

Intermediate One new branch, at the end of the chain, on purpose

RulePrecedenceResolver.kt — step 8, the only place this can live

// 8. Default: honor the user's chosen default action. BLOCK gets one more check first
return when (context.defaultAction) {
    DefaultAction.BLOCK ->
        if (context.repeatedAttemptsBypassCount > 0 &&
            context.recentAttemptsForNumber >= context.repeatedAttemptsBypassCount
        ) RuleDecision.AllowedAfterRepeatedAttempts(context.recentAttemptsForNumber)
        else RuleDecision.DefaultBlock
    DefaultAction.ASK -> RuleDecision.PendingReview
    DefaultAction.ALLOW -> RuleDecision.DefaultAllow
}
Why step 8 and nowhere earlier

manual block, pattern, country, spam, action-rule, and schedule checks (steps 1-7) all return before this code ever runs. That's not incidental — it's the entire point. Retrying is a robocall hallmark, so if the bypass were checked before the spam-pattern step, a number the app had already flagged as spam could talk its way back in just by calling more. Placing the new logic at the literal end of the existing chain, instead of threading a bypass check into every earlier branch, means the precedence order itself — not a separate flag on each rule type — is what protects real spam blocking. This mirrors ActionRule's "block after N attempts" (Chapter 10) almost exactly, just inverted: same attempt-tracking table, opposite conclusion, and deliberately a different point in the chain.

Intermediate SQLite can't ALTER a CHECK constraint

CallLogEntry.rule_type is constrained to a fixed list of tags. Adding REPEATED_ALLOWED to that list sounds like ALTER TABLE ... ADD CONSTRAINT — except SQLite has no such statement. The only way to change a CHECK is to rebuild the table:

The rebuild pattern — the shape every rule_type migration used

CREATE TABLE CallLogEntry_new (
    ...
    rule_type TEXT CHECK (rule_type IN ('MANUAL', ..., 'REPEATED_ALLOWED', NULL))
);
INSERT INTO CallLogEntry_new SELECT ... FROM CallLogEntry;
DROP TABLE CallLogEntry;
ALTER TABLE CallLogEntry_new RENAME TO CallLogEntry;

Create a shadow table with the new constraint, copy every row across, drop the old table, rename the shadow into place. SQLDelight's verifyMigrations build check replays every .sqm file in order on top of the snapshot baseline in databases/ and diffs the result against AppDatabase.sq's CREATE TABLE — if they don't match bit-for-bit, the build fails before a mismatched migration ever ships. Regenerate the snapshot with ./gradlew :shared:generateCommonMainAppDatabaseSchema whenever you cut a new baseline.

Case Study: A Broken Safety Net Nobody Noticed

Running verifyMigrations directly (not through the usual ./gradlew test/check chain) surfaced a pre-existing failure — duplicate column name: pattern_id. An early pass blamed a single missing snapshot file and concluded the schema itself was fine. That conclusion was wrong, and it is worth keeping the mistake visible.

What was actually wrong, in three layers:

  1. schemaOutputDirectory was never configured, so nothing regenerated the snapshots. The committed ones (1.db through 5.db) sat loose in the sqldelight source root and stopped at version 5 while migrations went on to 7.
  2. Replaying 5.sqm onto a snapshot that already carried the column produced the duplicate column name error — a symptom of the stale baseline, not of the migration.
  3. Once a correct baseline was rebuilt, the check failed again on something real: 5.sqm ran ALTER TABLE ActionRule ADD COLUMN pattern_id INTEGER, while AppDatabase.sq declares pattern_id INTEGER REFERENCES PatternRule(id). SQLite cannot add a foreign key through ALTER TABLE, so an upgraded database and a freshly installed one genuinely had different schemas. The safety net was broken and it was also right.

On top of all three, ci.yml ran ktlintCheck, assembleDebug, testDebugUnitTest and the iOS test task — none of which depend on verifySqlDelightMigration. The check had never run in CI even once.

The lesson: a dev-time safety net can quietly stop running, and a green CI history proves nothing about a check that was never wired into the graph it looks like it belongs to. The second lesson is sharper — when a check fails and you can't immediately explain it, "the tool is misconfigured" and "the code is broken" are not mutually exclusive. Fix the configuration first, then re-run, because a misconfigured check hides real findings behind fake ones. Here the fix was to configure schemaOutputDirectory, squash the seven now-userless migrations into a single databases/1.db baseline, and add the task to CI so it can never silently stop running again.

Advanced Threading an async decision into UI that's already on screen

The rule decision resolves inside a coroutine, seconds after the ringing screen is already showing — there's no prop to just pass it in. InCallState already exists as exactly this kind of bridge (Chapter 09), so the fix is one more field and one more setter on a pattern already proven, not new plumbing:

data class UiState(val number: String, val phase: CallUiPhase, val repeatedCallAttempts: Int? = null)

    _state.value = _state.value?.copy(repeatedCallAttempts = attempts)
}

The async result and the already-rendered UI meet through the same reactive state object, no callback or event bus required.

Advanced The best new code is the code you don't write

PassthroughInCallService.kt

if (settingsRepository.notificationsEnabled.value) {
    IncomingCallNotifier.notifyCallResult(
        this, number, R.string.notification_repeated_caller_title, decision.blockReason,
    )
}

The repeated-caller notification needed exactly that shape, so it reuses the function verbatim with a new title string instead of a new method. Before writing a new notification builder, the question worth asking is whether an existing one already has the right shape — here it did.

Case Study: When combine() Runs Out of Overloads

SettingsViewModel already combined 5 flows of different types into one UiState — kotlinx.coroutines.flow.combine()'s typed overloads stop at 5. Adding a 6th setting doesn't mean switching to the untyped vararg Array<T> form (which needs every flow to share a type): chaining a plain two-argument combine() on top of the existing one composes cleanly instead —

Composing two small typed operators beat forcing one large untyped one.

Key Takeaways

  • A new precedence branch belongs at the specific step that matches its risk profile — not wherever is convenient to code
  • "Block after N" and "allow after N" reuse the same attempt-tracking data but must live at different, deliberately chosen points in precedence order
  • SQLite has no ALTER ... ADD CONSTRAINT — changing a CHECK means rebuild-copy-drop-rename, and a migration-verification task should replay every step and diff the result
  • A build task that's silently SKIPPED is not the same as a build task that passed — confirm what's actually wired into the graph
  • Bridge state objects (InCallState-style) let already-rendered UI pick up an async result with zero new plumbing
  • Before adding a new function, check whether an existing one already has the shape you need
  • When a typed API runs out of overloads, compose smaller typed calls instead of dropping to an untyped one
Check your understanding (4 questions)

1. Why does the repeated-caller bypass check live at step 8 (the default-action step) instead of being threaded into the pattern/spam/action-rule checks earlier in the chain?

Retrying is a common robocall behavior. If the bypass were checked earlier, a number already matched by a spam/pattern/action rule could use enough retries to talk its way past a block that was working correctly. Placing it only at the very end, after every real block rule has already had a chance to fire and return, means precedence order itself enforces that this bypass can only ever apply to numbers nothing else recognized as a threat.

17State Management — MVVM + MVI Done Right

Chapter 03 taught ViewModel + StateFlow<UiState> as the state bridge and called it done. An architecture review of all 8 ViewModels in this app found that pattern held up as MVVM — but a second, separate pattern was missing entirely: MVI's single inbound dispatch point. Worse, 4 of the 8 ViewModels had quietly drifted from the "one UiState" rule Chapter 03 itself taught, in ways nothing had caught because nothing was checking for it. This module is that review, and the fix, traced through the two hardest cases it turned up.

Learning Objectives

  • Name the difference between MVVM and MVI precisely enough to tell whether a codebase actually has both
  • Convert N public setter methods into one sealed Intent + one onIntent() dispatcher without touching leaf Composables
  • Recognize when a ViewModel genuinely needs an Intent type — and when adding one is pure ceremony
  • Handle a callback-shaped side effect (a platform share-sheet handoff) in an Intent-based world without breaking "intents are plain data"
  • Know when NOT to force a pattern: system callbacks are not user intents, even when they arrive on the same class

Beginner MVVM gets you unidirectional state. MVI adds unidirectional intent.

MVVM's contract, as already built in this app: a ViewModel exposes one immutable StateFlow<UiState>, mutates it privately, and Compose renders from it via collectAsState(). That part was already correct everywhere. What MVVM's contract does not specify is how the UI talks back to the ViewModel — and this app answered that with N public methods per screen (SettingsViewModel had 6: setBlockingEnabled, setAutoAllowContacts, setDefaultAction...). MVI adds exactly one more rule on top: every inbound user action is a value of one sealed type, dispatched through one function. State stays single and unidirectional either way — MVI is about making the input side just as single and typed as the output side already was.

Intermediate The pattern: one sealed Intent, one onIntent(), existing methods go private

HomeViewModel.kt — before and after are the same logic, different entry shape

sealed interface HomeIntent {
    data object Refresh : HomeIntent
    data class ToggleBlocking(val enabled: Boolean) : HomeIntent
}

fun onIntent(intent: HomeIntent) {
    when (intent) {
        HomeIntent.Refresh -> refresh()
        is HomeIntent.ToggleBlocking -> toggleBlocking(intent.enabled)
    }
}
// refresh() and toggleBlocking() keep their exact original bodies -- just private now

Where the wiring changes, and where it deliberately doesn't: AppNavHost.kt's route wiring goes from a method reference (homeViewModel::toggleBlocking) to a lambda that builds and dispatches an intent ({ homeViewModel.onIntent(HomeIntent.ToggleBlocking(it)) }). Advanced When an Intent can't just carry a callback

BackupViewModel.exportJson(onResult: (String) -> Unit) took a UI-supplied callback so the exported JSON could reach a platform share-sheet Compose can't invoke directly. A sealed Intent case holding a function type would technically compile, but it breaks the actual point of MVI — intents are supposed to be inert data you can log, replay, or test by equality; a lambda inside one is neither.

BackupViewModel.kt — the result becomes a third effect case instead of a parameter

sealed interface BackupEffect {
    data class Exported(val json: String) : BackupEffect
    data class Success(val message: String) : BackupEffect
    data class Failure(val message: String) : BackupEffect
}
sealed interface BackupIntent { data object Export : BackupIntent /* ... */ }

onIntent(BackupIntent.Export) now sends Exported(json) down the same effect channel Success/Failure already used, and BackupScreen gained one more branch in its existing effect-collecting LaunchedEffect to call a new onExportReady callback. The general rule this generalizes to: when a mutation's "result" needs to reach something outside the state model — a share sheet, a file picker, a toast — that result is a one-time effect, not an intent parameter and not a UiState field.

Case Study: The ViewModel That Deliberately Didn't Get an Intent Type

InCallState — the Telecom bridge singleton from Chapter 09 and 16 — was reviewed for this same treatment and left alone on purpose. Its methods split into two categories that look identical in code but aren't: answer()/decline()/hangUp() are real user intents, dispatched from a tap in CallScreen. attach()/detach() are Android Telecom system lifecycle callbacks, invoked by PassthroughInCallService when the OS hands the app a call — no user asked for those to happen. Folding both into one sealed interface CallIntent would misrepresent a system event as something the user chose, which is a correctness problem in an MVI codebase, not just a style one: code reading "the user's intent was Attach" would be lying. InCallState already does the MVVM half correctly — one encapsulated StateFlow<UiState?> — and that's as far as this pattern should go here.

The same instinct killed a second, smaller addition: StatsViewModel has exactly one method, refresh(), and zero external call sites dispatch it (it only ever runs from its own init). A sealed interface StatsIntent { data object Refresh : StatsIntent } would compile and look consistent with every other VM — and add nothing. It stayed a plain private-called method. MVI earns its ceremony when there's more than one thing to dispatch and more than one place dispatching it; a single VM-internal call isn't that.

Key Takeaways

  • MVVM (single StateFlow<UiState> out) and MVI (single sealed Intent + onIntent() in) are two separate rules — a codebase can have one without the other, and this one did
  • Leaf Composables shouldn't know an Intent type exists; only the ViewModel and its navigation-layer wiring should
  • Derived properties (counts from list.size) beat separately-collected StateFlows for anything computable from state already held
  • An Intent that needs to carry a callback is a sign the "result" belongs in a one-time Effect instead
  • System lifecycle callbacks are not user intents, even on a class that also has real ones — don't fold them together for pattern consistency
  • A one-case sealed class with no external dispatcher is ceremony, not MVI — skip it

18Test Doubles at Scale — One Fake per Interface

Chapter 12 chose hand-written fakes over MockK, for a good reason: MockK doesn't run on Kotlin/Native, and this project's tests have to pass on both Android and the iOS simulator. That decision was right, and it has a bill that arrives later. By the time this app had 176 tests, 470 of its 3061 test source lines — 15% — were Fake* class bodies, and three of those fakes existed in two, three, and four near-identical copies. This module is the cleanup: what to consolidate, what to deliberately leave duplicated, and the two surprises that fell out of doing it.

Learning Objectives

  • Decide which test doubles are worth consolidating and which are cheaper left duplicated
  • Place a shared fake so both commonTest and androidUnitTest can use it, and know why internal works there
  • Explain the Kotlin "private top-level class" redeclaration trap that duplicate fakes hit in KMP test source sets
  • Design one fake that satisfies call sites which previously needed different fakes, without silently changing what a test asserts
  • Recognize a test that only exercises its own fake and asserts nothing about production code

Beginner Duplication in tests is real duplication — with one exception

The usual defense of copy-pasted test helpers is that tests should be readable in isolation. That holds for small doubles. It stops holding when the interface is big: RuleRepository has 64 members, so each copy of FakeRuleRepository was ~115 lines of override fun ... {}, and adding one method to the interface meant editing both copies to keep the build green. Intermediate Where the shared fake goes, and why internal reaches androidUnitTest

The three shared fakes now live once each in shared/src/commonTest/kotlin/.../app/testing/, declared internal. That single placement covers every consumer: androidUnitTest dependsOn commonTest in the default KMP hierarchy, and internal is module-scoped, so a Robolectric Compose test in androidUnitTest imports the same class a pure-Kotlin ViewModel test in commonTest does. Adding a sixth setting to SettingsRepository is now one new parameter and one new setter — the project's own corta-spam-add-setting runbook had listed five test files to edit for that, and now lists one.

Intermediate The redeclaration trap that duplicate fakes were quietly working around

Two of the duplicated fakes had a naming tell: the androidUnitTest copy was called FakeScreenTestSettingsRepository, not FakeSettingsRepository. That prefix wasn't a style choice. commonTest and androidUnitTest compile into one JVM compilation, and Kotlin's private on a top-level class restricts visibility but does not change the class's binary name — so two files in the same package each declaring private class FakeSettingsRepository fail with a JVM Redeclaration error. The prefix was a workaround for a problem that only existed because the fake was duplicated. One shared class in a testing package removes the workaround and the trap together.

Advanced Merging two fakes that disagreed about how state is read

The two FakeRuleRepository copies weren't just duplicates — they modeled the repository differently. The BlockList copy was flow-backed (MutableStateFlow fields, because the ViewModel collects blockedNumbers()). The rule-engine copy was snapshot-backed (var blockedEntries, because EvaluateIncomingCallUseCase calls the suspend accessor blockedNumberEntries()). A merged fake has to serve both without making a test seed the same data twice.

FakeRuleRepository.kt — one source of truth, two read paths

// reactive path -- what BlockListViewModel collects

One assignment (blockedNumbersFlow.value = ...) now drives both. Case Study: The Test That Only Tested Its Own Fake

SettingsRepositoryTest.kt — 78 lines, five green tests, sitting in the settings package next to the class it appeared to cover. It never touched SqlSettingsRepository. Every one of its assertions ran against the fake declared at the top of the same file:

That is a test of kotlinx.coroutines, wearing the name of a repository test. It was invisible for months precisely because it was green and its filename read like coverage. Consolidation surfaced it: once the fake moved out of the file, what remained had nothing left to test. The honest part of the outcome: the real SqlSettingsRepository still has no test. The gap didn't appear in this refactor; it was always there, hidden behind a filename. Renaming the file made the gap visible instead of pretending it was covered.

A second trap, avoided by checking first: the four FakeSettingsRepository copies differed in exactly one way — some had setters that mutated the backing flow, others had setters that did nothing. Unifying on write-through would silently break any test asserting that a setter had no effect. Every call site was checked for that assertion before the merge, and none existed. If one had, the merged fake would have needed a constructor flag, not a judgment call — when consolidating doubles, the differences between copies are the specification, so read them before deleting them.

Key Takeaways

  • Hand-written fakes are the right call in KMP (MockK has no Kotlin/Native support) — the cost is duplication that must be managed deliberately
  • Consolidate a double when the interface is large or the copies are many; leave 5-line doubles local where an import would cost more reading than it saves
  • internal in commonTest is visible from androidUnitTest via the default dependsOn hierarchy — no Gradle change needed
  • Top-level private restricts visibility, not the JVM binary name — duplicate private fakes in one package collide, and name prefixes to dodge that are a duplication smell
  • One fake can serve a reactive and a snapshot read path by deriving the snapshot from the flow — seed once, both paths see it
  • Differences between copies of a fake encode real assumptions; audit them before unifying, or a test's meaning changes silently
  • A test file named after a production class can assert nothing about it — check what the assertions actually reach

19Testing Persistence Against a Real Database

Chapter 18 consolidated the fakes and, in passing, exposed something the fakes had been hiding: not one Sql* repository in this app had a dedicated test. Five classes held every byte that survives an app restart — settings, call log, auto-responder, spam flag, and the key-value store beneath them — and all five were untested. This module is that gap being closed, and the user-visible bug the very first pass of tests uncovered.

Learning Objectives

  • Decide when a fake is the wrong test double and only a real database engine will do
  • Place SQLite-backed tests correctly in a KMP module, and know why they can't be shared with iOS
  • Test a repository that hydrates once at construction — where "does this survive a restart?" needs a second instance
  • Use a test to prove every branch of a sealed decision type satisfies a database CHECK constraint
  • Handle the moment a new test disagrees with shipped behaviour: pin it, judge it, then fix it

Beginner When a fake stops being enough

A fake is a stand-in for a collaborator you're not testing. That's the right tool when you're testing a ViewModel: HomeViewModel shouldn't need SQLite to prove it maps stats into a UiState. But the moment the class is the persistence — SqlSettingsRepository, SqlCallLogRepository — a fake has nothing left to stand in for, and the interesting behaviour lives entirely in things a fake never reproduces: SQL CHECK constraints, strftime date arithmetic, INSERT OR REPLACE semantics, and what a value actually looks like when read back off disk. Those tests need a real engine.

shared/src/androidUnitTest/kotlin/.../app/testing/TestDatabase.kt

internal fun createTestDatabase(): AppDatabase {
    val driver = JdbcSqliteDriver(JdbcSqliteDriver.IN_MEMORY)
    AppDatabase.Schema.create(driver)
    return AppDatabase(driver)
}

Why androidUnitTest and not commonTest: JdbcSqliteDriver is JVM-only. There is no Kotlin/Native equivalent that runs in the shared test source set, so these tests are deliberately excluded from the iOS simulator run — the opposite of Chapter 12's default, and a real limit of the approach. The rule of thumb: logic tests go in commonTest and run everywhere; engine tests go in androidUnitTest and run on the JVM only.

Intermediate Testing a repository that hydrates once

SqlSettingsRepository reads the database exactly once, in init, into MutableStateFlows. Its flows are not backed by live queries. That single design fact dictates how it must be tested: calling a setter and reading the flow back only proves the in-memory field moved. Proving the value reached disk takes a second repository over the same database — which is exactly what an app restart is.

SqlSettingsRepositoryTest.kt — a second instance is the restart

val db = createTestDatabase()
val first = SqlSettingsRepository(db)
first.setDefaultAction(DefaultAction.ASK)

// A fresh instance re-runs init, re-reading from the same database
assertEquals(DefaultAction.ASK, SqlSettingsRepository(db).defaultAction.first())

The same structure makes a subtler property testable: two live instances over one database disagree, because neither observes the other's writes. That isn't a bug — it's safe only because SharedModule binds the repository as single<SettingsRepository>. A test asserting the disagreement documents the constraint, so a future change to factory { } fails loudly instead of producing a screen showing stale settings.

Advanced Proving a sealed type satisfies a CHECK constraint

Chapter 16 added REPEATED_ALLOWED to the CallLogEntry.rule_type CHECK constraint via a rebuild-table migration. That constraint and the RuleDecision sealed hierarchy are two lists that must stay in lockstep — and nothing enforced it. A new decision variant whose ruleTypeTag isn't in the constraint compiles cleanly and throws at runtime, on a real user's phone, at the moment a call is being logged.

val decisions = listOf(
    RuleDecision.Allowlist(ruleId = 1, label = "Mom") to ("ALLOWED" to "CONTACTS"),
    RuleDecision.DefaultBlock to ("BLOCKED" to null),
    RuleDecision.PendingReview to ("ALLOWED" to "REVIEW"),

The insert itself is the assertion — a tag outside the constraint fails the statement. The explicit assertEquals on action and rule type then pins the mapping, so a decision silently switching from BLOCKED to ALLOWED is caught too.

Case Study: The Chart That Never Said "Today"

Writing an assertion for blockedByDay() meant reading it closely enough to predict its output — and the prediction didn't match the label. The old implementation walked forward from now - daysBack in 24-hour steps:

val cutoff = now - daysBack * dayMillis
(0 until daysBack).map { dayOffset ->
    val dayStart = cutoff + dayOffset * dayMillis   // newest bucket = [now-1d, now)
    val epochDay = dayStart / dayMillis             // ...whose START is one day ago
    DayStat(dateLabel = dayLabel(epochDay), /* ... */)   // ...so the label is "Yesterday"
}.reversed()

The newest bucket held every blocked call from the last 24 hours — including one placed five seconds ago — but its label came from the bucket's start, one epoch-day back. No bucket was ever labelled "Today". StatsViewModel calls blockedByDay(7) and StatsScreen renders dateLabel verbatim, so every install shipped a Stats screen filing today's blocks under "Yesterday".

The fix anchors buckets to UTC midnight — the same boundary countBlockedCallsToday was already using:

val todayStart = (currentTimeMillis() / dayMillis) * dayMillis
(0 until daysBack).map { dayOffset ->
    val dayStart = todayStart - dayOffset * dayMillis
    // dayLabel() now yields "Today" for dayOffset 0, and no .reversed() is needed
}

That alignment buys an invariant the code could not previously satisfy: the chart's first bar and the "blocked today" stat now derive from one day boundary, so they cannot disagree. The new test asserts precisely that — assertEquals(repo.blockedStats().today, repo.blockedByDay(7).first().count). Note the sequencing: the test suite landed first, pinning the wrong behaviour with a comment naming it as suspect, and the fix landed in the next commit updating those assertions. Enshrining a bug in a green test without saying so is how bugs become "intended behaviour"; documenting it and fixing it next is how it stays a bug.

A second finding, deliberately not fixed: clearing the auto-responder script writes "", but KeyValueSettingsStore.readString treats a stored blank as "unset" and returns the default — so a restart resurrects the default greeting. In memory the field is empty; after restart it isn't. That one stayed documented rather than fixed, because readString is shared by three repositories and changing its fallback semantics is a wider decision than a one-line patch.

Key Takeaways

  • Fakes are for collaborators you aren't testing; a persistence class has no collaborator left to fake, so it needs a real engine
  • JdbcSqliteDriver is JVM-only — database tests live in androidUnitTest and knowingly skip the iOS run
  • A repository that hydrates in init can only be proven durable by constructing a second instance over the same database
  • Two live instances disagreeing is a DI constraint worth asserting, not just a quirk to remember
  • Round-trip every branch of a sealed type through the database when a CHECK constraint mirrors it — the insert is the assertion
  • When a new test disagrees with shipped behaviour, pin it with a comment naming the suspicion, then fix it in the next commit — never silently
  • Not every finding has to be fixed in the same pass; a shared primitive's semantics deserve their own decision

Intermediate Normalising away the information you need

The resolver reduced every incoming number to bare digits before consulting any rule:

shared/src/commonMain/kotlin/.../rules/RulePrecedenceResolver.kt
// before
val normalized = PhoneNumberParser.normalizeForComparison(number)  // digits only

That is right for comparing against a number the user typed, where +34 600 123 456 and 0034600123456 should match. It is wrong for anything that needs to know whether the number was international at all.

Without the +, a national number is indistinguishable from an international one. 2125551234 is a Manhattan landline; its first three digits are also Morocco's country code. 912345678 is a Madrid landline; its first two are India's. Blocking either country quietly blocked an unrelated city.

shared/src/commonMain/kotlin/.../rules/PhoneNumberParser.kt
fun toE164OrNull(number: String): String? {
    val trimmed = number.trim()
    val digits = when {
        trimmed.startsWith("+")  -> normalizeForComparison(trimmed)
        trimmed.startsWith("00") -> normalizeForComparison(trimmed).drop(2)
        else -> return null      // national format carries no country at all
    }
    if (digits.isEmpty() || digits.length > MAX_E164_DIGITS) return null
    return "+$digits"
}
Why

Returning null rather than guessing is the whole fix. "I do not know which country this is" is a true and useful answer; "probably Morocco" is neither.

    if (inserted != null) queries.togglePatternRule(0, inserted.id)
}

Read the query it calls: SELECT * FROM PatternRule ORDER BY created_at DESC, id DESC. Newest first. So lastOrNull() is the oldest row, not the newest. Every restore containing a disabled rule switched off an unrelated rule the user still wanted, silently.

The fix is to stop having a second step at all — insert the row with its real state in one statement:

shared/src/commonMain/sqldelight/.../AppDatabase.sq
insertPatternRuleFull:
INSERT INTO PatternRule(pattern, label, enabled, created_at) VALUES (?, ?, ?, ?);
Contrast

The obvious fix is firstOrNull(). It would have worked here and broken on CountryRule, which orders by country_name ASC — neither end of that list is the row you just inserted. "Find what I wrote" is the wrong question; not needing to ask it is the fix.

Three more problems fell out of the same rewrite. Counts came from a loop counter rather than affected rows, so re-importing your own backup — legitimately a no-op against INSERT OR IGNORE on a UNIQUE column — claimed it had added everything twice. created_at was parsed out of the file and then discarded, so restored rules came back in an order they had never been in. And an action rule's patternId pointed at an id from the exporting device, which on the importing device belongs to somebody else's pattern.

Advanced A manifest entry is a promise

androidApp/src/main/AndroidManifest.xml
<meta-data
    android:name="android.telecom.IN_CALL_SERVICE_RINGING"
    android:value="true" />

That tells Telecom the app plays the ringtone itself, so Telecom stops playing one. Nothing in the source ever did — no Ringtone, no MediaPlayer on the ring stream, no Vibrator. As the user's default dialer the app took every incoming call in silence.

Why

The declaration was kept rather than removed, because it is what makes a blocked call silent. Handing ringing back to the system would mean every spam call rings before it is rejected. Owning the ringer is the feature; not implementing it was the bug.

Order matters on this path. The ringer starts as soon as the call is ringing and stops when a block decision lands, not the other way round:

// Ring first, decide second. Evaluation touches the database and the contacts
// provider, and a caller must never be dropped into silence because that was slow.
ringer.start()
state.evaluation = serviceScope.launch { /* ...decide, then ringer.stop() */ }

Advanced When lint has never run, "no lint errors" means nothing

Adding Android Lint to CI failed immediately, and not because of the code:

Module was compiled with an incompatible version of Kotlin.

AGP 8.7.3 bundles a UAST frontend that reads Kotlin 2.0 metadata. The project compiles with 2.2.20. Every lint task had been failing this way since the day the project moved to Kotlin 2.2 — which is exactly why lint was not in CI, and why nobody had noticed.

Gotcha

The tempting fix is lint { abortOnError = false } or dropping the task. Both convert a toolchain mismatch into a permanent blind spot. The fix is to raise AGP — which, as a bonus, retired two workarounds the old version had forced.

On its first successful run lint found three notify() calls with no permission guard it could see, a dead pre-API-26 branch, StateFlow.value read inside composition, plural forms that are wrong in Hindi and Portuguese, and an adaptive-icon monochrome layer that had been drawn, committed, and never referenced.

Verified

339 JVM tests and 227 of the same tests on the iOS simulator, plus ktlintCheck, both lintDebug tasks, verifySqlDelightMigration, compileKotlinIosSimulatorArm64 and assembleRelease. Then installed on a Motorola razr 50 ultra, where the database came back reporting user_version: 3 for a schema with two states.

Advanced The bug the device found and the tests could not

A SQLDelight migration file N.sqm takes the schema from version N to N+1. The squashed baseline in databases/1.db is version 1, so the first migration on top of it is 1.sqm. It was named 2.sqm.

That generated Schema.version = 3 with nothing implementing the 1 → 2 step. It worked — the generated guard is oldVersion <= 2 && newVersion > 2, which a device at version 1 satisfies — so the index was created, the rows survived, and verifySqlDelightMigration stayed green.

Verified

Pulling the database off the phone and running PRAGMA user_version is what exposed it. Every automated check in the project passed with a schema whose version number did not describe how many migrations exist.

Scope

Left deliberately unfixed: InCallState still tracks a single call. Multi-call UI is a feature, not a defect. What mattered was that a second call could no longer cancel the first call's in-flight blocking decision — which it could, because onCallAdded cancelled the entire service coroutine scope on every new call.

Intermediate Text that was English in a four-locale app

RuleDecision built its reason as an English sentence and wrote it straight into the database:

is CountryBlock -> "Country: $countryName ($countryCode)"

So it was not merely untranslated — it was persisted untranslated. Translating it later would still leave every historical call-log row frozen in the language it was created in. The fix stores structured data and chooses words at display time, with a codec that degrades an unrecognised row to its raw text rather than showing a blank cell.

Gotcha

The recording-consent check required the script to contain the English phrase "This call may be recorded". A user writing their greeting in Spanish could never enable recording — the only way through was pasting an English sentence into a greeting the caller would hear in Spanish. A compliance gate implemented as a substring match is a gate against your own users.

A new test walks all three resource trees in both directions. It immediately found eleven real gaps, including the in-app privacy policy — which additionally described behaviour the app does not have, claiming the spam check uploads numbers to a public database when the list ships inside the APK and makes no network calls at all.

Why

Android Lint has a MissingTranslation check. It is disabled here, because this project has two independent string systems and lint can only see one of them — a green lint run would have been actively misleading.

Done when

  • Every rule that can fire, does fire, proven through evaluate() rather than against the component
  • A backup can be restored twice without changing anything the second time
  • An incoming call rings, and a blocked one stops ringing without the user hearing it
  • Android Lint runs in CI and the build fails on its errors
  • PRAGMA user_version on a real device equals the number of migrations plus one

Check yourself

1. A component test for the spam provider passed while the feature was completely dead in production. What kind of test would have caught it?

A test through the real entry point — RulePrecedenceResolver.evaluate() with the provider wired in — rather than calling provider.lookup() directly. The bug was not in the provider or in the resolver; it was in the shape of the value passed between them, which only an integration-level test observes.

2. Why does toE164OrNull return null for a national-format number instead of assuming a default country?

Because the information genuinely is not there. Assuming the device's own country would be right most of the time and silently wrong while roaming or for a ported number — and this value decides whether a call is rejected. "Unknown" is a correct answer that the caller can handle; a confident guess is not.

3. The importer used lastOrNull() on a created_at DESC, id DESC query to find the row it had just inserted. Why is firstOrNull() not the fix?

It works for that one query and breaks on CountryRule, which orders by country_name ASC — the row just inserted is at neither end. The real fix is to insert the row in its final state so there is nothing to find afterwards.

4. Why keep IN_CALL_SERVICE_RINGING and write a ringer, rather than removing the declaration and letting the system ring?

Because owning the ringer is what allows a blocked call to be silent. If the system rings, every spam call audibly rings before it is rejected — which is most of what the app exists to prevent.

5. Android Lint failed with a Kotlin metadata version error. Why is disabling lint the wrong response?

The message is not a finding about the code, it is AGP's bundled analyser being older than the compiler. Disabling it converts a fixable toolchain mismatch into a permanent blind spot — and on the first run after the AGP bump, lint found five real defects that had been invisible for the project's whole life.

6. Every automated check passed on a migration numbered 2.sqm when it should have been 1.sqm. Why?

Because the migration still ran: the generated guard is oldVersion <= 2 && newVersion > 2, and a device at version 1 satisfies it. verifySqlDelightMigration checks that replaying the files reaches the current schema, which it did. What was wrong was the version number — visible only by reading PRAGMA user_version off a real device.

21When the Platform Says No

Two things collided in one day: a Google Play policy rejection that was wrong, and a feature that four different user-facing surfaces claimed to have and no line of code implemented. Both are about the same discipline — checking whether the thing you assert is actually true.

Learning Objectives

  • Verify a platform policy against your own manifest before complying with a rejection
  • Recognise a claim in a privacy policy as a promise the code must keep
  • Understand which audio sources Android reserves for privileged apps, and design honestly around that
  • Attach a file to a database row without leaking it when the row is deleted
  • Return an inserted row id safely when concurrent writes are possible

Beginner A rejection that was wrong

Play rejected version code 1: "Full-Screen Intent Permission policy: Permission use is not directly related to your app's core purpose." The prescribed fix was to remove USE_FULL_SCREEN_INTENT from every version code.

Reading the actual policy changed the answer. It auto-grants the permission when core functionality is setting an alarm or receiving phone or video calls. The manifest already settles which of those applies:

androidApp/src/main/AndroidManifest.xml
<service android:name=".telecom.PassthroughInCallService"
    android:permission="android.permission.BIND_INCALL_SERVICE">
    <meta-data android:name="android.telecom.IN_CALL_SERVICE_UI" android:value="true" />
    <meta-data android:name="android.telecom.IN_CALL_SERVICE_RINGING" android:value="true" />
</service>

IN_CALL_SERVICE_RINGING is not a preference. It tells Telecom to stop ringing because this app has taken that responsibility. An app the OS has made responsible for presenting incoming calls is, definitionally, an app whose core function is receiving calls.

Gotcha

A store's "How to fix" section describes the compliance path. It is not a finding that you are guilty. Following it and appealing at the same time destroys the appeal — you would be conceding the permission is not core while arguing that it is.

Why

The real defect was elsewhere: the Play Console full-screen-intent declaration form had never been submitted, so review judged the permission against the store listing alone — and the listing led with "Block calls by your own rules", naming the dialer role once, in a closing caveat about permissions. The APK said phone app; the listing said utility. Review trusts the listing.

Intermediate A privacy policy that promised a feature

The same audit found a "Record caller message" switch. It persisted its flag, validated a consent phrase, rendered as a Switch, and had a passing repository test. Nothing recorded. No RECORD_AUDIO permission, no MediaRecorder, no AudioRecord anywhere in the source.

That is Chapter 20's failure mode again, with a sharper edge: the published privacy policy carried an entire Call recording section, in both languages, describing the capability. A privacy policy is a legally operative document, and call recording is one of the most scrutinised areas in app review. The app was volunteering the topic for a feature it did not have.

Contrast

A dead code path is a bug. A dead code path that a legal document describes to users is a misrepresentation. The remedy is the same either way — make the claim and the code agree — but only one of them can cost you the listing.

Advanced What Android will and will not let you record

Implementing it honestly meant learning what is actually available. Android reserves the real call-audio sources behind a permission third-party apps cannot hold:

SourceAvailable to this app?
VOICE_CALL, VOICE_DOWNLINK, VOICE_UPLINKNo — needs CAPTURE_AUDIO_OUTPUT, which is signature|privileged
AudioPlaybackCapture (API 29+)No — cannot capture voice calls
Accessibility APINo — Play has prohibited its use for call recording since 2022
MediaRecorder.AudioSource.MICYes, but it is acoustic pickup through the earpiece

Holding ROLE_DIALER does not change any row of that table. So the feature was built on MIC, and every failure is treated as ordinary rather than exceptional:

androidApp/src/main/kotlin/.../telecom/AutoResponderRecorder.kt
} catch (e: IllegalStateException) {
    // start() on a mic the platform would not hand over -- the common OEM case.
    Log.w(TAG, "Microphone unavailable during the call", e)
    cleanUpAfterFailure(file)
    false
}

Several manufacturers give the telephony stack exclusive ownership of the microphone during a call, as an anti-wiretapping measure. A false return means the caller is disconnected exactly as it was before recording existed — the blocked call must always end, and must never stay open because recording failed.

Scope

The README, the privacy policy and the in-app toggle description all say the same sentence in four languages: it records through the microphone, so some phones capture nothing. Shipping a feature that may not work is fine. Shipping one while implying it will is not.

Advanced Tying a file to a row without leaking it

Audio belongs on the filesystem; the call log lives in SQLite. That split creates two failure modes, and the schema comment names both:

shared/src/commonMain/sqldelight/.../AppDatabase.sq
-- The file lives in app-internal storage; clearCallLog cannot delete it, so the caller that
-- clears the log must delete the files too -- see CallLogRepository.clearAll.
recording_path TEXT

Deleting rows before files strands the audio: nothing points at it, no UI can reach it, and it survives a "clear log" the user believed destroyed it. So clearAll deletes files first, and deleting a single recording clears the column even when the file delete failed — a row pointing at a file that still exists is worse than an orphan, because the UI keeps offering playback of a recording the user asked to destroy.

The other trap is finding the row at all. The entry is written while the call is still live (the decision must be logged even if everything after it fails), but the recording only exists once the call has ended:

shared/src/commonMain/kotlin/.../rules/SqlCallLogRepository.kt
// The insert and the id read share one transaction: last_insert_rowid() is
// connection-scoped, so a concurrent insert between the two -- two calls arriving
// together, which call waiting makes real -- would otherwise hand back the wrong row.
queries.transactionWithResult {
    queries.insertCallLogEntry(...).value
    queries.lastInsertRowId().executeAsOne()
}
Verified

346 JVM tests, including one that writes a real temp file, attaches it, calls clearAll, and asserts the file is gone. That failure is invisible through the UI — the rows vanish either way — so only a test that looks at the filesystem can catch it.

Case Study: the appeal that changed nothing in the code

The first response to the Play rejection was to start deleting: six files edited, the permission stripped from the manifest, the setFullScreenIntent call removed. It was the wrong instinct, and it was caught by reading the policy the rejection linked to.

The final change set contained no code at all for that issue — a declaration form, a category already set correctly, and rewritten listing copy. The lesson is not "appeal everything". It is that a rejection is a claim, claims can be checked, and the manifest is usually a better witness than the reviewer's summary.

Done when

  • Every user-facing claim about a feature — UI, privacy policy, store listing, onboarding — is backed by code that runs
  • A platform rejection has been checked against the platform's own policy text before you comply with it
  • Deleting a database row deletes whatever it points at outside the database
  • A feature that can fail on some devices says so, in every language you ship

Check Yourself

1. The app holds ROLE_DIALER. Does that let it record call audio with AudioSource.VOICE_CALL?

No. VOICE_CALL requires CAPTURE_AUDIO_OUTPUT, which is signature|privileged — granted only to apps signed with the platform key or installed on the privileged partition. The dialer role grants nothing here. The only option left is MIC, which picks the caller up acoustically and is blocked outright on some OEM builds.

2. Why does clearAll delete the recording files before deleting the rows, rather than after?

The rows hold the paths. Delete them first and the audio is unreachable but still on disk — invisible to the UI, undeletable by the user, and left over from a "clear log" they believed destroyed it.

3. Why must insertCallLogEntry and lastInsertRowId() run in the same transaction?

last_insert_rowid() is scoped to the connection, not to your insert. Another insert landing in between returns that row's id instead. Call waiting makes two simultaneous calls real, and the consequence is one caller's recording filed under a different caller's log entry.

4. A store rejection tells you to remove a permission. What do you check first?

The policy text the rejection links to, against your own manifest. Here the policy auto-granted the permission to apps whose core function is receiving calls, and IN_CALL_SERVICE_RINGING proved that is what the app is. The real gap was an unsubmitted declaration form, which no amount of deleting code would have fixed.

22Permissions Are a Conversation

Every previous chapter treated a permission as a boolean: you have it or you don't. This one treats it as something you ask for, explain, and can lose — three separate design problems, each of which this app got wrong in a different way.

Learning Objectives

  • Recognise why a permission dialog fired from onCreate is the worst possible ask
  • Model permissions the way a user groups them, not the way the manifest lists them
  • Handle a permission being revoked, not just granted
  • Put a failure warning on the screen where it will actually be read
  • Write positive assertions for state transitions instead of absence assertions

Beginner The ask that guarantees a "Deny"

This was the app's entire notification-permission strategy:

androidApp/src/main/kotlin/.../MainActivity.kt — before
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    enableEdgeToEdge()
    refreshPermissionStatus()

    // Fires before the user has seen anything but a splash.
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU && !notificationsPermissionGranted) {
        notificationsPermissionLauncher.launch(Manifest.permission.POST_NOTIFICATIONS)
    }

    setContent { /* welcome screen, which never mentioned permissions */ }
}

The dialog arrived over a welcome screen that said nothing about permissions. From the user's side that is indistinguishable from an app grabbing whatever it can reach on launch — and on Android 13+ a second denial is permanent. The app spent its single most valuable ask on the moment it had explained the least.

Why

The system dialog is a yes/no box with a one-line platform string. Everything persuasive you have to say — what the permission does, what breaks without it, what you will never do with it — has to be said before it opens, because there is no room inside it.

Intermediate A checklist modelled on the user, not the manifest

The replacement is an onboarding step listing each permission with the one thing it is used for. The tempting implementation is to enumerate AndroidManifest.xml. That produces a bad screen:

shared/src/commonMain/kotlin/.../permissions/PermissionChecklist.kt
// Deliberately *not* a mirror of AndroidManifest.xml. VIBRATE is a normal permission with
// nothing to grant, READ_PHONE_STATE and CALL_PHONE are one thing from the user's point of
// view ("Phone"), and USE_FULL_SCREEN_INTENT is an app-op the user can only reach from system
// Settings -- it belongs in the warning banners, not in a checklist of things to tap Allow on.
enum class AppPermission { NOTIFICATIONS, CONTACTS, PHONE, MICROPHONE }

Two rows then behave differently on purpose. Microphone is listed but non-requestable — named so the user knows it exists, never asked for here:

add(PermissionUiItem(AppPermission.MICROPHONE, micGranted, requestable = false))

And the notifications row disappears entirely below API 33, where POST_NOTIFICATIONS does not exist and an Allow button would open nothing:

if (notificationsApplicable) {
    add(PermissionUiItem(AppPermission.NOTIFICATIONS, notificationsGranted, requestable = true))
}
Gotcha

A "required" checklist is the old dialog with extra steps. The continue button here is always enabled; it only changes label to Continue anyway. If refusing a permission cannot get the user into the app, the explanation screen was never an explanation — it was a gate.

Scope

The microphone rule generalises: ask for a sensitive permission at the moment the feature that needs it is switched on, not during onboarding. A dialer asking for the microphone on first run, for a feature that ships off, reads as overreach — and spends the ask before there is anything to show for it.

Advanced A permission you can lose

Granting is the easy half. The default-dialer role can be handed to another app from system Settings at any time, and the app's resume hook only knew how to move one way:

shared/src/commonMain/kotlin/.../onboarding/DialerOnboardingViewModel.kt — before
private fun refresh() {
    if (gateway.isDefaultDialer()) {
        _state.value = _state.value.copy(dialerState = DialerOnboardingState.ALREADY_DEFAULT)
    }
}

Revoke the role and nothing happened. The state stayed GRANTED for the life of the process: blocking toggle on, rules listed, stats counting, and Telecom no longer handing the app a single call. The fix recomputes in both directions, with one carve-out:

private fun refresh() {
    // The system role dialog is on screen; its result, not this poll, decides what happens.
    if (_state.value.dialerState == DialerOnboardingState.REQUESTING) return

    val newState = when {
        gateway.isDefaultDialer() -> DialerOnboardingState.ALREADY_DEFAULT
        _state.value.dialerRoleHeld -> DialerOnboardingState.NOT_REQUESTED
        else -> _state.value.dialerState
    }
    _state.value = _state.value.copy(dialerState = newState)
}

The REQUESTING guard is not defensive padding. An onResume fires when the system role dialog appears over the activity, so without it a refresh lands mid-request, moves the state, and RequestResult's check then throws on a perfectly ordinary grant.

Advanced Where a warning has to live

The app already had permission warning cards. They were a private composable inside SettingsScreen — a screen a user who is not looking for a problem never opens. So an app that had silently stopped screening calls looked, on the screen people actually use, exactly like one that was working.

PermissionWarnings moved to its own file in commonMain, and Home renders it above the counters:

shared/src/commonMain/kotlin/.../home/HomeScreen.kt
// Above the stats deliberately: a user whose blocking has stopped working needs
// to see why before they read a "0 blocked today" that looks like good news.
PermissionWarnings(
    modifier = Modifier.fillMaxWidth(),
    dialerRoleHeld = dialerRoleHeld,
    ...
)

Two design constraints came with the move. Every parameter defaults to the non-warning value, so iOS — which builds these screens and has none of these concepts — renders nothing rather than a fix button that does nothing. And contacts and microphone are deliberately not shown: both are optional, both are explained where the feature that needs them lives, and a banner for a permission the user has not asked to use is a nag rather than a warning.

Contrast

A warning for something broken belongs where the user already is. A warning for something optional belongs where that feature is. Putting both in the same list trains the user to ignore the list.

Case Study: the assertion that would have passed anyway

DialerOnboardingViewModel was not untested. It had coverage of the request flow, the denial path, and the welcome flag. The revocation bug survived because no test ever called Refresh while the role was gone — the only refresh test asserted that a granted role stayed granted.

The obvious regression test is also the wrong one:

// Passes if refresh() downgrades correctly.
// Also passes if refresh() does nothing at all -- which was the bug.
assertNotEquals(DialerOnboardingState.GRANTED, viewModel.state.value.dialerState)

The shipped test names the destination instead:

assertEquals(DialerOnboardingState.NOT_REQUESTED, viewModel.state.value.dialerState)
assertFalse(viewModel.state.value.dialerRoleHeld)

Three of the five new tests were watched failing against the old body before the fix was written. That step is what distinguishes a regression test from a test that merely agrees with the code in front of it.

Verified

368 JVM tests. The Home warnings are covered through the real HomeScreen composable under Robolectric — including a case asserting that a fully permitted app shows no banner at all, because a warning system that cannot be silent is one users learn to scroll past.

Done when

  • No permission dialog opens before the app has explained, in its own words, what the permission is for
  • Refusing any permission still lets the user into the app
  • Every permission the app can lose has a code path that notices the loss
  • The warning for a broken permission is visible on a screen the user opens anyway
  • State-transition tests assert the destination, not the absence of the old value

Check Yourself

1. Why is firing POST_NOTIFICATIONS from onCreate worse than firing it one screen later?

The system dialog has no room to explain anything — it is a yes/no box with a platform string. Everything persuasive must be said before it opens. Fired from onCreate it lands over a screen that has explained nothing, so it reads as an app grabbing what it can. On Android 13+ the second denial is permanent, so this spends a one-shot ask at the moment of least trust.

2. The manifest declares seven permissions. Why does the onboarding checklist show four rows?

Because it is modelled on what the user is being asked, not on what the manifest declares. VIBRATE is a normal permission with nothing to grant; READ_PHONE_STATE and CALL_PHONE are one concept ("Phone") to a user; and USE_FULL_SCREEN_INTENT is an app-op reachable only from system Settings, so it belongs in a warning banner rather than behind an Allow button.

3. Why does refresh() return early when the state is REQUESTING?

The system role dialog appears over the activity, which triggers a resume and therefore a refresh. Without the guard the poll moves the state out from under the in-flight request, and RequestResult's check then throws on an ordinary grant. The dialog's result — not a resume poll — is the authority while a request is open.

4. Why is assertNotEquals(GRANTED, state) a poor regression test for the revocation bug?

It is an absence assertion. It passes when refresh() downgrades correctly and when refresh() does nothing at all — but "does nothing at all" is precisely the bug, so long as the state was not GRANTED to begin with. Naming the expected destination (NOT_REQUESTED) is the only version that fails on the broken code, which is why the tests were run against the old body first.
