01Gradle & The Build System

Learn how the project compiles, links dependencies, and packages into an APK.

Learning Objectives

  • Understand Kotlin DSL build files vs Groovy
  • Read version catalogs and plugin declarations
  • Grasp multi-module Gradle projects
  • See how dependency resolution prevents version conflicts

Beginner What is a build system?

Think of a recipe. You have ingredients (source files, libraries) and steps (compile Kotlin, link resources, sign APK). Gradle orchestrates every step. Before Gradle, developers ran javac, aapt, dx manually. Gradle automates this so one command — ./gradlew :androidApp:assembleDebug — produces a working APK.

Beginner The four build files you need to know

Every KMP Android project has this structure:

settings.gradle.kts    — "Here are my modules"
build.gradle.kts      — "Here are my shared plugins & config"
shared/build.gradle.kts   — "The KMP shared module"
androidApp/build.gradle.kts — "The Android app shell"

Intermediate Version Catalogs — libs.versions.toml

Single source of truth for all dependency versions. Without it, you'd have version numbers scattered across multiple files — upgrade one, forget another, get cryptic runtime crashes.

gradle/libs.versions.toml

[versions]
kotlin = "2.2.20"
agp = "8.7.3"
compose-multiplatform = "1.11.1"
sqldelight = "2.3.2"
koin = "4.2.0"

[libraries]
sqldelight-runtime = { module = "app.cash.sqldelight:runtime", version.ref = "sqldelight" }
koin-core = { module = "io.insert-koin:koin-core", version.ref = "koin" }

[plugins]
kotlin-multiplatform = { id = "org.jetbrains.kotlin.multiplatform", version.ref = "kotlin" }
Why this pattern

Upgrade Kotlin from 2.2.20 to 2.3.0? Change one line. All 8 plugins and libraries that reference kotlin update automatically. No hunting through Gradle files.

Intermediate Root build.gradle.kts — Plugin declarations

build.gradle.kts

plugins {
    alias(libs.plugins.kotlin.multiplatform) apply false
    alias(libs.plugins.compose.multiplatform) apply false
    alias(libs.plugins.android.application) apply false
}

Why apply false? These plugins are declared at the root level (so all subprojects know about them) but only applied in the modules that need them. The shared module applies kotlin.multiplatform; the Android app applies android.application. Without apply false, every subproject would get every plugin.

Intermediate settings.gradle.kts — Module registry

settings.gradle.kts

rootProject.name = "BloqueaLlamadas"

include(":shared")
include(":androidApp")

Gradle needs to know which directories are subprojects. Each include points to a directory with its own build.gradle.kts. The root project can configure them all at once in allprojects { } or subprojects { } blocks.

Advanced Dependency resolution strategy

Sometimes libraries pull in incompatible transitive dependencies. Koin 4.2.0 pulls androidx.activity-ktx 1.12.4 which needs AGP 8.9.1+. We're on 8.7.3 — crash.

build.gradle.kts (root)

allprojects {
    configurations.all {
        resolutionStrategy {
            force(
                "androidx.activity:activity:1.9.3",
                "androidx.activity:activity-ktx:1.9.3",
            )
        }
    }
}
Why

force() overrides whatever version any library requests. We pin to 1.9.3 which works with AGP 8.7.3. Koin only touches baseline ComponentActivity APIs present since 1.9.3 — safe downgrade.

Trade-off

Forcing versions is a hammer — use sparingly. If Koin 4.3.0 removes the need, remove the force block. Document why each force exists (see the comment in the real build file) so future maintainers know when it can be dropped.

Key Takeaways

  • Kotlin DSL (.kts) replaces Groovy — type-safe, IDE autocomplete
  • Version catalogs centralize dependency versions — one-line upgrades
  • apply false declares plugin availability without forcing it on all modules
  • resolutionStrategy.force() is a last resort for transitive dependency conflicts
Check your understanding (4 questions)

1. What happens if you remove apply false from a plugin in the root build.gradle.kts?

Every subproject would apply that plugin, even the shared module which doesn't need android.application. The build would fail because the shared module isn't an Android app.

2. Why use version.ref in the version catalog instead of hardcoding version numbers in build.gradle.kts?

Single source of truth. Upgrade Kotlin from 2.2.20 to 2.3.0 and all 8+ dependencies that reference kotlin update automatically. Prevents version-mismatch bugs.

3. What does resolutionStrategy.force() do, and when should you use it?

It overrides whatever version any transitive dependency requests. Use only as a last resort when a library demands a version incompatible with your build tools. Document the reason.

4. How does settings.gradle.kts connect to the other build files?

include(":shared") tells Gradle to look for shared/build.gradle.kts. Without the include, Gradle doesn't know the directory is a subproject module.

02KMM Architecture

How Kotlin Multiplatform shares code between Android and iOS without sacrificing platform APIs.

Learning Objectives

  • Understand the source set hierarchy
  • Master the expect/actual pattern
  • See how platform modules inject platform-specific dependencies
  • Compare KMP to alternatives (Flutter, React Native)

Beginner What is Kotlin Multiplatform?

KMP lets you write business logic once in Kotlin and compile it to JVM (Android), Native (iOS), JS (web), and Wasm. The key insight: you don't share UI code between platforms — each platform renders its own UI. But with Compose Multiplatform, even the UI can be shared.

In this project, commonMain holds all the logic: rule engine, repositories, ViewModels, Compose screens. androidMain and iosMain are thin layers (~4 files each) that provide platform-specific implementations.

Intermediate Source set hierarchy

shared/build.gradle.kts (source sets)

kotlin {
    androidTarget()
    iosArm64()
    iosSimulatorArm64()

    sourceSets {
        commonMain.dependencies {
            implementation(compose.runtime)
            implementation(libs.sqldelight.runtime)
            implementation(libs.koin.core)
        }
        androidMain.dependencies {
            implementation(libs.sqldelight.android.driver)
        }
        iosMain.dependencies {
            implementation(libs.sqldelight.native.driver)
        }
    }
}
Key insight

commonMain depends on sqldelight.runtime (pure Kotlin). androidMain adds the Android-specific driver; iosMain adds the Native driver. The expect/actual pattern bridges these at compile time.

Intermediate The expect/actual pattern

Declare an interface (or expect declaration) in commonMain. Each platform provides an actual implementation:

commonMain — ContactsGateway.kt

interface ContactsGateway {
    suspend fun contactNumbers(): Set<String>
    fun hasPermission(): Boolean
}

androidMain — AndroidContactsGateway.kt

class AndroidContactsGateway(private val context: Context) : ContactsGateway {
    override suspend fun contactNumbers(): Set<String> =
        withContext(Dispatchers.IO) {
            // Read from ContactsContract provider
            context.contentResolver.query(ContactsContract.CommonDataKinds.Phone.CONTENT_URI, ...)
        }
}

Why interfaces over expect class: expect class has Beta compiler limitations and can't accept constructor parameters that differ by platform. A plain interface in commonMain with platform actual implementations is the idiomatic KMP pattern.

Advanced Platform modules — wiring DI per platform

commonMain — KoinInit.kt

fun initKoin(appDeclaration: KoinAppDeclaration = {}) {
    startKoin {
        appDeclaration()
        modules(platformModule(), sharedModule)
    }
}

platformModule() is an expect fun — each platform returns its module with platform-specific bindings (Android Context, iOS NSApplication). The sharedModule is pure Kotlin, identical on all platforms.

KMP vs Alternatives

  • Flutter: Dart language (new skill), custom rendering engine (not native UI), no access to Telecom APIs without plugins
  • React Native: JavaScript bridge (performance overhead), platform modules needed for native APIs
  • KMP: Native Android APIs accessible with zero bridging. Same Kotlin skills as Android dev.

Common KMP iOS Pitfalls

iOS Kotlin/Native compilation often reveals issues hidden on JVM. The Corta Spam project hit several real-world gotchas:

  • Dispatchers.IO is marked @InternalCoroutinesApi on Kotlin/Native — crashes at compile time. Use Dispatchers.Default or an expect/actual dispatcher.
  • kotlinx.datetime.Clock.System may not resolve on all Native toolchains — platform-specific time providers (expect/actual) are more reliable.
  • Navigation Compose KMP Bundle.getString() doesn't compile for iOS — cast to Map<String, *> instead.
  • Koin must be initialized manually on iOS — Android's Application.onCreate() doesn't exist on iOS.
  • Compose Multiplatform Metal GPU rendering may hang on certain iOS simulators — restart the simulator or test on a different device model.

See Chapter 14 for full debugging procedures and real crash logs for each of these errors.

Key Takeaways

  • Put business logic in commonMain — it compiles everywhere
  • Use interfaces (not expect class) for platform abstractions — avoids Beta compiler issues
  • Platform modules inject platform-specific types via Koin
  • KMP is the most "Android-native" cross-platform option — no new language, no bridge
Check your understanding (3 questions)

1. Why use an interface in commonMain instead of expect class for DriverFactory?

expect class has Beta compiler limitations, can't have platform-specific constructor parameters, and triggers compiler warnings. A plain interface with platform actual implementations is the idiomatic and stable KMP pattern.

2. Can androidMain code use iOS APIs?

No. androidMain compiles only for the JVM/Android target. It can use Android SDK APIs (Context, ContactsContract). iosMain uses iOS frameworks. They never mix.

3. What happens if you put an Android-specific API call in commonMain?

Compilation fails for iOS. commonMain compiles for ALL targets simultaneously, so it can only use APIs available on all platforms (pure Kotlin, Compose Multiplatform, kotlinx libraries).

03Jetpack Compose — Declarative UI

Build native Android UI with pure Kotlin — no XML, no findViewById, no View hierarchy.

Learning Objectives

  • Understand declarative vs imperative UI
  • Master @Composable functions and recomposition
  • Use StateFlow and ViewModel for reactive state
  • Apply Material3 theming and Modifier chains

Beginner Imperative vs Declarative

Imperative (old XML way): "Find the TextView with ID 'title'. Set its text to 'Hello'. When data changes, find it again and update."

Declarative (Compose): "Here's a Text composable showing state.title. When state.title changes, the UI automatically re-renders."

No more findViewById, no more manual view updates, no more "my RecyclerView shows stale data" bugs. The UI is a function of state — UI = f(state).

Intermediate The @Composable function

CallScreen.kt (fragment)

@Composable
fun CallScreen(
    number: String,
    phase: CallUiPhase,
    onAnswer: () -> Unit,
    onDecline: () -> Unit,
) {
    MaterialTheme {
        Surface(modifier = Modifier.fillMaxSize()) {
            Column(modifier = Modifier.fillMaxSize().safeDrawingPadding().padding(24.dp)) {
                Text(
                    text = when (phase) {
                        CallUiPhase.RINGING -> "Incoming call"
                        CallUiPhase.ACTIVE -> "In call"
                        else -> ""
                    }, style = MaterialTheme.typography.labelLarge)
                Text(text = number, style = MaterialTheme.typography.headlineMedium)
            }
        }
    }
}

Every @Composable function:

  • Has no return value — it emits UI into the composition tree
  • Can call other @Composable functions
  • Re-executes ("recomposes") when its state inputs change
  • Runs on the main thread (unless explicitly shifted)

Intermediate State management — ViewModel + StateFlow

HomeViewModel.kt (fragment)

class HomeViewModel(
    private val callLogRepository: CallLogRepository,
    private val settingsRepository: SettingsRepository,
) : ViewModel() {
    private val _state = MutableStateFlow(HomeUiState())
    val state: StateFlow<HomeUiState> = _state.asStateFlow()

    val blockingEnabled: StateFlow<Boolean> =
        settingsRepository.blockingEnabled
            .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), true)

    init { refresh() }

    fun refresh() {
        viewModelScope.launch {
            val stats = callLogRepository.blockedStats()
            _state.value = HomeUiState(blockedToday = stats.today)
        }
    }
}

In the Composable:

val state by homeViewModel.state.collectAsState()
Text(text = "${state.blockedToday}")  // auto-updates when StateFlow emits
Why StateFlow over LiveData

LiveData is Android-only. StateFlow is pure Kotlin — works in KMP commonMain, works with Compose's collectAsState(), and integrates with coroutines naturally.

Advanced Modifier chains — order matters

// Padding added OUTSIDE the clickable area
Modifier.clickable { ... }.padding(16.dp)

// Padding added INSIDE — clickable area extends to padded bounds
Modifier.padding(16.dp).clickable { ... }

// Chaining: fill → safe drawing padding → content padding
Modifier.fillMaxSize().safeDrawingPadding().padding(24.dp)

Modifiers are applied outside-in: the leftmost modifier wraps everything to its right. safeDrawingPadding() must come before padding() to ensure the system bars inset is handled before the content padding is applied.

Key Takeaways

  • Compose is declarative: describe what the UI should be, not how to update it
  • @Composable functions re-execute when State reads change — this is recomposition
  • StateFlow + collectAsState() is the idiomatic state bridge in KMP
  • Modifier order determines layout behavior — always test your chains
Check your understanding (4 questions)

1. What triggers recomposition in Compose?

When a State object read by a @Composable function changes value. The Compose runtime tracks which composables read which states and re-executes only those that need updating.

2. Why use StateFlow instead of LiveData in KMP?

LiveData is an Android-only API. StateFlow is pure Kotlin (kotlinx.coroutines) and works in commonMain, making it available on iOS, JVM, and JS targets.

3. What happens if you call .padding(16.dp) before .clickable {} vs after?

Padding first: padding is INSIDE the clickable area — the entire padded region is tappable. Clickable first: only the inner (non-padded) area is tappable; the padding sits outside the clickable region.

4. What does stateIn(viewModelScope, WhileSubscribed(5000), true) do?

Converts a cold Flow to a hot StateFlow. WhileSubscribed(5000) keeps the upstream active for 5 seconds after the last subscriber disappears (prevents restart on config changes). The last argument (true) is the initial value.

04Navigation Compose

Move between screens while keeping state, passing arguments, and managing the back stack.

Learning Objectives

  • Define routes with typed arguments
  • Build a NavHost with composable destinations
  • Use launchSingleTop and popUpTo for correct navigation
  • Handle section-based navigation for bottom bars

Beginner Routes — String-based screen identifiers

object Routes {
    const val HOME = "home"
    const val CALL_LOG = "call_log/{filter}"
    const val STATS = "stats"
    const val SETTINGS = "settings"
    fun callLogRoute(filter: String = "all") = "call_log/$filter"
}

{filter} is a path parameter — it gets substituted at runtime. call_log/today, call_log/week, call_log/all all match the same route template.

Intermediate NavHost wiring

AppNavHost.kt (core pattern)

@Composable
fun AppNavHost(navController: NavHostController, ...) {
    NavHost(navController = navController, startDestination = Routes.HOME) {
        composable(Routes.HOME) {
            HomeScreen(onNavigateToCallLog = {
                navController.navigate(Routes.callLogRoute())
            })
        }
        composable(
            route = Routes.CALL_LOG,
            arguments = listOf(navArgument("filter") { type = NavType.StringType })
        ) { backStackEntry ->
            val filter = backStackEntry.arguments?.getString("filter") ?: "all"
            CallLogScreen(filter = filter)
        }
    }
}

Each composable() block registers a screen. When the navController navigates to that route, Compose creates (or reuses) the composable. The backStackEntry.arguments bundle contains the parsed route parameters.

Advanced Navigation options — preventing reload

The bug

User taps "Call Log" in the bottom bar repeatedly. Each tap navigates call_log/all → popUpTo(home) → navigate(call_log/all), which destroys and recreates the screen.

AppNavHost.kt — the fix

val navBackStackEntry by navController.currentBackStackEntryAsState()
val currentRoute = navBackStackEntry?.destination?.route
val selectedSection = routeSection(currentRoute)

onNavigate = { index ->
    val destination = sectionRoutes.getOrElse(index) { Routes.HOME }
    val isRoot = currentRoute in sectionRoutes ||
        (currentRoute?.startsWith("call_log") == true && destination.startsWith("call_log"))
    if (index == selectedSection && isRoot) return@AdaptiveScaffold // already here, skip
    navController.navigate(destination) {
        popUpTo(Routes.HOME)
        launchSingleTop = true
    }
}
Why two checks

launchSingleTop alone isn't enough — it prevents duplicate instances but popUpTo can still destroy the existing screen. The explicit isRoot check prevents any navigation when already on the section root. The call_log pattern check handles route templates where "call_log/{filter}" ≠ "call_log/all".

Key Takeaways

  • navArgument() with NavType enables type-safe argument passing
  • launchSingleTop = true reuses existing screen instead of creating duplicates
  • popUpTo(ROOT) clears the back stack when switching sections
  • Explicit route comparison prevents screen reload on same-tab taps
Check your understanding (3 questions)

1. What does launchSingleTop = true do?

If a destination matching the route already exists at the top of the back stack, it reuses it instead of creating a new instance. Prevents "screen stacking" when tapping the same nav item.

2. Why use popUpTo(Routes.HOME) when switching bottom nav tabs?

Without it, tapping between tabs would stack screens: [Home, CallLog, Home, BlockList, Home]. The back stack would grow indefinitely. popUpTo(HOME) clears everything and makes each tab feel like a fresh start.

3. How are route arguments like {filter} passed and retrieved?

They're part of the route string: "call_log/today". Navigation Compose parses them into the arguments bundle. The composable retrieves them via backStackEntry.arguments?.getString("filter").

05Adaptive Form Factors

Make the app look great on phones (portrait/landscape), foldables, and tablets with zero platform-specific code.

Learning Objectives

  • Detect WindowSizeClass at runtime
  • Switch between BottomBar and NavigationRail
  • Cap content width and center on wide screens
  • Implement two-pane list-detail on Expanded

Beginner Why adaptive?

Android apps run on everything from 4" phones to 14" tablets. A layout built for 360dp-wide phones looks absurdly stretched on 840dp+ tablets. The WindowSizeClass system gives three tiers so you can build one layout that works everywhere.

Intermediate WindowSizeClass detection

WindowSizeClass.kt

enum class WindowSizeClass { Compact, Medium, Expanded }

@Composable
fun rememberWindowSizeClass(): WindowSizeClass {
    val widthDp = LocalConfiguration.current.screenWidthDp
    return when {
        widthDp < 600 -> WindowSizeClass.Compact   // phone portrait
        widthDp < 840 -> WindowSizeClass.Medium    // phone landscape, small tablet
        else -> WindowSizeClass.Expanded               // tablet, desktop
    }
}

600dp and 840dp are Material Design canonical breakpoints. Respect them, don't invent your own — users recognize the pattern.

Intermediate AdaptiveScaffold — two scaffold modes

AdaptiveScaffold.kt (structure, ~150 lines)

when (windowSizeClass) {
    WindowSizeClass.Compact -> {
        Column {
            Box(modifier = Modifier.weight(1f)) { content() }
            NavigationBar {
                NavigationBarItem(selected = ..., onClick = { onNavigate(i) })
            }
        }
    }
    WindowSizeClass.Medium, WindowSizeClass.Expanded -> {
        Row {
            NavigationRail {
                NavigationRailItem(selected = ..., onClick = { onNavigate(i) })
            }
            Box(modifier = Modifier.weight(1f)) { content() }
        }
    }
}

NavigationBar (bottom) for Compact and NavigationRail (side) for Medium/Expanded. The content area is identical — only the chrome changes.

Advanced AdaptiveContent + two-pane layout

On wide screens, content looks best capped at 600dp and centered. Otherwise, a single-column form stretches across a 14" tablet looking absurd.

// CallLogScreen — one pane on phone, two panes on tablet
if (windowSizeClass == WindowSizeClass.Expanded) {
    Row {
        CallLogListPane(modifier = Modifier.width(340.dp).fillMaxHeight())
        CallLogDetailPane(modifier = Modifier.weight(1f).fillMaxHeight())
    }
} else {
    AdaptiveContent(windowSizeClass = windowSizeClass) {
        // single column, capped at 600dp
        LazyColumn { ... }
    }
}

340dp for the list pane is a Goldilocks width: wide enough for readable text, narrow enough that the detail pane has room on an 840dp screen (840 - 340 = 500dp remaining). On larger screens the detail pane grows via weight(1f).

Edge-to-edge

Android 15+ (targetSdk 36) enforces edge-to-edge — your content draws behind the status bar and navigation bar. WindowInsets.safeDrawing.only(Top + Horizontal) adds padding only where needed so content isn't hidden behind system chrome.

Key Takeaways

  • WindowSizeClass uses 600dp and 840dp Material Design breakpoints
  • NavigationBar (bottom) for Compact, NavigationRail (side) for larger
  • AdaptiveContent caps at 600dp — content looks silly stretched to 1400dp
  • Two-pane on Expanded: 340dp fixed list + weight(1f) detail — test on actual tablet
Check your understanding (3 questions)

1. Why 600dp and 840dp specifically?

These are Google's canonical Material Design breakpoints. 600dp is where a phone landscape or small tablet has room for a nav rail. 840dp is where a full-size tablet can support two-pane layouts.

2. What happens if you use NavigationBar on an Expanded screen?

It would work but look wrong — a bottom bar stretches across the full tablet width while your eyes track a completely different focal point than on a phone. The nav rail keeps navigation near your thumb/pointer in landscape.

3. Why weight(1f) on the detail pane instead of a fixed width?

A fixed width would work on exactly one screen size. weight(1f) means "take all remaining space" — it grows/shrinks with the window, working on 840dp and 1200dp tablets alike.

06SQLDelight — Type-Safe SQL for KMP

Persist rules, call logs, and settings with a database that works identically on Android and iOS.

Learning Objectives

  • Write .sq files with valid SQL and named queries
  • Design schema with migrations (5 versions)
  • Implement the Repository pattern over SQLDelight
  • Handle platform-specific drivers via DriverFactory

Beginner Why SQLDelight over Room?

Room is Android-only (uses annotation processing, ties to Android lifecycle). SQLDelight generates Kotlin from .sq files — works on JVM, Native, JS. For KMP, it's the standard choice.

Intermediate Schema design

AppDatabase.sq (7 tables)

CREATE TABLE BlockedNumber (
    id INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    number TEXT NOT NULL,
    label TEXT,
    created_at INTEGER NOT NULL DEFAULT (CAST(strftime('%s','now') AS INTEGER)),
    UNIQUE(number)
);

-- Named query → generates Kotlin function
selectAllBlockedNumbers:
SELECT * FROM BlockedNumber ORDER BY created_at DESC;

insertBlockedNumber:
INSERT OR IGNORE INTO BlockedNumber(number, label) VALUES (?, ?);

Pattern: each table gets CRUD queries: selectAll, insert, deleteById, toggle. The CallLogEntry table uses CHECK constraints for type safety on the action column.

Advanced Migrations & timestamp portability

Schema history lives in two places you probably expect — AppDatabase.sq holds the current CREATE TABLE statements, and numbered .sqm files describe how to bring an older database up to that shape — plus a third that is easy to forget: a snapshot baseline under src/commonMain/sqldelight/databases/, which only exists if you point the build at it:

// shared/build.gradle.kts
sqldelight {
    databases {
        create("AppDatabase") {
            packageName.set("org.carlospinan.bloqueador.app.db")
            verifyMigrations.set(true)
            schemaOutputDirectory.set(file("src/commonMain/sqldelight/databases"))
        }
    }
}

verifyMigrations takes the oldest snapshot in that directory, replays every later .sqm on top of it, and diffs the result against AppDatabase.sq. With no baseline it has nothing to replay from, so it builds the database from the current .sq — which already contains every column the migrations were going to add — and then dies on the first ADD COLUMN. A missing databases/ directory doesn't disable the check; it makes it fail for a reason that has nothing to do with your migrations.

Squashing while still pre-release: this app renamed its database file (bloquellamadas.db → cortaspam.db) before any public release. A new filename means every device opens a fresh, empty database, so the seven historical .sqm files had zero users left to migrate. They were deleted and the current schema was snapshotted as databases/1.db. Migration history is only worth carrying when somebody is actually still on the old version — otherwise it is untested code that can only cost you.

Critical decision: timestamps use strftime('%s', 'now') instead of unixepoch(). Why? unixepoch() needs SQLite 3.38+ — not available on older Android devices (confirmed crash on API 33 emulator). strftime() has been available since SQLite 3.0.

Advanced Repository pattern — interface + SQL impl

RuleRepository (interface in commonMain)

interface RuleRepository {
    fun blockedNumbers(): Flow<List<BlockedNumberEntry>>
    suspend fun addBlockedNumber(number: String)
    suspend fun removeBlockedNumber(id: Long)
}

SqlRuleRepository (SQLDelight implementation)

class SqlRuleRepository(private val db: AppDatabase) : RuleRepository {
    override fun blockedNumbers() = db.appDatabaseQueries
        .selectAllBlockedNumbers()
        .asFlow().mapToList()
}
Why Flow

SQLDelight's asFlow() emits on every database change. ViewModels collect these flows and the UI auto-updates — no polling, no manual refresh.

Key Takeaways

  • SQLDelight is the KMP-standard database — Room is Android-only
  • Named queries in .sq files generate type-safe Kotlin functions
  • asFlow().mapToList() gives reactive query results — UI auto-updates on writes
  • Use strftime() not unixepoch() for portable timestamp handling
Check your understanding (4 questions)

1. How does a named query like selectAllBlockedNumbers become a Kotlin function?

SQLDelight's Gradle plugin reads the .sq file at compile time and generates a Kotlin function with the same name, typed parameters for WHERE clauses, and typed return values.

2. Why Flow as the return type for list queries?

asFlow() triggers a re-emission whenever the underlying table changes. A ViewModel collecting this Flow automatically gets fresh data after any insert/delete — no manual refresh calls needed.

3. Why not use unixepoch() for timestamps?

unixepoch() requires SQLite 3.38+ which isn't bundled on older Android versions (confirmed crash on API 33). strftime('%s', 'now') works on all SQLite versions since 3.0.

4. What does INSERT OR IGNORE do?

If a row with the same UNIQUE constraint already exists, the insert is silently skipped (no error). Used here for number which has a UNIQUE constraint — prevents duplicate entries.

07Koin — Dependency Injection

Wire up repositories, ViewModels, and platform services without annotation processing or code generation.

Learning Objectives

  • Define modules with single, factory, get()
  • Inject dependencies in Activity, Service, and ViewModel
  • Split modules into shared and platform-specific
  • Compare Koin to Dagger/Hilt

Beginner Why DI matters

Without DI, every class creates its own dependencies:

class HomeViewModel() {
    private val repo = SqlRuleRepository(createDatabase(AndroidDriverFactory(context)))
    // hard to test — can't swap the database for a fake
}

With DI, dependencies are passed in:

class HomeViewModel(
    private val callLogRepository: CallLogRepository, // interface!
) : ViewModel()

Tests pass a fake CallLogRepository. Production passes the SQL one. Koin decides which at startup.

Intermediate Module definitions

SharedModule.kt

val sharedModule = module {
    single { createDatabase(get()) }                // one DB instance for app lifetime
    single<RuleRepository> { SqlRuleRepository(get()) }   // bound to interface
    single<CallLogRepository> { SqlCallLogRepository(get()) }
    factory { HomeViewModel(get(), get()) }            // new VM each time
    factory { CallLogViewModel(get()) }
}

single = one instance for the application lifetime (database, repositories). factory = new instance each time requested (ViewModels — they're scoped by the platform).

Beginner What is InCallService?

Android's Telecom framework manages the phone stack. When your app is the default dialer, InCallService is the callback that fires on every incoming and outgoing call. You get a Call object with the phone number, state (ringing/active/disconnected), and methods to answer() or reject().

Intermediate Service manifest + lifecycle

Advanced Show UI instantly — the race condition

PassthroughInCallService.kt (critical flow)

override fun onCallAdded(call: Call) {
    val number = call.details?.handle?.schemeSpecificPart.orEmpty()

    // STEP 1: Show UI IMMEDIATELY — don't wait for rule evaluation
    InCallState.attach(call)   // sets ringing state for InCallActivity to read
    startActivity(Intent(this, InCallActivity::class.java)
        .addFlags(Intent.FLAG_ACTIVITY_NEW_TASK))

    // STEP 2: Evaluate rules asynchronously
    serviceScope?.launch {
        val decision = evaluateCall(number)
        if (decision.isBlocked) {
            val autoConfig = autoResponderRepository.config.first()
            if (autoConfig.enabled) {
                call.registerCallback(callCallback)
                call.answer(VideoProfile.STATE_AUDIO_ONLY)  // answer for auto-responder
            } else {
                call.reject(false, null)           // silent reject
            }
        }
        // If allowed: InCallActivity already showing — user decides answer/decline
    }
}
Why show UI first, evaluate later

If you evaluate before showing UI and the evaluation takes 500ms (DB queries, contact lookup), Android shows its own system incoming-call UI because it thinks you're not responding. By showing InCallActivity immediately, the system sees your UI and stays out of the way. If the call turns out to be blocked, call.reject() dismisses it.

Advanced InCallState — the singleton bridge

Key Takeaways

  • IN_CALL_SERVICE_UI and IN_CALL_SERVICE_RINGING metadata tells Android to use your UI
  • Show the InCallActivity FIRST, evaluate rules SECOND — wins the race against system UI
  • InCallState as a singleton bridges the Service (has Call object) to the Activity (shows UI)
  • setShowWhenLocked + requestDismissKeyguard are mandatory for incoming call UX
Check your understanding (4 questions)

1. Why start InCallActivity before rule evaluation?

If you delay while evaluating rules, the system sees your InCallService as unresponsive and shows its own incoming call UI instead. Starting the activity first preempts this race condition.

2. What does IN_CALL_SERVICE_RINGING = true do?

It tells Android that your InCallService handles the ringing state. Without it, the system shows its own ringing notification alongside your UI — the user sees two overlapping call screens.

3. Why use a singleton object for InCallState instead of a regular class?

There's only one active call at a time by design. A singleton provides simplicity — the Service writes to it, the Activity reads from it. Both access the same StateFlow without needing to coordinate instances.

4. What's the difference between call.reject(false, null) and calling finish() on the Activity?

call.reject() tells Telecom to reject the call — the caller gets a busy signal. finish() only closes your Activity; the call would continue ringing in the background. You must use Telecom APIs to actually control the call.

10Rule Precedence Engine

Design a decision system that evaluates every incoming call against 7 rule types in strict order — pure, testable, fast.

Learning Objectives

  • Design a stateless ResolveContext pattern
  • Implement strict precedence ordering
  • Normalize phone numbers for cross-format matching
  • Build glob-style pattern matching

Beginner What does a call blocker decide?

Every incoming call needs one of three outcomes: BLOCK (reject), ALLOW (let through), or AUTO_RESPOND (answer with greeting). The rule engine checks 7 rule types in fixed order and returns the first match. If nothing matches, the "default action" setting takes over.

Intermediate ResolveContext — stateless input

RulePrecedenceResolver.kt

data class ResolveContext(
    val allowlistedNumbers: Set<String>,
    val contactNumbers: Set<String> = emptySet(),
    val blockedNumbers: Set<String>,
    val enabledPatterns: List<PatternRule>,
    val enabledCountryCodes: Set<String>,
    val defaultAction: DefaultAction = DefaultAction.ALLOW,
    // ... plus spam provider, action rules, schedule rules
)
Why a data class, not global state

The resolver is a pure function: evaluate(number, context) → Decision. All inputs are in the data class. No mutable state. This makes it trivially testable — create a context, check the output. No mock servers, no database setup, no race conditions.

Intermediate Precedence order (7 levels)

The order is deliberate and tested at each step:

// 1. MANUAL BLOCK — user explicitly chose to block this exact number
if (normalized in context.blockedNumbers) return RuleDecision.ManualBlock

// 2. ALLOWLIST — contacts + manual allowlist override everything below
if (normalized in mergedAllowlist) return RuleDecision.Allowlist

// 3. PATTERN — glob match (prefix, suffix, contains)
for (pattern in context.enabledPatterns) { ... }

// 4. COUNTRY — country code from libphonenumber-style parsing
val countryCode = parseCountryCode(number)

// 5. SPAM → 6. ACTION → 7. SCHEDULE

// 8. DEFAULT — allow, block, or ask (based on user settings)
Why manual block overrides contacts

If a user explicitly added mom's number to the block list, they have a reason. Respecting that explicit choice is more important than the auto-allow-contacts convenience feature.

Intermediate Making "Ask" mean something

The default action has three settings: Allow, Block, Ask. For a long time, Ask silently behaved exactly like Allow — there was no way to build a real-time "should I let this through?" prompt, because by the time the resolver runs, the call is already ringing. Rather than ship a setting that lies about what it does, the fix makes Ask a genuinely distinct outcome:

RulePrecedenceResolver.kt — the default step

// 8. Default: honor the user's chosen default action.
return when (context.defaultAction) {
    DefaultAction.BLOCK -> RuleDecision.DefaultBlock
    DefaultAction.ASK -> RuleDecision.PendingReview
    DefaultAction.ALLOW -> RuleDecision.DefaultAllow
}

The call still goes through — you can't interrupt a live ring to ask the user anything — but PendingReview is logged with its own rule_type = 'REVIEW' tag instead of blending into ordinary allowed calls. Home shows a "Pending review" count; Call Log gets a matching filter and a distinct amber "Needs review" state.

An honest limitation, not a bug: the call log is an immutable, append-only history (Chapter 06) — there's no "resolved" flag. If the user later blocks a number that generated a REVIEW entry, that old entry stays tagged REVIEW forever. This is a filter over history, not a stateful inbox with read/unread state. Don't oversell it in the UI as more than it is.

Advanced Phone number normalization

The problem: A contact is stored as "(555) 123-4567". The incoming call arrives as "+15551234567". Direct string comparison fails — contacts aren't auto-allowed.

PhoneNumberParser.kt — the fix

fun normalizeForComparison(number: String): String =
    number.filter { it.isDigit() }

Applied everywhere: incoming call number, contact numbers, blocked/allowlist numbers, pattern cores. All comparisons now use digit-only strings. "+1 (555) 123-4567" → "15551234567" matches "+15551234567" → "15551234567".

Where normalization happens:

  • AndroidContactsGateway — normalizes contact numbers when reading from ContactsContract
  • RulePrecedenceResolver.evaluate() — normalizes the incoming number AND all stored numbers from context before comparison
  • matchesPattern() — normalizes both the pattern core and the target number

Advanced Pattern matching

RulePrecedenceResolver.matchesPattern()

internal fun matchesPattern(number: String, pattern: String): Boolean {
    val normalizedCore = normalizeForComparison(core)
    val normalizedNumber = normalizeForComparison(number)
    return when {
        startsWithStar && endsWithStar -> normalizedNumber.contains(normalizedCore)
        startsWithStar -> normalizedNumber.endsWith(normalizedCore)
        endsWithStar -> normalizedNumber.startsWith(normalizedCore)
        else -> normalizedNumber == normalizedCore
    }
}

Simple glob, not full regex: Full regex would be impossible to expand into concrete numbers for iOS's CallDirectory extension. Simple prefix/suffix/contains globs can be pre-computed into static lists that iOS can consume.

Key Takeaways

  • ResolveContext is a pure data class — no mutable state, no side effects, fully testable
  • Manual block overrides contacts — user's explicit choice beats convenience
  • Normalize ALL numbers to digits-only before comparison — cross-format matching
  • Glob patterns (not regex) keep the engine simple and iOS-compatible
  • Don't let a setting silently do something other than what it claims — Ask now produces a distinct, taggable decision instead of quietly aliasing Allow
Check your understanding (6 questions)

1. Why does manual block (step 1) override allowlist (step 2)?

The user explicitly chose to block this number. If the allowlist overrode manual blocks, adding your ex to the block list would be pointless — they'd just get through because they're also in your contacts.

2. What problem does normalizeForComparison() solve?

Phone numbers arrive in different formats: contacts store "(555) 123-4567", incoming calls arrive as "+15551234567". Direct string comparison would say these are different numbers. Normalization strips everything except digits so they match.

3. Why pass all data in a ResolveContext instead of having the resolver access the database directly?

Pure functions are testable. You can create any ResolveContext in a test and verify the output — no database, no mocks. If the resolver accessed the database, tests would need a running SQLite instance.

4. What happens if no rule matches and defaultAction is BLOCK?

The call is blocked via DefaultBlock. But only AFTER all 7 rule levels failed to match. If any rule (including allowlist) matched, it would have short-circuited earlier — the default only activates when nothing else applies.

5. Why not use full regex for pattern matching?

iOS's CallDirectory extension takes a static list of concrete numbers — it can't evaluate regex at runtime. Simple prefix/suffix/contains patterns can be expanded into concrete number lists that iOS can consume. Regex patterns would be Android-only.

6. Why does RuleDecision.PendingReview still let the call through instead of holding it?

There's no way to pause a live ring and wait for the user to decide — the call is already happening. PendingReview is a logging distinction, not a hold: the call proceeds like DefaultAllow, but gets tagged rule_type='REVIEW' so the user can look at it later in Call Log instead of it disappearing into ordinary allowed calls.

Error 1: Dispatchers.IO is internal on Kotlin/Native

Symptom

Why

Dispatchers.IO is annotated with @InternalCoroutinesApi in the Kotlin/Native artifact. It's platform-specific — Android implemented it as a thread pool, but Native/JS haven't stabilized it.

Diagnosis

Fix

Replace all Dispatchers.IO with Dispatchers.Default (43 occurrences across SqlRuleRepository, SqlCallLogRepository, KeyValueSettingsStore). Default is public on all platforms. For IO-heavy workloads, use expect/actual to provide the optimal dispatcher per platform.

15Call Notifications & Permission UX

A default-dialer app has to show its own incoming-call UI — Android doesn't do it for you. Here's why the obvious approach silently fails on a locked phone, the notification design that actually works, and a real case study in a platform limitation no amount of app code can fix.

Learning Objectives

  • Understand background-activity-launch restrictions and why full-screen-intent notifications exist
  • Design notification channels by importance, not by feature
  • Use NotificationCompat.CallStyle — the same API real dialers use
  • Wire notification button actions back into app state via PendingIntent.getBroadcast
  • Detect and deep-link broken permission state instead of asking once and going silent
  • Recognize when a limitation is the platform's, not the app's

Beginner Why startActivity() alone isn't enough

The obvious way to show incoming-call UI is PassthroughInCallService.onCallAdded() calling startActivity(InCallActivity). That works — right up until the screen is off or locked. Since Android 10, apps can't launch activities from the background without an active user-interaction token, and a ringing call arriving while the phone is asleep is exactly the background case. The call silently never shows anything.

The fix isn't more permissions — it's a different mechanism. A notification with setFullScreenIntent() is the one OS-sanctioned way to launch UI over the lock screen from the background. Real dialers, alarm apps, and video-call apps all use this same escape hatch.

Intermediate Three channels, three importances

IncomingCallNotifier.kt — createChannel()

NotificationChannel("incoming_calls", ..., NotificationManager.IMPORTANCE_HIGH).apply {
    setBypassDnd(true)
    lockscreenVisibility = Notification.VISIBILITY_PUBLIC
}
NotificationChannel("ongoing_call", ..., NotificationManager.IMPORTANCE_LOW)
NotificationChannel("call_history", ..., NotificationManager.IMPORTANCE_DEFAULT)

One notification, one job each: the ringing alert needs HIGH + setBypassDnd + full-screen intent, because it's time-critical and has to interrupt. The "return to call" notification shown while active is deliberately LOW — silent, no heads-up, just a status-bar affordance, because the call is already answered and doesn't need to demand attention again. The post-call missed/blocked notification is DEFAULT — visible, but not urgent enough to bypass Do Not Disturb. Picking one importance for all three would either make the ringing alert too quiet or the post-call summary too loud.

Intermediate CallStyle — the API real dialers use

IncomingCallNotifier.kt

NotificationCompat.Builder(context, CHANNEL_ID)
    .setFullScreenIntent(fullScreenPendingIntent, true)
    .setStyle(
        NotificationCompat.CallStyle.forIncomingCall(caller, declinePendingIntent, answerPendingIntent),
    )
    .build()

CallStyle (androidx.core 1.10+) gives you the system's own big Answer/Decline layout — the same chrome the Phone app itself uses — instead of hand-rolling notification actions that look like a generic app alert. forOngoingCall() is the equivalent for the active-call notification, with a single Hang Up action.

Advanced Wiring notification buttons back into the call

Tapping Answer/Decline/Hang Up on a notification doesn't run inside an Activity — there's no UI to hold a click listener. The action has to travel through a PendingIntent to something that can run headless:

CallActionReceiver.kt

class CallActionReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        when (intent.action) {
            ACTION_ANSWER -> InCallState.answer()
            ACTION_DECLINE -> InCallState.decline()
            ACTION_HANG_UP -> InCallState.hangUp()
        }
        IncomingCallNotifier.cancel(context)
    }
}
Why this works without an Activity

InCallState is a plain Kotlin singleton holding the live android.telecom.Call reference — same process, same object, regardless of whether the caller is InCallActivity's buttons or this receiver. The BroadcastReceiver is just a second entry point into the same state.

Intermediate Permission UX: detect and deep-link, don't ask once and go quiet

A single requestPermission() call handles the happy path. It says nothing about what happens when the user taps Deny, or later revokes the permission from system Settings — both cases where the feature just silently stops working with zero signal. The fix tracks real state and surfaces it:

MainActivity.kt — refreshed on launch and on every resume

private fun refreshPermissionStatus() {
    notificationsPermissionGranted = ContextCompat.checkSelfPermission(...) == GRANTED
    fullScreenIntentAllowed = Build.VERSION.SDK_INT < UPSIDE_DOWN_CAKE ||
        getSystemService(NotificationManager::class.java).canUseFullScreenIntent()
    callPhonePermissionGranted = ContextCompat.checkSelfPermission(...) == GRANTED
}

Settings then shows a warning card per broken permission, each with a button to the specific system screen that fixes it — ACTION_APP_NOTIFICATION_SETTINGS, ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT (API 34+, since users can revoke this independently of notifications), or ACTION_APPLICATION_DETAILS_SETTINGS — instead of one generic "open Settings" link.

Case Study: The Auto-Responder Audio Ceiling

The auto-responder plays TTS/MediaPlayer audio with AudioAttributes.USAGE_VOICE_COMMUNICATION, hoping Android mixes it into the live call's uplink so the caller hears it. This is the exact same technique call-recorder and IVR/auto-attendant apps have used for years — and exactly what Google and OEMs have been hardening against at the audio-HAL level on newer Android versions, as an anti-wiretapping measure. Verified live on a Motorola razr running Android 16: this is a real, current-generation device where that hardening plausibly applies.

Why no code fix exists

there is no public Android API that grants a non-privileged third-party app guaranteed injection into a live cellular call's uplink. Forcing AudioManager.mode/routing calls during a Telecom-managed call is explicitly discouraged and risks breaking the user's actual call audio — a far worse failure than a silent auto-responder.

The right fix was honest UI, not more code: sharpen the existing experimental-badge string to explain why ("depends on your phone letting call audio through; many newer Android versions block it") instead of chasing a workaround that either doesn't exist or actively risks the live call. Recognizing a platform ceiling — and saying so in the UI — is sometimes the correct engineering deliverable.

Key Takeaways

  • Background-activity-launch restrictions mean a ringing call needs a full-screen-intent notification, not just startActivity()
  • Match notification importance to urgency per channel — HIGH only for what truly needs to interrupt
  • CallStyle gives you the system's own call UI chrome for free
  • Notification button actions need a BroadcastReceiver + PendingIntent — there's no Activity to hold the click
  • Track real permission state and deep-link to the specific fix — "ask once, go silent forever" is a UX bug
  • Some limitations are the platform's, not yours — recognize the ceiling instead of writing risky code to route around it
Check your understanding (4 questions)

1. Why does startActivity() from onCallAdded() fail to show UI when the phone is locked?

Since Android 10, apps can't launch activities from the background without an active user-interaction token. A call ringing while the screen is off/locked is exactly the background case Android restricts — the launch is silently dropped, not delayed.

2. Why are the three notification channels (incoming, ongoing, history) given different importance levels instead of all HIGH?

Only the ringing alert is time-critical enough to justify HIGH + bypassing Do Not Disturb. The ongoing-call notification is just a status affordance for an already-answered call (LOW, silent), and the post-call summary is informational (DEFAULT). Making them all HIGH would make routine notifications as disruptive as an actual ring.

3. Why does a notification button (Answer/Decline/Hang Up) need a BroadcastReceiver instead of just calling a function directly?

A notification isn't hosted by your Activity — there's no live UI to attach a click listener to. The action has to be a PendingIntent the system can fire independently, and a BroadcastReceiver is the headless entry point that receives it and mutates the same in-process InCallState the Activity's own buttons would.

4. Why wasn't the auto-responder's call-audio problem fixed with code?

Injecting audio into a live cellular call's uplink from a third-party app is an OEM-dependent trick, not a supported public API, and is increasingly blocked at the audio-HAL level as anti-wiretapping hardening. The alternative — forcing AudioManager routing during a Telecom-managed call — risks breaking the user's real call audio, a worse outcome than a silent auto-responder. The honest fix was clearer in-app messaging about the limitation, not a workaround.

16Extending a Precedence Engine Safely

A feature request that sounds like one sentence — "let repeated callers through" — touches the resolver, the database schema, an async-to-sync UI handoff, and a notification, and every one of those layers has a wrong place to put the change. This module is a single feature traced end-to-end through all four, including a real migration-tooling gap discovered along the way.

Learning Objectives

  • Add a new branch to an existing precedence chain without reordering it
  • Recognize why "block after N attempts" and "allow after N attempts" need opposite scoping rules
  • Understand why SQLite can't ALTER a CHECK constraint, and the rebuild-table migration pattern that works around it
  • Thread a value computed asynchronously (a rule decision) into UI that's already showing
  • Prefer reusing an existing function's shape over inventing a new one
  • Know the difference between "the build is green" and "every dev-time safety net actually ran"

Beginner The problem with a binary default action

defaultAction = Block is one bit: match no rule, get blocked. That's fine for actual spam, but it can't distinguish a robocaller from an old friend calling from a number you never saved. The feature: if an otherwise-unrecognized number retries enough times, let the next attempt through — but only that number, only after real persistence, and never for a number the app has already positively identified as spam.

Intermediate One new branch, at the end of the chain, on purpose

RulePrecedenceResolver.kt — step 8, the only place this can live

// 8. Default: honor the user's chosen default action. BLOCK gets one more check first
return when (context.defaultAction) {
    DefaultAction.BLOCK ->
        if (context.repeatedAttemptsBypassCount > 0 &&
            context.recentAttemptsForNumber >= context.repeatedAttemptsBypassCount
        ) RuleDecision.AllowedAfterRepeatedAttempts(context.recentAttemptsForNumber)
        else RuleDecision.DefaultBlock
    DefaultAction.ASK -> RuleDecision.PendingReview
    DefaultAction.ALLOW -> RuleDecision.DefaultAllow
}
Why step 8 and nowhere earlier

manual block, pattern, country, spam, action-rule, and schedule checks (steps 1-7) all return before this code ever runs. That's not incidental — it's the entire point. Retrying is a robocall hallmark, so if the bypass were checked before the spam-pattern step, a number the app had already flagged as spam could talk its way back in just by calling more. Placing the new logic at the literal end of the existing chain, instead of threading a bypass check into every earlier branch, means the precedence order itself — not a separate flag on each rule type — is what protects real spam blocking. This mirrors ActionRule's "block after N attempts" (Chapter 10) almost exactly, just inverted: same attempt-tracking table, opposite conclusion, and deliberately a different point in the chain.

Intermediate SQLite can't ALTER a CHECK constraint

CallLogEntry.rule_type is constrained to a fixed list of tags. Adding REPEATED_ALLOWED to that list sounds like ALTER TABLE ... ADD CONSTRAINT — except SQLite has no such statement. The only way to change a CHECK is to rebuild the table:

The rebuild pattern — the shape every rule_type migration used

CREATE TABLE CallLogEntry_new (
    ...
    rule_type TEXT CHECK (rule_type IN ('MANUAL', ..., 'REPEATED_ALLOWED', NULL))
);
INSERT INTO CallLogEntry_new SELECT ... FROM CallLogEntry;
DROP TABLE CallLogEntry;
ALTER TABLE CallLogEntry_new RENAME TO CallLogEntry;

Create a shadow table with the new constraint, copy every row across, drop the old table, rename the shadow into place. SQLDelight's verifyMigrations build check replays every .sqm file in order on top of the snapshot baseline in databases/ and diffs the result against AppDatabase.sq's CREATE TABLE — if they don't match bit-for-bit, the build fails before a mismatched migration ever ships. Regenerate the snapshot with ./gradlew :shared:generateCommonMainAppDatabaseSchema whenever you cut a new baseline.

Case Study: A Broken Safety Net Nobody Noticed

Running verifyMigrations directly (not through the usual ./gradlew test/check chain) surfaced a pre-existing failure — duplicate column name: pattern_id. An early pass blamed a single missing snapshot file and concluded the schema itself was fine. That conclusion was wrong, and it is worth keeping the mistake visible.

What was actually wrong, in three layers:

  1. schemaOutputDirectory was never configured, so nothing regenerated the snapshots. The committed ones (1.db through 5.db) sat loose in the sqldelight source root and stopped at version 5 while migrations went on to 7.
  2. Replaying 5.sqm onto a snapshot that already carried the column produced the duplicate column name error — a symptom of the stale baseline, not of the migration.
  3. Once a correct baseline was rebuilt, the check failed again on something real: 5.sqm ran ALTER TABLE ActionRule ADD COLUMN pattern_id INTEGER, while AppDatabase.sq declares pattern_id INTEGER REFERENCES PatternRule(id). SQLite cannot add a foreign key through ALTER TABLE, so an upgraded database and a freshly installed one genuinely had different schemas. The safety net was broken and it was also right.

On top of all three, ci.yml ran ktlintCheck, assembleDebug, testDebugUnitTest and the iOS test task — none of which depend on verifySqlDelightMigration. The check had never run in CI even once.

The lesson: a dev-time safety net can quietly stop running, and a green CI history proves nothing about a check that was never wired into the graph it looks like it belongs to. The second lesson is sharper — when a check fails and you can't immediately explain it, "the tool is misconfigured" and "the code is broken" are not mutually exclusive. Fix the configuration first, then re-run, because a misconfigured check hides real findings behind fake ones. Here the fix was to configure schemaOutputDirectory, squash the seven now-userless migrations into a single databases/1.db baseline, and add the task to CI so it can never silently stop running again.

Advanced Threading an async decision into UI that's already on screen

The rule decision resolves inside a coroutine, seconds after the ringing screen is already showing — there's no prop to just pass it in. InCallState already exists as exactly this kind of bridge (Chapter 09), so the fix is one more field and one more setter on a pattern already proven, not new plumbing:

InCallState.kt

data class UiState(val number: String, val phase: CallUiPhase, val repeatedCallAttempts: Int? = null)
   
fun setRepeatedCallAttempts(attempts: Int) {
    _state.value = _state.value?.copy(repeatedCallAttempts = attempts)
}

Because CallScreen already collects InCallState.state as a StateFlow, calling setRepeatedCallAttempts() from the Telecom service — well after the screen first composed — recomposes it automatically with the new subtitle. The async result and the already-rendered UI meet through the same reactive state object, no callback or event bus required.

Advanced The best new code is the code you don't write

PassthroughInCallService.kt

if (settingsRepository.notificationsEnabled.value) {
    IncomingCallNotifier.notifyCallResult(
        this, number, R.string.notification_repeated_caller_title, decision.blockReason,
    )
}

notifyCallResult() already existed for post-call missed/blocked notifications (Chapter 15) — non-full-screen, auto-cancel, history channel. The repeated-caller notification needed exactly that shape, so it reuses the function verbatim with a new title string instead of a new method. Before writing a new notification builder, the question worth asking is whether an existing one already has the right shape — here it did.

Case Study: When combine() Runs Out of Overloads

SettingsViewModel already combined 5 flows of different types into one UiState — kotlinx.coroutines.flow.combine()'s typed overloads stop at 5. Adding a 6th setting doesn't mean switching to the untyped vararg Array<T> form (which needs every flow to share a type): chaining a plain two-argument combine() on top of the existing one composes cleanly instead —

combine(a, b, c, d, e) { ... }.combine(f) { partial, f -> partial.copy(newField = f) }

Composing two small typed operators beat forcing one large untyped one.

Case Study: The Allowlist That Did Not Know Your Contacts

Every comparison in the engine went through one function:

fun normalizeForComparison(number: String): String = number.filter { it.isDigit() }

People save contacts the way they dial them — 611 99 88 77 — and Telecom hands over +34611998877. Those normalise to 611998877 and 34611998877, which are not equal. The reported symptom was cosmetic: the call log showed bare numbers for people who were in the address book. The actual defect was not:

val mergedAllowlist = normalizedAllowlist + normalizedContacts

A contact saved in national format was not in the allowlist, so "your contacts always come through" quietly failed for them and quiet hours, a country rule or the default action could block a real person. Since most people save contacts nationally, that was the common case, not the edge.

Gotcha

The incoming-call notification showed the right name the whole time, because that path uses ContactsContract.PhoneLookup and gets the platform's own fuzzy matching for free. One app, two number-matching implementations, disagreeing — and the correct one was the one nobody had written.

The obvious fix, matching on a digit suffix the way PhoneNumberUtils.compare does, trades a correctness bug for a security-shaped one: this function guards blocking decisions, and a 7-digit tail is a coincidence a stranger can share. The obvious alternative — canonicalising national numbers to E.164 with a default region — needs a SIM/locale lookup, an ISO-to-dialling-code table the app does not have, and a trunk-prefix rule that is country-specific: dropping a leading zero is right for the UK and wrong for Italy, whose E.164 form keeps it.

The way out was to stop guessing: an international number already states its own country code, so stripping it yields exactly the national form a contact card holds. No region required.

Contrast

The first implementation intersected a set of keys per number, and a test caught what review had not: +34611998877 and +51611998877 both emit the national key 611998877 and so matched. When both sides state a country, the codes are known facts and must decide. The national form may only bridge two numbers when at least one of them is silent about its country — an asymmetry a flat key set cannot express, which is why the comparison is pairwise.

Then the Italy case failed, because the weak path reduced each side to one string and dropped the trunk zero it needed. Intersecting candidate sets — digits and national form — satisfies both countries at once. Two design errors, both found by tests written before the code was trusted.

Verified

The four resolver tests were watched failing against the old comparison first, with the negative case passing throughout so the suite could not be trivially red. Then installed on an emulator with two contacts deliberately saved in different formats: the national one now renders its name, the international one still does, and numbers with no contact still render as numbers.

Why no existing test caught it: every one of them used the same format on both sides of the comparison.

Key Takeaways

  • Phone-number equality is not string equality — a contact card and a Telecom handle describe the same person in different formats, and digit comparison silently treats them as different people
  • When a lookup can be wrong in two directions, ask which error is affordable: here a missed match hides a name, and a false match allowlists a stranger past every block rule
  • Two implementations of the same concept in one app will disagree — the notification path and the call-log path used different number matching, and only one was correct
  • A new precedence branch belongs at the specific step that matches its risk profile — not wherever is convenient to code
  • "Block after N" and "allow after N" reuse the same attempt-tracking data but must live at different, deliberately chosen points in precedence order
  • SQLite has no ALTER ... ADD CONSTRAINT — changing a CHECK means rebuild-copy-drop-rename, and a migration-verification task should replay every step and diff the result
  • A build task that's silently SKIPPED is not the same as a build task that passed — confirm what's actually wired into the graph
  • Bridge state objects (InCallState-style) let already-rendered UI pick up an async result with zero new plumbing
  • Before adding a new function, check whether an existing one already has the shape you need
  • When a typed API runs out of overloads, compose smaller typed calls instead of dropping to an untyped one
Check your understanding (4 questions)

1. Why does the repeated-caller bypass check live at step 8 (the default-action step) instead of being threaded into the pattern/spam/action-rule checks earlier in the chain?

Retrying is a common robocall behavior. If the bypass were checked earlier, a number already matched by a spam/pattern/action rule could use enough retries to talk its way past a block that was working correctly. Placing it only at the very end, after every real block rule has already had a chance to fire and return, means precedence order itself enforces that this bypass can only ever apply to numbers nothing else recognized as a threat.

2. Why can't rule_type's CHECK constraint just be altered in place to add a new allowed value?

SQLite has no ALTER TABLE syntax for modifying a CHECK constraint. The only way to change one is to create a new table with the desired constraint, copy every row from the old table into it, drop the old table, and rename the new one into its place — the pattern every rule_type migration in this project follows.

3. The migration-verification task failed when run directly, but had never failed in normal CI. What does that actually mean?

It means the task wasn't part of the task graph those normal runs exercised — confirmed via --dry-run showing it as SKIPPED — not that the migrations were secretly broken the whole time. A clean build/test history only proves the checks that actually ran passed; it says nothing about a safety net that was quietly disconnected.

4. Why did the repeated-caller notification call the existing notifyCallResult() instead of a new notification function?

notifyCallResult() already produced exactly the right notification shape for this case — non-full-screen, auto-cancel, posted on the history channel, same as the existing missed/blocked-call notifications. It needed a new title string, not new notification-building logic, so reusing it avoided duplicating code that already did the job.

17State Management — MVVM + MVI Done Right

Chapter 03 taught ViewModel + StateFlow<UiState> as the state bridge and called it done. An architecture review of all 8 ViewModels in this app found that pattern held up as MVVM — but a second, separate pattern was missing entirely: MVI's single inbound dispatch point. Worse, 4 of the 8 ViewModels had quietly drifted from the "one UiState" rule Chapter 03 itself taught, in ways nothing had caught because nothing was checking for it. This module is that review, and the fix, traced through the two hardest cases it turned up.

Learning Objectives

  • Name the difference between MVVM and MVI precisely enough to tell whether a codebase actually has both
  • Convert N public setter methods into one sealed Intent + one onIntent() dispatcher without touching leaf Composables
  • Recognize when a ViewModel genuinely needs an Intent type — and when adding one is pure ceremony
  • Handle a callback-shaped side effect (a platform share-sheet handoff) in an Intent-based world without breaking "intents are plain data"
  • Know when NOT to force a pattern: system callbacks are not user intents, even when they arrive on the same class

Beginner MVVM gets you unidirectional state. MVI adds unidirectional intent.

MVVM's contract, as already built in this app: a ViewModel exposes one immutable StateFlow<UiState>, mutates it privately, and Compose renders from it via collectAsState(). That part was already correct everywhere. What MVVM's contract does not specify is how the UI talks back to the ViewModel — and this app answered that with N public methods per screen (SettingsViewModel had 6: setBlockingEnabled, setAutoAllowContacts, setDefaultAction...). MVI adds exactly one more rule on top: every inbound user action is a value of one sealed type, dispatched through one function. State stays single and unidirectional either way — MVI is about making the input side just as single and typed as the output side already was.

Intermediate The pattern: one sealed Intent, one onIntent(), existing methods go private

HomeViewModel.kt — before and after are the same logic, different entry shape

sealed interface HomeIntent {
    data object Refresh : HomeIntent
    data class ToggleBlocking(val enabled: Boolean) : HomeIntent
}

fun onIntent(intent: HomeIntent) {
    when (intent) {
        HomeIntent.Refresh -> refresh()
        is HomeIntent.ToggleBlocking -> toggleBlocking(intent.enabled)
    }
}
// refresh() and toggleBlocking() keep their exact original bodies -- just private now

Where the wiring changes, and where it deliberately doesn't: AppNavHost.kt's route wiring goes from a method reference (homeViewModel::toggleBlocking) to a lambda that builds and dispatches an intent ({ homeViewModel.onIntent(HomeIntent.ToggleBlocking(it)) }). HomeScreen itself — the leaf Composable — does not change at all. It still takes a plain onToggleBlocking: (Boolean) -> Unit callback, with no idea an Intent type exists. That's deliberate: leaking ViewModel-shaped types into leaf Composables is its own anti-pattern (Chapter 03's UI-layer boundary), and confining the whole refactor to ViewModel files plus one navigation file is what kept an 8-ViewModel, app-wide change from also touching ten screen files.

Intermediate Case study: 11 StateFlows collapse into one UiState, 13 methods collapse into one onIntent()

BlockListViewModel backs all 6 block-list screens (hub + manual + allowlist + patterns + countries + schedules) from a single Koin-scoped instance that doesn't know which screen is asking — so it had accumulated 5 list StateFlows, 5 separately-collected count StateFlows, and a contactNames flow, with no aggregate UiState tying them together. The counts were the tell: each one was a MutableStateFlow updated by its own viewModelScope.launch { list.collect { ... } } block in init — five nearly-identical collectors doing by hand what a derived property does for free.

BlockListViewModel.kt — counts became computed properties, not collected state

data class BlockListUiState(
    val blockedNumbers: List<BlockedNumberEntry> = emptyList(),
    // ...4 more lists, contactNames...
) {
    val blockedCount: Int get() = blockedNumbers.size
    // ...4 more derived counts...
}

The 5 list flows combine via the same chained-combine() pattern Chapter 16 already established for exceeding the 5-flow typed-overload ceiling. The 13 mutation methods (addBlockedNumber, removeBlockedNumber, addPatternRule...) collapse into one BlockListIntent sealed type and one onIntent() — the single biggest before/after in this pass, and the case where MVI's value is least debatable: 13 near-identical public entry points is exactly the surface area a single typed dispatcher exists to remove.

Advanced When an Intent can't just carry a callback

BackupViewModel.exportJson(onResult: (String) -> Unit) took a UI-supplied callback so the exported JSON could reach a platform share-sheet Compose can't invoke directly. A sealed Intent case holding a function type would technically compile, but it breaks the actual point of MVI — intents are supposed to be inert data you can log, replay, or test by equality; a lambda inside one is neither.

BackupViewModel.kt — the result becomes a third effect case instead of a parameter

sealed interface BackupEffect {
    data class Exported(val json: String) : BackupEffect
    data class Success(val message: String) : BackupEffect
    data class Failure(val message: String) : BackupEffect
}
sealed interface BackupIntent { data object Export : BackupIntent /* ... */ }

onIntent(BackupIntent.Export) now sends Exported(json) down the same effect channel Success/Failure already used, and BackupScreen gained one more branch in its existing effect-collecting LaunchedEffect to call a new onExportReady callback. The general rule this generalizes to: when a mutation's "result" needs to reach something outside the state model — a share sheet, a file picker, a toast — that result is a one-time effect, not an intent parameter and not a UiState field.

Case Study: The ViewModel That Deliberately Didn't Get an Intent Type

InCallState — the Telecom bridge singleton from Chapter 09 and 16 — was reviewed for this same treatment and left alone on purpose. Its methods split into two categories that look identical in code but aren't: answer()/decline()/hangUp() are real user intents, dispatched from a tap in CallScreen. attach()/detach() are Android Telecom system lifecycle callbacks, invoked by PassthroughInCallService when the OS hands the app a call — no user asked for those to happen. Folding both into one sealed interface CallIntent would misrepresent a system event as something the user chose, which is a correctness problem in an MVI codebase, not just a style one: code reading "the user's intent was Attach" would be lying. InCallState already does the MVVM half correctly — one encapsulated StateFlow<UiState?> — and that's as far as this pattern should go here.

The same instinct killed a second, smaller addition: StatsViewModel has exactly one method, refresh(), and zero external call sites dispatch it (it only ever runs from its own init). A sealed interface StatsIntent { data object Refresh : StatsIntent } would compile and look consistent with every other VM — and add nothing. It stayed a plain private-called method. MVI earns its ceremony when there's more than one thing to dispatch and more than one place dispatching it; a single VM-internal call isn't that.

Key Takeaways

  • MVVM (single StateFlow<UiState> out) and MVI (single sealed Intent + onIntent() in) are two separate rules — a codebase can have one without the other, and this one did
  • Leaf Composables shouldn't know an Intent type exists; only the ViewModel and its navigation-layer wiring should
  • Derived properties (counts from list.size) beat separately-collected StateFlows for anything computable from state already held
  • An Intent that needs to carry a callback is a sign the "result" belongs in a one-time Effect instead
  • System lifecycle callbacks are not user intents, even on a class that also has real ones — don't fold them together for pattern consistency
  • A one-case sealed class with no external dispatcher is ceremony, not MVI — skip it
Check your understanding (4 questions)

That pattern covers the outbound half only — state flowing from ViewModel to UI, which is the MVVM contract. MVI additionally requires the inbound half (user actions flowing from UI to ViewModel) to be a single typed sealed value dispatched through one function. This app had the first half everywhere and the second half nowhere — every VM took N separate public methods instead of one Intent type.

18Test Doubles at Scale — One Fake per Interface

Chapter 12 chose hand-written fakes over MockK, for a good reason: MockK doesn't run on Kotlin/Native, and this project's tests have to pass on both Android and the iOS simulator. That decision was right, and it has a bill that arrives later. By the time this app had 176 tests, 470 of its 3061 test source lines — 15% — were Fake* class bodies, and three of those fakes existed in two, three, and four near-identical copies. This module is the cleanup: what to consolidate, what to deliberately leave duplicated, and the two surprises that fell out of doing it.

Learning Objectives

  • Decide which test doubles are worth consolidating and which are cheaper left duplicated
  • Place a shared fake so both commonTest and androidUnitTest can use it, and know why internal works there
  • Explain the Kotlin "private top-level class" redeclaration trap that duplicate fakes hit in KMP test source sets
  • Design one fake that satisfies call sites which previously needed different fakes, without silently changing what a test asserts
  • Recognize a test that only exercises its own fake and asserts nothing about production code

Beginner Duplication in tests is real duplication — with one exception

The usual defense of copy-pasted test helpers is that tests should be readable in isolation. That holds for small doubles. It stops holding when the interface is big: RuleRepository has 64 members, so each copy of FakeRuleRepository was ~115 lines of override fun ... {}, and adding one method to the interface meant editing both copies to keep the build green. The measured split before this pass:

FakeRuleRepository2229Consolidate
FakeSettingsRepository5104Consolidate
FakeCallLogRepository376Consolidate
FakeContactsGateway, FakeGateway3 + 25–10 eachLeave alone

The exception is the bottom row. A ContactsGateway fake is three one-line overrides; a reader scanning the test file sees exactly what it returns without opening another file, and the interface is stable enough that a shared copy would rarely save an edit. Consolidation is justified by edit-point count and body size, not by the mere fact that two files declare the same name.

Intermediate Where the shared fake goes, and why internal reaches androidUnitTest

The three shared fakes now live once each in shared/src/commonTest/kotlin/.../app/testing/, declared internal. That single placement covers every consumer: androidUnitTest dependsOn commonTest in the default KMP hierarchy, and internal is module-scoped, so a Robolectric Compose test in androidUnitTest imports the same class a pure-Kotlin ViewModel test in commonTest does. Nothing in build.gradle.kts had to change to make that work.

shared/src/commonTest/kotlin/.../app/testing/FakeSettingsRepository.kt

internal class FakeSettingsRepository(
    override val blockingEnabled: MutableStateFlow<Boolean> = MutableStateFlow(true),
    // ...one constructor parameter per flow, each with a default...
    override val welcomeShown: Boolean = false,
) : SettingsRepository {
    override suspend fun setBlockingEnabled(enabled: Boolean) {
        blockingEnabled.value = enabled   // write-through, not a no-op
    }
}

Every flow being a constructor parameter with a default is what let one class replace five: a test that needs a starting value passes it (FakeSettingsRepository(defaultAction = MutableStateFlow(DefaultAction.BLOCK))), a test that doesn't passes nothing, and a test that wants to observe a write keeps the handle it passed in. Adding a sixth setting to SettingsRepository is now one new parameter and one new setter — the project's own corta-spam-add-setting runbook had listed five test files to edit for that, and now lists one.

Intermediate The redeclaration trap that duplicate fakes were quietly working around

Two of the duplicated fakes had a naming tell: the androidUnitTest copy was called FakeScreenTestSettingsRepository, not FakeSettingsRepository. That prefix wasn't a style choice. commonTest and androidUnitTest compile into one JVM compilation, and Kotlin's private on a top-level class restricts visibility but does not change the class's binary name — so two files in the same package each declaring private class FakeSettingsRepository fail with a JVM Redeclaration error. The prefix was a workaround for a problem that only existed because the fake was duplicated. One shared class in a testing package removes the workaround and the trap together.

Advanced Merging two fakes that disagreed about how state is read

The two FakeRuleRepository copies weren't just duplicates — they modeled the repository differently. The BlockList copy was flow-backed (MutableStateFlow fields, because the ViewModel collects blockedNumbers()). The rule-engine copy was snapshot-backed (var blockedEntries, because EvaluateIncomingCallUseCase calls the suspend accessor blockedNumberEntries()). A merged fake has to serve both without making a test seed the same data twice.

FakeRuleRepository.kt — one source of truth, two read paths

val blockedNumbersFlow = MutableStateFlow(emptyList<BlockedNumberEntry>())

// reactive path -- what BlockListViewModel collects
override fun blockedNumbers() = blockedNumbersFlow

// snapshot path -- what the rule engine calls
override suspend fun blockedNumberEntries() = blockedNumbersFlow.value

// derived, so seeding the flow is enough for the resolver too
override suspend fun enabledCountryRules() = countryRulesFlow.value.filter { it.enabled }

One assignment (blockedNumbersFlow.value = ...) now drives both. Writes stay recorded-not-applied on purpose: addBlockedNumber() appends to an addBlockedNumberCalls list rather than mutating the flow, because the tests that call it assert the ViewModel delegated, and a fake that also applied the write would let a test pass while the real repository call was missing.

Case Study: The Test That Only Tested Its Own Fake

SettingsRepositoryTest.kt — 78 lines, five green tests, sitting in the settings package next to the class it appeared to cover. It never touched SqlSettingsRepository. Every one of its assertions ran against the fake declared at the top of the same file:

That is a test of kotlinx.coroutines, wearing the name of a repository test. It was invisible for months precisely because it was green and its filename read like coverage. Consolidation surfaced it: once the fake moved out of the file, what remained had nothing left to test. It became testing/FakeSettingsRepositoryTest.kt, rewritten to drive the shared fake through its setters — which is a genuinely useful test now, because every ViewModel test depends on those setters writing through. The honest part of the outcome: the real SqlSettingsRepository still has no test. The gap didn't appear in this refactor; it was always there, hidden behind a filename. Renaming the file made the gap visible instead of pretending it was covered.

A second trap, avoided by checking first: the four FakeSettingsRepository copies differed in exactly one way — some had setters that mutated the backing flow, others had setters that did nothing. Unifying on write-through would silently break any test asserting that a setter had no effect. Every call site was checked for that assertion before the merge, and none existed. If one had, the merged fake would have needed a constructor flag, not a judgment call — when consolidating doubles, the differences between copies are the specification, so read them before deleting them.

Key Takeaways

  • Hand-written fakes are the right call in KMP (MockK has no Kotlin/Native support) — the cost is duplication that must be managed deliberately
  • Consolidate a double when the interface is large or the copies are many; leave 5-line doubles local where an import would cost more reading than it saves
  • internal in commonTest is visible from androidUnitTest via the default dependsOn hierarchy — no Gradle change needed
  • Top-level private restricts visibility, not the JVM binary name — duplicate private fakes in one package collide, and name prefixes to dodge that are a duplication smell
  • One fake can serve a reactive and a snapshot read path by deriving the snapshot from the flow — seed once, both paths see it
  • Differences between copies of a fake encode real assumptions; audit them before unifying, or a test's meaning changes silently
  • A test file named after a production class can assert nothing about it — check what the assertions actually reach

19Testing Persistence Against a Real Database

Chapter 18 consolidated the fakes and, in passing, exposed something the fakes had been hiding: not one Sql* repository in this app had a dedicated test. Five classes held every byte that survives an app restart — settings, call log, auto-responder, spam flag, and the key-value store beneath them — and all five were untested. This module is that gap being closed, and the user-visible bug the very first pass of tests uncovered.

Learning Objectives

  • Decide when a fake is the wrong test double and only a real database engine will do
  • Place SQLite-backed tests correctly in a KMP module, and know why they can't be shared with iOS
  • Test a repository that hydrates once at construction — where "does this survive a restart?" needs a second instance
  • Use a test to prove every branch of a sealed decision type satisfies a database CHECK constraint
  • Handle the moment a new test disagrees with shipped behaviour: pin it, judge it, then fix it

Beginner When a fake stops being enough

A fake is a stand-in for a collaborator you're not testing. That's the right tool when you're testing a ViewModel: HomeViewModel shouldn't need SQLite to prove it maps stats into a UiState. But the moment the class is the persistence — SqlSettingsRepository, SqlCallLogRepository — a fake has nothing left to stand in for, and the interesting behaviour lives entirely in things a fake never reproduces: SQL CHECK constraints, strftime date arithmetic, INSERT OR REPLACE semantics, and what a value actually looks like when read back off disk. Those tests need a real engine.

shared/src/androidUnitTest/kotlin/.../app/testing/TestDatabase.kt

internal fun createTestDatabase(): AppDatabase {
    val driver = JdbcSqliteDriver(JdbcSqliteDriver.IN_MEMORY)
    AppDatabase.Schema.create(driver)
    return AppDatabase(driver)
}

Why androidUnitTest and not commonTest: JdbcSqliteDriver is JVM-only. There is no Kotlin/Native equivalent that runs in the shared test source set, so these tests are deliberately excluded from the iOS simulator run — the opposite of Chapter 12's default, and a real limit of the approach. The rule of thumb: logic tests go in commonTest and run everywhere; engine tests go in androidUnitTest and run on the JVM only.

Intermediate Testing a repository that hydrates once

SqlSettingsRepository reads the database exactly once, in init, into MutableStateFlows. Its flows are not backed by live queries. That single design fact dictates how it must be tested: calling a setter and reading the flow back only proves the in-memory field moved. Proving the value reached disk takes a second repository over the same database — which is exactly what an app restart is.

SqlSettingsRepositoryTest.kt — a second instance is the restart

val db = createTestDatabase()
val first = SqlSettingsRepository(db)
first.setDefaultAction(DefaultAction.ASK)

// A fresh instance re-runs init, re-reading from the same database
assertEquals(DefaultAction.ASK, SqlSettingsRepository(db).defaultAction.first())

The same structure makes a subtler property testable: two live instances over one database disagree, because neither observes the other's writes. That isn't a bug — it's safe only because SharedModule binds the repository as single<SettingsRepository>. A test asserting the disagreement documents the constraint, so a future change to factory { } fails loudly instead of producing a screen showing stale settings.

Advanced Proving a sealed type satisfies a CHECK constraint

Chapter 16 added REPEATED_ALLOWED to the CallLogEntry.rule_type CHECK constraint via a rebuild-table migration. That constraint and the RuleDecision sealed hierarchy are two lists that must stay in lockstep — and nothing enforced it. A new decision variant whose ruleTypeTag isn't in the constraint compiles cleanly and throws at runtime, on a real user's phone, at the moment a call is being logged.

SqlCallLogRepositoryTest.kt — one test covers the whole hierarchy

val decisions = listOf(
    RuleDecision.Allowlist(ruleId = 1, label = "Mom") to ("ALLOWED" to "CONTACTS"),
    RuleDecision.DefaultBlock to ("BLOCKED" to null),
    RuleDecision.PendingReview to ("ALLOWED" to "REVIEW"),

    repo.logCall("+3460000000$index", now + index, decision)  // throws if CHECK rejects the tag

The insert itself is the assertion — a tag outside the constraint fails the statement. The explicit assertEquals on action and rule type then pins the mapping, so a decision silently switching from BLOCKED to ALLOWED is caught too.

Case Study: The Chart That Never Said "Today"

Writing an assertion for blockedByDay() meant reading it closely enough to predict its output — and the prediction didn't match the label. The old implementation walked forward from now - daysBack in 24-hour steps:

val cutoff = now - daysBack * dayMillis
(0 until daysBack).map { dayOffset ->
    val dayStart = cutoff + dayOffset * dayMillis   // newest bucket = [now-1d, now)
    val epochDay = dayStart / dayMillis             // ...whose START is one day ago
    DayStat(dateLabel = dayLabel(epochDay), /* ... */)   // ...so the label is "Yesterday"
}.reversed()

The newest bucket held every blocked call from the last 24 hours — including one placed five seconds ago — but its label came from the bucket's start, one epoch-day back. No bucket was ever labelled "Today". StatsViewModel calls blockedByDay(7) and StatsScreen renders dateLabel verbatim, so every install shipped a Stats screen filing today's blocks under "Yesterday".

The fix anchors buckets to UTC midnight — the same boundary countBlockedCallsToday was already using:

val todayStart = (currentTimeMillis() / dayMillis) * dayMillis
(0 until daysBack).map { dayOffset ->
    val dayStart = todayStart - dayOffset * dayMillis
    // dayLabel() now yields "Today" for dayOffset 0, and no .reversed() is needed
}

That alignment buys an invariant the code could not previously satisfy: the chart's first bar and the "blocked today" stat now derive from one day boundary, so they cannot disagree. The new test asserts precisely that — assertEquals(repo.blockedStats().today, repo.blockedByDay(7).first().count). Note the sequencing: the test suite landed first, pinning the wrong behaviour with a comment naming it as suspect, and the fix landed in the next commit updating those assertions. Enshrining a bug in a green test without saying so is how bugs become "intended behaviour"; documenting it and fixing it next is how it stays a bug.

A second finding, deliberately not fixed: clearing the auto-responder script writes "", but KeyValueSettingsStore.readString treats a stored blank as "unset" and returns the default — so a restart resurrects the default greeting. In memory the field is empty; after restart it isn't. That one stayed documented rather than fixed, because readString is shared by three repositories and changing its fallback semantics is a wider decision than a one-line patch.

Key Takeaways

  • Fakes are for collaborators you aren't testing; a persistence class has no collaborator left to fake, so it needs a real engine
  • JdbcSqliteDriver is JVM-only — database tests live in androidUnitTest and knowingly skip the iOS run
  • A repository that hydrates in init can only be proven durable by constructing a second instance over the same database
  • Two live instances disagreeing is a DI constraint worth asserting, not just a quirk to remember
  • Round-trip every branch of a sealed type through the database when a CHECK constraint mirrors it — the insert is the assertion
  • When a new test disagrees with shipped behaviour, pin it with a comment naming the suspicion, then fix it in the next commit — never silently
  • Not every finding has to be fixed in the same pass; a shared primitive's semantics deserve their own decision

Intermediate Normalising away the information you need

The resolver reduced every incoming number to bare digits before consulting any rule:

shared/src/commonMain/kotlin/.../rules/RulePrecedenceResolver.kt
// before
val normalized = PhoneNumberParser.normalizeForComparison(number)  // digits only
val countryCode = parseCountryCode(normalized)
val result = context.spamProvider.lookup(normalized)

That is right for comparing against a number the user typed, where +34 600 123 456 and 0034600123456 should match. It is wrong for anything that needs to know whether the number was international at all.

Without the +, a national number is indistinguishable from an international one. 2125551234 is a Manhattan landline; its first three digits are also Morocco's country code. 912345678 is a Madrid landline; its first two are India's. Blocking either country quietly blocked an unrelated city.

shared/src/commonMain/kotlin/.../rules/PhoneNumberParser.kt
fun toE164OrNull(number: String): String? {
    val trimmed = number.trim()
    val digits = when {
        trimmed.startsWith("+")  -> normalizeForComparison(trimmed)
        trimmed.startsWith("00") -> normalizeForComparison(trimmed).drop(2)
        else -> return null      // national format carries no country at all
    }
    if (digits.isEmpty() || digits.length > MAX_E164_DIGITS) return null
    return "+$digits"
}
Why

Returning null rather than guessing is the whole fix. "I do not know which country this is" is a true and useful answer; "probably Morocco" is neither.

Intermediate A pattern that matched every number alive

Patterns are compared on digits, so a pattern containing none has an empty core — and an empty core satisfies startsWith, endsWith and contains for every number in existence. Typing * into the add-pattern dialog blocked the user's entire phone.

fun isUsablePattern(pattern: String): Boolean =
    PhoneNumberParser.normalizeForComparison(pattern.trim().trim('*')).isNotEmpty()
Gotcha

There was already a test covering this, named patternMatch_caseInsensitive. It asserted that the pattern "ABC*" matches "abc123" — and it passed, because "ABC*" matched everything. The test was observing the bug and calling it a feature. Pattern matching has no notion of case; there was nothing to be insensitive about.

Advanced Restoring a backup by disabling the wrong rule

The importer wrote a default row, then went looking for the row it had just written:

queries.insertPatternRule(entry.pattern, entry.label)
if (!entry.enabled) {
    val inserted = queries.selectAllPatternRules().executeAsList().lastOrNull()
    if (inserted != null) queries.togglePatternRule(0, inserted.id)
}

Read the query it calls: SELECT * FROM PatternRule ORDER BY created_at DESC, id DESC. Newest first. So lastOrNull() is the oldest row, not the newest. Every restore containing a disabled rule switched off an unrelated rule the user still wanted, silently.

The fix is to stop having a second step at all — insert the row with its real state in one statement:

shared/src/commonMain/sqldelight/.../AppDatabase.sq
insertPatternRuleFull:
INSERT INTO PatternRule(pattern, label, enabled, created_at) VALUES (?, ?, ?, ?);
Contrast

The obvious fix is firstOrNull(). It would have worked here and broken on CountryRule, which orders by country_name ASC — neither end of that list is the row you just inserted. "Find what I wrote" is the wrong question; not needing to ask it is the fix.

Three more problems fell out of the same rewrite. Counts came from a loop counter rather than affected rows, so re-importing your own backup — legitimately a no-op against INSERT OR IGNORE on a UNIQUE column — claimed it had added everything twice. created_at was parsed out of the file and then discarded, so restored rules came back in an order they had never been in. And an action rule's patternId pointed at an id from the exporting device, which on the importing device belongs to somebody else's pattern.

Advanced A manifest entry is a promise

androidApp/src/main/AndroidManifest.xml
<meta-data
    android:name="android.telecom.IN_CALL_SERVICE_RINGING"
    android:value="true" />

That tells Telecom the app plays the ringtone itself, so Telecom stops playing one. Nothing in the source ever did — no Ringtone, no MediaPlayer on the ring stream, no Vibrator. As the user's default dialer the app took every incoming call in silence.

Why

The declaration was kept rather than removed, because it is what makes a blocked call silent. Handing ringing back to the system would mean every spam call rings before it is rejected. Owning the ringer is the feature; not implementing it was the bug.

Order matters on this path. The ringer starts as soon as the call is ringing and stops when a block decision lands, not the other way round:

// Ring first, decide second. Evaluation touches the database and the contacts
// provider, and a caller must never be dropped into silence because that was slow.
ringer.start()
state.evaluation = serviceScope.launch { /* ...decide, then ringer.stop() */ }

Intermediate Testing the thing that was inert

Writing CallRinger closed the bug. It did not close the gap: for the next week the ringer had no test at all, because a ringtone lives inside MediaPlayer, Vibrator and an InCallService no unit test can construct. "Untestable" is how it got to ship empty in the first place.

The move is the one NotificationPolicy made in Chapter 23: take the decision out of the untestable class and leave the I/O behind.

androidApp/src/main/kotlin/.../RingerPolicy.kt
fun plan(ringerMode: Int, vibrateWhileRinging: Boolean): RingerPlan =
    when (ringerMode) {
        AudioManager.RINGER_MODE_SILENT -> RingerPlan(playRingtone = false, vibrate = false)
        AudioManager.RINGER_MODE_VIBRATE -> RingerPlan(playRingtone = false, vibrate = true)
        else -> RingerPlan(playRingtone = true, vibrate = vibrateWhileRinging)
    }

Two details in that when are decisions, not mechanics. Vibrate mode ignores vibrateWhileRinging — there the vibration is the ring, so the setting that suppresses buzzing-alongside-a-ringtone must not reach it. And an unrecognised mode falls into else and rings: the app told Telecom to stop ringing on its behalf, so an unexpected value from AudioManager must never be the reason a call arrives silent.

Gotcha

A policy object is only half the work, and the other half is the failure this whole chapter is about: a perfect plan that nobody consumes leaves the phone exactly as silent as no plan at all. So a second test drives the real CallRinger under Robolectric and asserts the vibrator is actually running — the decision, and the fact that something acts on it, are separate claims needing separate tests.

Then the tests were checked the way this project checks every regression test — by breaking the thing they cover. Stubbing out the startVibration() call failed exactly three of the six:

CallRingerTest > vibrate mode actually vibrates FAILED
CallRingerTest > normal mode vibrates alongside the ringtone FAILED
CallRingerTest > stop cancels a vibration that start began FAILED

The other three — silent mode does not vibrate, stop() on a ringer that never started, a double start() — stayed green against a ringer that did nothing whatsoever. That is the tell. Every one of them asserts an absence, and an absence assertion is satisfied by a feature that was never built.

Contrast

Had the original inert ringer been "covered" by tests, they would have been absence tests — no crash, no exception, silent mode stays silent — and all of them would have passed on the empty implementation. Six of the audit's findings shipped with green suites. Positive assertions are what separate a test suite from a formality.

Scope

What these still do not prove: that a ringtone is audible. That needs a real MediaPlayer, a real ringtone URI and a real audio HAL, and the OEM behaviour it depends on is precisely what an emulator cannot stand in for. A device script covers it, and saying so in the test file is part of the test — a reader who thinks ringing is now covered is worse off than one who knows it is half-covered.

Advanced The check that measures something other than what it claims

Three device scripts in this repo were written to catch what unit tests cannot. On 2026-08-13 all three were found reporting something other than what they measured, and two had been doing it since the day they were written.

The loudest was rule_matrix_test.sh, which drives 13 block/allow scenarios with real calls and came back 4 failed. Its assertion read the newest call-log row after a fixed sleep:

// Wrong: whatever row is newest, not the row THIS call produced.
sleep 5; ...; sleep 2
SELECT action, rule_type FROM CallLogEntry ORDER BY id DESC LIMIT 1

When a write landed slower than the sleep, the scenario read the previous scenario's row. The failure output said so out loud, for anyone reading it as evidence rather than as a verdict:

FAIL  a prefix on the bundled spam list  expected BLOCKED/SPAM,     got BLOCKED/COUNTRY
FAIL  a manually allowlisted number      expected ALLOWED/CONTACTS, got BLOCKED/SPAM

Scenario five reported SPAM — which is scenario four's correct result, arriving one step late. The spam rule had worked. Recording the max row id before dialling and polling for a row that beats it turns "the newest row" into "this call's row".

Gotcha

This defect is far more dangerous as a false pass than as a false failure. Any run where two consecutive scenarios expect the same outcome reads a stale row and calls it a match. The suite had been recorded as "13/13 on real calls" — a number that, on this harness, could not distinguish a passing engine from a lagging one.

The second failure was the regression test for contact matching, and it was the test data:

// The digit class stops at the first space.
sed -n 's/.*data1=\([0-9+][0-9]*\).*/\1/p'
// contact "611 99 88 77"  ->  "611"  ->  dials +34611

+34611 is five digits, and PhoneNumberParser requires code.length + 4 before it will read 34 as a country code. So the engine correctly refused to match, and the harness reported a contact-matching regression that did not exist. Dialling the whole number, it passes — 13 of 13.

Why

The instinct on seeing four red lines is to go looking in the rule engine. The engine was innocent on all four. What made the difference was reading the reported values rather than the pass/fail column: a scenario reporting its neighbour's answer is not a wrong rule, it is a wrong read.

Worst of the three, because it was silent: ring_test.sh watch exists specifically because an emulator cannot settle whether an OEM lets the app ring. It resolved the app's uid like this:

On a razr 50 ultra it exited "org.carlospinan.cortaspam is not installed" while the app was installed, running, and holding the dialer role. The mode written for real hardware had never once run on real hardware — a large part of why ringing sat "verified on emulator only" for two weeks with nobody able to say why the device run never happened.

Scope

And device_check.sh ran its crash check with logcat -d over the device's whole persistent buffer — no logcat -c first, no package filter, then exit 1. On a phone somebody actually uses it matched a two-day-old trace and a fatal belonging to an entirely unrelated app, and quit before the schema and index assertions that are the script's entire purpose. A verification script is code. Nothing in this project was testing it.

Advanced When lint has never run, "no lint errors" means nothing

Gotcha

Advanced The bug the device found and the tests could not

A SQLDelight migration file N.sqm takes the schema from version N to N+1. The squashed baseline in databases/1.db is version 1, so the first migration on top of it is 1.sqm. It was named 2.sqm.

Verified

Left deliberately unfixed: InCallState still tracks a single call. Multi-call UI is a feature, not a defect. Check yourself

1. A component test for the spam provider passed while the feature was completely dead in production. What kind of test would have caught it?

A test through the real entry point — RulePrecedenceResolver.evaluate() with the provider wired in — rather than calling provider.lookup() directly. The bug was not in the provider or in the resolver; it was in the shape of the value passed between them, which only an integration-level test observes.

2. Why does toE164OrNull return null for a national-format number instead of assuming a default country?

Because the information genuinely is not there. Assuming the device's own country would be right most of the time and silently wrong while roaming or for a ported number — and this value decides whether a call is rejected. "Unknown" is a correct answer that the caller can handle; a confident guess is not.

3. The importer used lastOrNull() on a created_at DESC, id DESC query to find the row it had just inserted. Why is firstOrNull() not the fix?

It works for that one query and breaks on CountryRule, which orders by country_name ASC — the row just inserted is at neither end. The real fix is to insert the row in its final state so there is nothing to find afterwards.

4. Why keep IN_CALL_SERVICE_RINGING and write a ringer, rather than removing the declaration and letting the system ring?

Because owning the ringer is what allows a blocked call to be silent. If the system rings, every spam call audibly rings before it is rejected — which is most of what the app exists to prevent.

5. Android Lint failed with a Kotlin metadata version error. Why is disabling lint the wrong response?

The message is not a finding about the code, it is AGP's bundled analyser being older than the compiler. Disabling it converts a fixable toolchain mismatch into a permanent blind spot — and on the first run after the AGP bump, lint found five real defects that had been invisible for the project's whole life.

6. Every automated check passed on a migration numbered 2.sqm when it should have been 1.sqm. Why?

Because the migration still ran: the generated guard is oldVersion <= 2 && newVersion > 2, and a device at version 1 satisfies it. verifySqlDelightMigration checks that replaying the files reaches the current schema, which it did. What was wrong was the version number — visible only by reading PRAGMA user_version off a real device.

7. Six tests cover the ringer. Stubbing out the vibration call failed only three of them. What does that tell you about the other three?

That they assert absences — silent mode does not vibrate, stop() is safe when nothing started, a second start() does not stack — and an absence assertion is satisfied by a feature that was never implemented. All three pass against a ringer that does nothing at all, which is exactly the state this app shipped in. They are worth keeping, but only the positive assertions ("vibrate mode actually vibrates") can distinguish a working ringer from an empty one. Breaking the code and watching which tests notice is how you find out which kind you wrote.

8. A device suite reports 4 failures out of 13, and one line reads expected BLOCKED/SPAM, got BLOCKED/COUNTRY while the next reads expected ALLOWED/CONTACTS, got BLOCKED/SPAM. Where is the bug?

In the harness, not the rule engine. Each scenario is reporting the previous scenario's result — the assertion read ORDER BY id DESC LIMIT 1 after a fixed sleep, so a write that landed late left it reading a stale row. Scenario five reporting SPAM is in fact scenario four's correct answer arriving one step behind. Reading the reported values instead of the pass/fail column is what shows this; a wrong rule and a wrong read look identical in the red column. The same defect also produces false passes whenever two consecutive scenarios expect the same outcome, which makes it a correctness bug rather than a flake.

21When the Platform Says No

Two things collided in one day: a Google Play policy rejection that was wrong, and a feature that four different user-facing surfaces claimed to have and no line of code implemented. Both are about the same discipline — checking whether the thing you assert is actually true.

Learning Objectives

  • Verify a platform policy against your own manifest before complying with a rejection
  • Recognise a claim in a privacy policy as a promise the code must keep
  • Understand which audio sources Android reserves for privileged apps, and design honestly around that
  • Attach a file to a database row without leaking it when the row is deleted
  • Return an inserted row id safely when concurrent writes are possible

Beginner A rejection that was wrong

Play rejected version code 1: "Full-Screen Intent Permission policy: Permission use is not directly related to your app's core purpose." The prescribed fix was to remove USE_FULL_SCREEN_INTENT from every version code.

Reading the actual policy changed the answer. It auto-grants the permission when core functionality is setting an alarm or receiving phone or video calls. The manifest already settles which of those applies:

androidApp/src/main/AndroidManifest.xml
<service android:name=".telecom.PassthroughInCallService"
    android:permission="android.permission.BIND_INCALL_SERVICE">
    <meta-data android:name="android.telecom.IN_CALL_SERVICE_UI" android:value="true" />
    <meta-data android:name="android.telecom.IN_CALL_SERVICE_RINGING" android:value="true" />
</service>

IN_CALL_SERVICE_RINGING is not a preference. It tells Telecom to stop ringing because this app has taken that responsibility. An app the OS has made responsible for presenting incoming calls is, definitionally, an app whose core function is receiving calls.

Gotcha

A store's "How to fix" section describes the compliance path. It is not a finding that you are guilty. Following it and appealing at the same time destroys the appeal — you would be conceding the permission is not core while arguing that it is.

Why

The diagnosis at the time: the Play Console full-screen-intent declaration form had never been submitted, so review judged the permission against the store listing alone — and the listing led with "Block calls by your own rules", naming the dialer role once, in a closing caveat about permissions. The APK said phone app; the listing said utility. Both halves were fixed. It was not enough — see below.

Advanced Being right, twice, and still rejected

Version code 3 went up with the declaration form submitted first, deliberately, and with listing copy rewritten to open with "phone app" in both languages. Play rejected it with the identical finding. Every fact in the section above was still true, and the app was still not published.

The mistake was reading the declaration form as a single question. It has two:

QuestionAnsweredLoad-bearing?
What is the core functionality of your app?Making and receiving callsTrue, and never disputed
Do you want this permission pre-granted at installation?Yes → changed to NoThis is the one being judged

"Permission use is not directly related to your app's core purpose" is not a verdict on whether you may declare the permission. It is the answer to a request to have the app-op granted at install without asking the user. Decline the pre-grant and there is nothing left to review. The permission stays in the manifest, setFullScreenIntent stays in the code, and the user grants the app-op themselves.

Gotcha

A policy rejection names the permission, so it reads as a verdict on the permission. Read the form the rejection came from before believing that. Two submissions and one deleted-feature plan were spent on a question that had already been answered correctly, next to one that had not been read at all.

Intermediate A fix that is not in the bundle still costs a bundle

Changing that one answer required no code. The natural next thought — resubmit the artifact already sitting in the release folder — does not work. A version code is spent the moment it is uploaded, not when it is published, and Play will not re-review a code it has already ruled on. So the remedy for a form-only mistake is still a rebuild:

androidApp/build.gradle.kts
val appVersionName = "0.1.0"
val appVersionCode = 4   // 1 rejected (FSI), 2 withdrawn (implied mic), 3 rejected (FSI again)

Four codes, one unreleased app. Code 2 never even reached a reviewer — it was withdrawn after Play warned that declaring RECORD_AUDIO had implied android.hardware.microphone as required and dropped 6 devices. Treat version codes as consumable, not as a version history: numbering that tries to stay tidy across a review cycle will lose.

Gotcha

The audit you run before uploading — aapt2 dump badging on the built artifact, jarsigner -verify on the bundle — cannot see any of this. A fix that lives in a Console form leaves no trace in the build, so nothing in your tooling will notice if it silently reverts to its default. The only defence is a checklist step that re-opens the form and looks.

Intermediate The cost of opting out lands on onboarding

Declining the pre-grant means every install on Android 14+ starts with the ringing screen off. That turns the in-app route to the setting from a fallback into the only route — and the app's route was a warning card ranked third, behind the dialer role and notifications, on a Home screen that renders only the first card. On a fresh install, the one permission now guaranteed to be missing was the hardest of the four to reach.

So it became a checklist row, directly under notifications, because between them they are one feature: the notification carries the ringing call, the app-op lets it take over the screen.

shared/src/commonMain/kotlin/.../permissions/PermissionChecklist.kt
data class PermissionUiItem(
    val permission: AppPermission,
    val granted: Boolean,
    val requestable: Boolean,
    val opensSettings: Boolean = false,   // no runtime dialog exists for an app-op
)

The opensSettings flag exists to change one word. Every other row's button says Allow and produces a system dialog; this one says Open settings and leaves the app. A button labelled "Allow" that opens no dialog is a dead control, and the user learns not to trust the screen.

Verified

On a Pixel 8 Pro AVD at API 36, with the app-op forced to the shipping state via adb shell cmd appops set <pkg> USE_FULL_SCREEN_INTENT deny: the row renders second reading "Open settings"; tapping it resumes com.android.settings/.spa.SpaActivity on the per-app Full-screen notifications page with the toggle off; switching it on and pressing back returns to the checklist showing "✓ Granted", refreshed by onResume. Note that a sideloaded install grants the app-op — granted=true in dumpsys package — so the user's state has to be set deliberately or the test proves nothing.

Gotcha

canUseFullScreenIntent() is API 34+. Below it, MainActivity.refreshPermissionStatus hard-codes fullScreenIntentAllowed = true, so the warning card and the checklist row are correctly absent — and correspondingly unreachable. This project's only AVD was API 33, which means every full-screen-intent state had shipped without once being rendered. An emulator one API level below the feature does not test the feature; it silently tests the other branch.

Intermediate A privacy policy that promised a feature

The same audit found a "Record caller message" switch. It persisted its flag, validated a consent phrase, rendered as a Switch, and had a passing repository test. Nothing recorded. No RECORD_AUDIO permission, no MediaRecorder, no AudioRecord anywhere in the source.

That is Chapter 20's failure mode again, with a sharper edge: the published privacy policy carried an entire Call recording section, in both languages, describing the capability. A privacy policy is a legally operative document, and call recording is one of the most scrutinised areas in app review. The app was volunteering the topic for a feature it did not have.

Contrast

A dead code path is a bug. A dead code path that a legal document describes to users is a misrepresentation. The remedy is the same either way — make the claim and the code agree — but only one of them can cost you the listing.

Advanced What Android will and will not let you record

Implementing it honestly meant learning what is actually available. Android reserves the real call-audio sources behind a permission third-party apps cannot hold:

SourceAvailable to this app?
VOICE_CALL, VOICE_DOWNLINK, VOICE_UPLINKNo — needs CAPTURE_AUDIO_OUTPUT, which is signature|privileged
AudioPlaybackCapture (API 29+)No — cannot capture voice calls
Accessibility APINo — Play has prohibited its use for call recording since 2022
MediaRecorder.AudioSource.MICYes, but it is acoustic pickup through the earpiece

Holding ROLE_DIALER does not change any row of that table. So the feature was built on MIC, and every failure is treated as ordinary rather than exceptional:

androidApp/src/main/kotlin/.../telecom/AutoResponderRecorder.kt
} catch (e: IllegalStateException) {
    // start() on a mic the platform would not hand over -- the common OEM case.
    Log.w(TAG, "Microphone unavailable during the call", e)
    cleanUpAfterFailure(file)
    false
}

Several manufacturers give the telephony stack exclusive ownership of the microphone during a call, as an anti-wiretapping measure. A false return means the caller is disconnected exactly as it was before recording existed — the blocked call must always end, and must never stay open because recording failed.

Scope

The README, the privacy policy and the in-app toggle description all say the same sentence in four languages: it records through the microphone, so some phones capture nothing. Shipping a feature that may not work is fine. Shipping one while implying it will is not.

Advanced Tying a file to a row without leaking it

Audio belongs on the filesystem; the call log lives in SQLite. That split creates two failure modes, and the schema comment names both:

shared/src/commonMain/sqldelight/.../AppDatabase.sq
-- The file lives in app-internal storage; clearCallLog cannot delete it, so the caller that
-- clears the log must delete the files too -- see CallLogRepository.clearAll.
recording_path TEXT

Deleting rows before files strands the audio: nothing points at it, no UI can reach it, and it survives a "clear log" the user believed destroyed it. So clearAll deletes files first, and deleting a single recording clears the column even when the file delete failed — a row pointing at a file that still exists is worse than an orphan, because the UI keeps offering playback of a recording the user asked to destroy.

The other trap is finding the row at all. The entry is written while the call is still live (the decision must be logged even if everything after it fails), but the recording only exists once the call has ended:

shared/src/commonMain/kotlin/.../rules/SqlCallLogRepository.kt
// The insert and the id read share one transaction: last_insert_rowid() is
// connection-scoped, so a concurrent insert between the two -- two calls arriving
// together, which call waiting makes real -- would otherwise hand back the wrong row.
queries.transactionWithResult {
    queries.insertCallLogEntry(...).value
    queries.lastInsertRowId().executeAsOne()
}
Verified

346 JVM tests, including one that writes a real temp file, attaches it, calls clearAll, and asserts the file is gone. That failure is invisible through the UI — the rows vanish either way — so only a test that looks at the filesystem can catch it.

Case Study: the appeal that changed nothing in the code

The first response to the Play rejection was to start deleting: six files edited, the permission stripped from the manifest, the setFullScreenIntent call removed. It was the wrong instinct, and it was caught by reading the policy the rejection linked to.

The final change set contained no code at all for that issue — a declaration form, a category already set correctly, and rewritten listing copy. The lesson is not "appeal everything". It is that a rejection is a claim, claims can be checked, and the manifest is usually a better witness than the reviewer's summary.

Done when

  • Every user-facing claim about a feature — UI, privacy policy, store listing, onboarding — is backed by code that runs
  • A platform rejection has been checked against the platform's own policy text before you comply with it
  • Deleting a database row deletes whatever it points at outside the database
  • A feature that can fail on some devices says so, in every language you ship

Check Yourself

1. The app holds ROLE_DIALER. Does that let it record call audio with AudioSource.VOICE_CALL?

No. VOICE_CALL requires CAPTURE_AUDIO_OUTPUT, which is signature|privileged — granted only to apps signed with the platform key or installed on the privileged partition. The dialer role grants nothing here. The only option left is MIC, which picks the caller up acoustically and is blocked outright on some OEM builds.

2. Why does clearAll delete the recording files before deleting the rows, rather than after?

The rows hold the paths. Delete them first and the audio is unreachable but still on disk — invisible to the UI, undeletable by the user, and left over from a "clear log" they believed destroyed it.

3. Why must insertCallLogEntry and lastInsertRowId() run in the same transaction?

last_insert_rowid() is scoped to the connection, not to your insert. Another insert landing in between returns that row's id instead. Call waiting makes two simultaneous calls real, and the consequence is one caller's recording filed under a different caller's log entry.

4. A store rejection tells you to remove a permission. What do you check first?

The policy text the rejection links to, against your own manifest. Here the policy auto-granted the permission to apps whose core function is receiving calls, and IN_CALL_SERVICE_RINGING proved that is what the app is. The real gap was an unsubmitted declaration form, which no amount of deleting code would have fixed.

22Permissions Are a Conversation

Every previous chapter treated a permission as a boolean: you have it or you don't. This one treats it as something you ask for, explain, and can lose — three separate design problems, each of which this app got wrong in a different way.

Learning Objectives

  • Recognise why a permission dialog fired from onCreate is the worst possible ask
  • Model permissions the way a user groups them, not the way the manifest lists them
  • Handle a permission being revoked, not just granted
  • Put a failure warning on the screen where it will actually be read
  • Write positive assertions for state transitions instead of absence assertions

Beginner The ask that guarantees a "Deny"

This was the app's entire notification-permission strategy:

androidApp/src/main/kotlin/.../MainActivity.kt — before
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    enableEdgeToEdge()
    refreshPermissionStatus()

    // Fires before the user has seen anything but a splash.
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU && !notificationsPermissionGranted) {
        notificationsPermissionLauncher.launch(Manifest.permission.POST_NOTIFICATIONS)
    }

    setContent { /* welcome screen, which never mentioned permissions */ }
}

The dialog arrived over a welcome screen that said nothing about permissions. From the user's side that is indistinguishable from an app grabbing whatever it can reach on launch — and on Android 13+ a second denial is permanent. The app spent its single most valuable ask on the moment it had explained the least.

Why

The system dialog is a yes/no box with a one-line platform string. Everything persuasive you have to say — what the permission does, what breaks without it, what you will never do with it — has to be said before it opens, because there is no room inside it.

Intermediate A checklist modelled on the user, not the manifest

The replacement is an onboarding step listing each permission with the one thing it is used for. The tempting implementation is to enumerate AndroidManifest.xml. That produces a bad screen:

shared/src/commonMain/kotlin/.../permissions/PermissionChecklist.kt
// Deliberately *not* a mirror of AndroidManifest.xml. VIBRATE is a normal permission with
// nothing to grant, READ_PHONE_STATE and CALL_PHONE are one thing from the user's point of
// view ("Phone"), and USE_FULL_SCREEN_INTENT is an app-op the user can only reach from system
// Settings -- it belongs in the warning banners, not in a checklist of things to tap Allow on.
enum class AppPermission { NOTIFICATIONS, CONTACTS, PHONE, MICROPHONE }

Two rows then behave differently on purpose. Microphone is listed but non-requestable — named so the user knows it exists, never asked for here:

add(PermissionUiItem(AppPermission.MICROPHONE, micGranted, requestable = false))

And the notifications row disappears entirely below API 33, where POST_NOTIFICATIONS does not exist and an Allow button would open nothing:

if (notificationsApplicable) {
    add(PermissionUiItem(AppPermission.NOTIFICATIONS, notificationsGranted, requestable = true))
}
Gotcha

A "required" checklist is the old dialog with extra steps. The continue button here is always enabled; it only changes label to Continue anyway. If refusing a permission cannot get the user into the app, the explanation screen was never an explanation — it was a gate.

Scope

The microphone rule generalises: ask for a sensitive permission at the moment the feature that needs it is switched on, not during onboarding. A dialer asking for the microphone on first run, for a feature that ships off, reads as overreach — and spends the ask before there is anything to show for it.

Advanced A permission you can lose

Granting is the easy half. The default-dialer role can be handed to another app from system Settings at any time, and the app's resume hook only knew how to move one way:

shared/src/commonMain/kotlin/.../onboarding/DialerOnboardingViewModel.kt — before
private fun refresh() {
    if (gateway.isDefaultDialer()) {
        _state.value = _state.value.copy(dialerState = DialerOnboardingState.ALREADY_DEFAULT)
    }
}

Revoke the role and nothing happened. The state stayed GRANTED for the life of the process: blocking toggle on, rules listed, stats counting, and Telecom no longer handing the app a single call. The fix recomputes in both directions, with one carve-out:

private fun refresh() {
    // The system role dialog is on screen; its result, not this poll, decides what happens.
    if (_state.value.dialerState == DialerOnboardingState.REQUESTING) return

    val newState = when {
        gateway.isDefaultDialer() -> DialerOnboardingState.ALREADY_DEFAULT
        _state.value.dialerRoleHeld -> DialerOnboardingState.NOT_REQUESTED
        else -> _state.value.dialerState
    }
    _state.value = _state.value.copy(dialerState = newState)
}

The REQUESTING guard is not defensive padding. An onResume fires when the system role dialog appears over the activity, so without it a refresh lands mid-request, moves the state, and RequestResult's check then throws on a perfectly ordinary grant.

Advanced Where a warning has to live

The app already had permission warning cards. They were a private composable inside SettingsScreen — a screen a user who is not looking for a problem never opens. So an app that had silently stopped screening calls looked, on the screen people actually use, exactly like one that was working.

PermissionWarnings moved to its own file in commonMain, and Home renders it above the counters:

shared/src/commonMain/kotlin/.../home/HomeScreen.kt
// Above the stats deliberately: a user whose blocking has stopped working needs
// to see why before they read a "0 blocked today" that looks like good news.
PermissionWarnings(
    modifier = Modifier.fillMaxWidth(),
    dialerRoleHeld = dialerRoleHeld,
    ...
)

Two design constraints came with the move. Every parameter defaults to the non-warning value, so iOS — which builds these screens and has none of these concepts — renders nothing rather than a fix button that does nothing. And contacts and microphone are deliberately not shown: both are optional, both are explained where the feature that needs them lives, and a banner for a permission the user has not asked to use is a nag rather than a warning.

Contrast

A warning for something broken belongs where the user already is. A warning for something optional belongs where that feature is. Putting both in the same list trains the user to ignore the list.

Case Study: the assertion that would have passed anyway

DialerOnboardingViewModel was not untested. It had coverage of the request flow, the denial path, and the welcome flag. The revocation bug survived because no test ever called Refresh while the role was gone — the only refresh test asserted that a granted role stayed granted.

The obvious regression test is also the wrong one:

// Passes if refresh() downgrades correctly.
// Also passes if refresh() does nothing at all -- which was the bug.
assertNotEquals(DialerOnboardingState.GRANTED, viewModel.state.value.dialerState)

The shipped test names the destination instead:

assertEquals(DialerOnboardingState.NOT_REQUESTED, viewModel.state.value.dialerState)
assertFalse(viewModel.state.value.dialerRoleHeld)

Three of the five new tests were watched failing against the old body before the fix was written. That step is what distinguishes a regression test from a test that merely agrees with the code in front of it.

Verified

373 JVM tests. The Home warnings are covered through the real HomeScreen composable under Robolectric — including a case asserting that a fully permitted app shows no banner at all, because a warning system that cannot be silent is one users learn to scroll past.

Case Study: two bugs that only a real install could show

Everything above was green — 368 tests, lint, both platforms — when the release build went onto a razr 50 ultra and every permission was refused. Home then said two things at once:

┌────────────────────────────────────────────┐
│ Not your default phone app                 │
│ Call screening is off until Corta Spam is  │
│ set as your default phone app.             │
└────────────────────────────────────────────┘
  Corta Spam                          [ ●━ ]
  Blocking is on — spam and blocked calls
  are filtered

Both lines were individually correct code. The banner reads the dialer role; the caption reads the blockingEnabled setting, which knows nothing about the role. Neither had a bug in isolation, which is exactly why no unit test and no component test flagged it — there was no single wrong function to catch. The screen as a whole told the user they were protected, and that was false.

The caption now has a third state, and it is the state a user in trouble actually lands in:

when {
    !state.blockingEnabled -> Res.string.home_blocking_disabled
    !dialerRoleHeld        -> Res.string.home_blocking_inert
    else                   -> Res.string.home_blocking_enabled
}

The same screenshot showed the second bug. Four warning cards stacked to roughly 1400px on a 2640px display, pushing the toggle, all three counters and every quick link below the fold — the "put the warning where the user is" fix from earlier in this chapter had crowded out the thing the user came for. Home now renders only the most severe card and links to Settings for the rest, with severity meaning how much of the app this breaks: the dialer role stops every call reaching the app, so it outranks a permission that degrades one feature.

Gotcha

Component tests assert one composable's contract. Contradictions live between components, and so does layout. Both of these needed the release build, a real screen size, and the least convenient state — nothing granted — which is the state a first-time user is in and the one nobody screenshots.

Case Study: The Permission That Was Only Ever a Comment

Preparing the Play submission meant auditing the built bundle rather than the source manifest, because manifest merging adds entries nobody wrote. The permission list came back with one that no feature needed:

androidApp/src/main/AndroidManifest.xml — before
<!-- Required to be eligible for RoleManager.ROLE_DIALER and to act as the
     default phone app (docs/SPEC.md §1/§4). -->
<uses-permission android:name="android.permission.READ_PHONE_STATE" />

The comment is the entire justification, and it is wrong. AOSP's roles.xml lists only the two ACTION_DIAL activities under <required-components> for ROLE_DIALER; the phone permission set appears under <permissions>, which is what holding the role grants, not what qualifying for it demands. The permission was being requested so that the role could grant back the thing that was never needed.

One grep settled how much code depended on it:

grep -rniE 'READ_PHONE_STATE|TelephonyManager|getLine1Number|SubscriptionManager' \
  --include='*.kt' androidApp/src shared/src
# one hit — inside a comment

The onboarding checklist's Phone row looked like the counter-example, since AppPermission.PHONE sounds like phone state. It checks CALL_PHONE, used for placing a call back from the log. Removing READ_PHONE_STATE changed no screen and no test.

Contrast

<pkg>.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION, contributed by androidx.core, showed up in the same audit and was deliberately kept. It is app-private and grants nothing, this app's own code calls registerReceiver zero times — but the androidx libraries it depends on do, and stripping a permission a library genuinely needs fails as a runtime SecurityException on a user's phone, not as a build error. An unverifiable cleanup on the eve of a submission is not a cleanup.

The reason this matters beyond tidiness: a store reviewer reads the permission list and asks what each one is for. "Nothing reads it" is the worst possible answer, and this app had already been rejected once over a permission that was load-bearing. A declaration you cannot defend costs you the argument for the ones you can.

Gotcha

A permission can also declare hardware on your behalf. Uploading the next build produced "This release no longer supports 6 devices that were supported in your previous release" — nothing in the manifest said anything about hardware except telephony. The build tools did:

aapt2 dump badging app-release.apk | grep feature
uses-implied-feature: name='android.hardware.microphone'
  reason='requested android.permission.RECORD_AUDIO permission'

A uses-permission implies its corresponding uses-feature as required unless you declare that feature yourself. Adding an optional recording feature therefore deleted every microphone-less device from the store catalogue, silently, with no line of manifest to point at. The fix is one declaration:

<uses-feature android:name="android.hardware.microphone" android:required="false" />

Declaring it optional is only honest if the app really runs without the hardware — here AutoResponderRecorder.start() already returned false for a missing or busy microphone. Verify on the artefact, not the source: the same command afterwards reports uses-feature-not-required. And note what the warning cost — version code 2 had already been uploaded, and Play never accepts a version code twice, so a one-line manifest fix consumed a version number.

Done when

  • No permission dialog opens before the app has explained, in its own words, what the permission is for
  • Refusing any permission still lets the user into the app
  • Every permission the app can lose has a code path that notices the loss
  • The warning for a broken permission is visible on a screen the user opens anyway
  • State-transition tests assert the destination, not the absence of the old value
  • Every permission in the built artefact has a caller, or a written reason it cannot be removed

Check Yourself

1. Why is firing POST_NOTIFICATIONS from onCreate worse than firing it one screen later?

The system dialog has no room to explain anything — it is a yes/no box with a platform string. Everything persuasive must be said before it opens. Fired from onCreate it lands over a screen that has explained nothing, so it reads as an app grabbing what it can. On Android 13+ the second denial is permanent, so this spends a one-shot ask at the moment of least trust.

2. The manifest declares six permissions. Why does the onboarding checklist show four rows?

Because it is modelled on what the user is being asked, not on what the manifest declares. VIBRATE is a normal permission with nothing to grant, and USE_FULL_SCREEN_INTENT is an app-op reachable only from system Settings, so it belongs in a warning banner rather than behind an Allow button. The other four map one to one, with CALL_PHONE shown as plain "Phone" because the permission name means nothing to a user, and the microphone row shown but not requestable.

3. Why does refresh() return early when the state is REQUESTING?

The system role dialog appears over the activity, which triggers a resume and therefore a refresh. Without the guard the poll moves the state out from under the in-flight request, and RequestResult's check then throws on an ordinary grant. The dialog's result — not a resume poll — is the authority while a request is open.

4. Why is assertNotEquals(GRANTED, state) a poor regression test for the revocation bug?

It is an absence assertion. It passes when refresh() downgrades correctly and when refresh() does nothing at all — but "does nothing at all" is precisely the bug, so long as the state was not GRANTED to begin with. Naming the expected destination (NOT_REQUESTED) is the only version that fails on the broken code, which is why the tests were run against the old body first.

5. Home showed a banner saying screening was off and, directly beneath it, a caption saying blocked calls were being filtered. Which one had the bug?

Neither, taken alone. The banner correctly read the dialer role; the caption correctly read the blockingEnabled setting. The defect was that the caption described a setting as though it described an outcome, and the two are only the same thing while the app holds the role. That is why every unit and component test passed — there was no single wrong function, and a contradiction between two correct components is invisible to a test that renders one of them.

6. Home caps its permission warnings at one card while Settings shows all of them. Why the asymmetry?

They answer different questions. Home answers "is something wrong, and what do I do first" — four stacked error cards pushed the toggle and every counter off a 2640px screen, and a wall of red reads as one broken app rather than four fixable settings. Settings is the screen you open to diagnose, so it lists everything. Same component, one limit parameter, one severity order shared by both.

7. An audit finds two permissions in the built bundle that no application code reads. Why was one deleted and the other kept?

READ_PHONE_STATE was written by hand, justified only by a comment that misread ROLE_DIALER's requirements, and nothing — app or library — depends on it, so removing it is verifiable by compiling. DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION arrives through manifest merging from androidx.core, and although this app never calls registerReceiver, the libraries it ships do. Removing it fails as a runtime SecurityException on a user's device rather than as a build error, so "no hits in our source" is not evidence. The deciding question is not "does anything use it" but "would I find out if I were wrong".

23One Behaviour, Two Copies

Chapter 20 was about code that ships and never runs. This one is about code that ships, runs, and is right in one place and wrong in another — the same behaviour written three times, fixed once. The third copy turns out to be a platform API, which is the hardest kind to suspect. Along the way, two features whose obvious implementation would have quietly broken the product.

Learning Objectives

  • Spot the drift that happens when one behaviour lives in two private functions
  • See why a permission check in init is a check that runs at the wrong time
  • Refuse the literal reading of a feature request when it would break the feature
  • Recognise when a platform API is answering a different question from the one you asked
  • Understand what PendingIntent equality actually compares — and what it ignores

Beginner The fix that only landed in one file

Chapter 10 describes matching a contact saved 611 99 88 77 against the same person calling as +34611998877. The gateway builds its name map keyed by every form a contact may be recognised by:

shared/src/androidMain/kotlin/.../AndroidContactsGateway.kt
val keys = PhoneNumberParser.comparisonKeys(raw)
keys.forEach { key -> names.getOrPut(key) { name } }

So a lookup has to probe the same set. The call log did:

PhoneNumberParser.comparisonKeys(number).firstNotNullOfOrNull { contactNames[it] } ?: number

And the block lists, in their own private function with the same name, in a different file, did not:

contactNames[PhoneNumberParser.normalizeForComparison(number)] ?: number

One key, bare digits. Both functions were called displayName, both were private, and both were correct on the day they were written. When the contact-matching bug was fixed, the fix landed in the file where the bug had been reported and nowhere else — so for two days the call log showed names and the block lists showed numbers, for the same people, on the same phone.

Why

Nothing connected the two copies. No import, no shared symbol, no test that named both. A grep for displayName finds them, but only if you already suspect there are two — and the person fixing a reported bug has no reason to. The duplication itself is the defect; the wrong answer is only its symptom.

The repair is not "fix the second copy". It is to make a second copy impossible: one public contactDisplayName in the contacts package, both screens importing it, the private pair deleted. The test then has one place to point at — and it builds its fixture the way the gateway builds the real map, not by hand:

// A map keyed by hand would pass against a lookup that cannot work on a device.
private fun contactsOf(vararg saved: Pair<String, String>): Map<String, String> { ... }

Both failing cases — a contact saved nationally, and one saved with a trunk zero — were watched failing against the single-key body before it was replaced.

Intermediate A permission check that runs before the permission arrives

Both view models loaded the address book like this:

init {
    if (contactsGateway.hasPermission()) {
        viewModelScope.launch { contactNamesFlow.value = contactsGateway.contactNames() }
    }
}

Correct, and useless in the case that matters. The user grants contacts from Settings or the onboarding checklist — both of which run while a screen is already on top. By then init has run, seen no permission, and will never look again. The names stayed missing until the process died, which on a healthy phone can be days.

Contrast

The tempting fix is to collect the permission as a flow. It is not one: checkSelfPermission is a synchronous poll with no change notification. The event that actually exists is the activity resuming, which is precisely what happens when a permission dialog closes. So the trigger is LifecycleEventEffect(ON_RESUME) dispatching a RefreshContactNames intent — the same shape HomeViewModel already used, for the same reason.

Intermediate When the literal reading breaks the feature

"Add a way to disable notifications for unknown callers" has an obvious implementation: find every notify* call, gate them all on the new setting. It would have shipped a bug that no test in this repository could catch.

This app is the default dialer. Chapter 09 covers what that means: Telecom hands it IN_CALL_SERVICE_RINGING and stops ringing on its behalf, and the full-screen notification is the incoming-call screen over the lock screen. Suppressing it does not hide a banner — it leaves a stranger's call with no UI at all.

Gotcha

The setting therefore covers only the three after-the-fact notifications — blocked, missed, repeat caller — and the ringing one is deliberately not routed through it. A user who wants a stranger silenced outright already has a tool for that: a block rule. A setting named "notifications" that can stop calls from arriving is not a notification setting.

The second trap is inside the check itself. Whatever answers "unknown" returns nothing both for a stranger and for every number on earth when READ_CONTACTS is denied, so the policy has to ask whether the lookup can answer before trusting what it answers:

if (!notificationsEnabled) return false
if (notifyUnknownCallers) return true
// Without the permission everyone looks unknown, so filtering here would silence
// the channel for the user's whole address book, not for strangers.
if (!contactsAccessGranted) return true
return callerIsInContacts

Note where that lives: a pure NotificationPolicy object, not inside PassthroughInCallService. The service is Telecom-bound and no unit test can construct it, which is why every notification decision this app had shipped until now was provable only by placing a real call. Moved out, the whole truth table is five assertions at a desk.

What the service then fed that policy is the subject of the next section, and it was wrong.

Advanced The third copy was the platform's own

This chapter opened with one behaviour written twice. It was written three times. The third copy is not in this repository — it is ContactsContract.PhoneLookup, and the service used it to answer the question the policy above turns on:

androidApp/src/main/kotlin/.../PassthroughInCallService.kt
// Wrong: a different address book from the one the rest of the app uses.
contactsAccessGranted = ContactNameLookup.hasContactsAccess(this),
callerIsInContacts = ContactNameLookup.displayNameFor(this, number) != null,

PhoneLookup does not compare the digits you pass it. It matches through the provider's NORMALIZED_NUMBER column (data4), which the provider computes when the contact is saved, from the device's default region. A contact saved 611 99 88 77 only gets +34611998877 in that column if the phone believed it was in Spain at save time. The call arrives in E.164 from Telecom. If the two disagree, there is no match — the same national-versus-international mismatch Chapter 10 fixed in the rule engine, reintroduced by delegating to a component that has its own opinion about region.

Gotcha

On an emulator with no SIM, data4 is null for every row, so every contact reads as a stranger. With "silence unknown callers" switched on, that is a real contact's missed call being deliberately suppressed — the setting doing precisely the opposite of what it promises, on the one caller the user most wanted to hear about.

Why

The same lookup had been in the notification path for months without anyone noticing, because it was used for a name: a miss falls back to showing the number, which looks like a design choice rather than a defect. The moment its result was read as a boolean and used to decide whether to notify at all, the identical miss became a silently dropped notification. One function, two callers, and only the second one has a blast radius.

The repair is the same as the beginner section's: stop having a second address book. ContactsGateway is what the rule engine and every screen already consult, and its map is keyed by every form a contact may be recognised by, so the probe is one line beside contactDisplayName:

fun isKnownContact(number: String, contactNames: Map<String, String>): Boolean =
    PhoneNumberParser.comparisonKeys(number).any { it in contactNames }
Contrast

Deriving the country code from the number itself, which is what comparisonKeys does, has no region to be wrong about. PhoneLookup is not a worse implementation of that idea — it is a different idea, one that requires the device's region and the contact's save-time region to agree. Reaching for the platform API is usually right; it is wrong the moment the platform is answering a slightly different question than the one you asked.

Gotcha

The gateway is suspend — it is cached for five minutes precisely because it runs on the ringing path — so the policy call became suspend too, and one of its three callers was onCallRemoved, a Telecom callback that cannot wait. The number has to be read off the Call before launching the coroutine: onCallRemoved is the last moment Telecom guarantees details.handle is readable, and the coroutine outlives the callback. Capturing the Call and dereferencing it later is a null waiting for a busy phone.

The permission is also checked once and reused, rather than asked again as part of building the argument list: a denied read returns an empty address book, and the gateway would cache that emptiness for its full TTL — so a user who grants contacts mid-call would keep getting stranger treatment for five more minutes.

Advanced PendingIntent equality ignores your extras

The finished-call notification grew one-tap Block and Always allow buttons, each carrying the number in an extra. The natural implementation collides:

// Wrong: two numbers, one PendingIntent.
PendingIntent.getBroadcast(context, 0,
    Intent(context, CallActionReceiver::class.java)
        .setAction(ACTION_BLOCK_NUMBER)
        .putExtra(EXTRA_NUMBER, number),
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE)

Two PendingIntents are the same object when their request code and their Intent match under filterEquals — which compares action, data, type, package, component and categories, and ignores extras entirely. Post a missed-call notification for a second number and FLAG_UPDATE_CURRENT rewrites the first one's extra. The first notification still says the first name; its Block button now blocklists the second number.

Why

This class of bug survives every test that renders a notification, because it needs two notifications alive at once to appear, and it damages data rather than the UI — the notification looks perfect right up to the moment it blocks the wrong person.

The fix is to put the number somewhere filterEquals looks: a per-number data URI, plus the per-number history id as the request code.

.setData("cortaspam://call/${Uri.encode(number)}".toUri())
Gotcha

A BroadcastReceiver is dead the moment onReceive returns, so a suspend write started there is lost whenever the system reclaims the process first. goAsync() holds the broadcast open; the notification is dismissed only after the rule lands, so a tap that failed never looks like one that worked. And the buttons offered depend on the outcome — Block on an already-blocked call would do nothing, and a control that does nothing teaches the user their taps are ignored.

Scope

These buttons could not go on the ringing notification at all: CallStyle.forIncomingCall fixes its action set to answer and decline and drops anything added beside them. That constraint turned out to be good design advice — mid-ring is the worst moment to ask someone to make a filing decision.

Done when

  • No behaviour is implemented by two private functions in two files
  • Every permission-gated load has a trigger that fires when the permission arrives, not only when the object is built
  • A feature request that would break an existing guarantee is answered with the narrower reading, and the reason is written down
  • One question — "is this caller a contact?" — has exactly one answer in the codebase, including on the paths that call a platform API
  • Every PendingIntent that varies by data differs in something filterEquals compares
  • Decisions made inside untestable framework classes are extracted to something a unit test can call

Check Yourself

1. Two files each had a private displayName function. Which one had the bug?

The block-list copy, which probed the name map with a single normalised-digits key while the map is built keyed by every comparisonKeys form. But the more useful answer is that the duplication was the defect: both functions were correct when written, and the fix for the reported bug had no way to reach the copy nobody had mentioned. Extracting one shared contactDisplayName is the repair; correcting the second copy would only reset the clock.

2. Why is if (hasPermission()) in a ViewModel's init the wrong place for that check?

Because the grant usually happens after the ViewModel exists. The user is on the screen when they open Settings or the onboarding checklist and allow contacts, so init has already run and already decided no. There is no flow to observe either — checkSelfPermission is a synchronous poll with no change notification — so the real event is the activity resuming, which is exactly what a closing permission dialog produces.

3. Why does the "notifications for unknown callers" setting deliberately not cover the incoming-call notification?

Because as the default dialer this app owns the incoming-call UI. That notification's full-screen intent is the call screen over the lock screen, not a banner about it, so suppressing it would leave a stranger's call with no UI at all — a silent failure to receive calls, dressed as a notification preference. The user who wants a stranger stopped has a block rule for that.

4. With READ_CONTACTS denied, what would a naive "is this caller in my contacts?" check do to the setting?

Invert it. Any contacts lookup returns nothing without the permission, so every caller reads as unknown and the filter silences the entire channel — including the user's own family. The policy checks whether the lookup can answer at all before trusting its answer, and notifies when it cannot. The same grant is also read once and reused rather than re-asked, so a denied read never causes the gateway to cache an empty address book for its whole TTL.

5. Two notifications, two numbers, two Block buttons built with the same request code and action. What goes wrong?

PendingIntent identity is decided by Intent.filterEquals — action, data, type, package, component, categories — and extras are not part of it. The second build is therefore the same PendingIntent, and FLAG_UPDATE_CURRENT overwrites the first one's number extra. Both notifications now act on the second number, so tapping Block on the first blocklists the wrong caller while the UI shows the right name. Giving each a per-number data URI puts the distinguishing value somewhere filterEquals actually looks.

6. The app already had a contact-matching fix. Why did calling ContactsContract.PhoneLookup reintroduce the same bug?

Because PhoneLookup matches through the provider's NORMALIZED_NUMBER (data4) column, which is computed from the device's default region when the contact is saved — not from the number you pass in. A contact stored nationally therefore fails to match an E.164 call unless the phone's region happens to agree, and on an emulator with no SIM data4 is null, so every contact reads as a stranger. The fix in the rule engine derives the country code from the number itself, which has no region to be wrong about; delegating to the platform swapped that for a component holding its own regional assumption. It went unnoticed for months because the lookup had only ever supplied a display name, where a miss degrades to showing the number.

24Two Kinds of Non-Evidence

A user reports that a screen does not scroll. You read the code and find the scroll modifier exactly where it should be. You run the app on a device and watch it fail to scroll. Both of those feel like answers. Neither one is, and this chapter is about the shape of the test that finally is.

Learning Objectives

  • Tell the difference between reading a modifier chain and verifying its behaviour
  • Recognise when an on-device observation is invalidated by the state of the device
  • See why assertExists passes for the very bug being reported
  • Shrink a window in a Robolectric test instead of hoping content overflows
  • Test a screen inside the composition it actually ships in, not on its own

Beginner The code says it scrolls

Home hands the scroll modifier down to the shared adaptive container:

shared/src/commonMain/kotlin/.../home/HomeScreen.kt
AdaptiveContent(
    windowSizeClass = windowSizeClass,
    contentModifier = Modifier.verticalScroll(rememberScrollState()),
) { ... }

And the container applies it to its column:

shared/src/commonMain/kotlin/.../adaptive/AdaptiveContent.kt
modifier.fillMaxWidth().padding(24.dp).then(contentModifier)

Chase it further and everything still checks out: AdaptiveScaffold puts the content in a Box(Modifier.weight(1f)), so the column is measured against a bounded height; verticalScroll measures its child unbounded and clamps itself to that bound, which is exactly the arrangement that produces a scrollable viewport. The reading is correct. It was also given to the user as the answer, before anything had been run.

Why

A modifier chain is a description of intent, and layout bugs are almost never in the intent — they are in what some ancestor did to the constraints, or in a second component docked on top, or in a font scale nobody tried. "I read the code and it looks right" is the same evidence the person who wrote the bug had.

Intermediate The device says it doesn't — and that isn't evidence either

So it was run: a 1344x2992 emulator at font_scale 2.0 and wm density 560. Home's last quick link sat clipped at the bottom edge, and two swipes produced pixel-identical screenshots. That is the reported bug, reproduced.

Except that mid-run the emulator threw "System UI isn't responding" and died shortly after. If the window manager is failing, an injected swipe that changes nothing tells you nothing about the scroll container — it may never have been delivered. A uiautomator dump also found no scrollable="true" node, which sounds decisive and is not: Compose scroll containers do not reliably surface that attribute.

Gotcha

A failed observation on a broken instrument is not a weaker result — it is no result. The tempting move is to treat it as suggestive and go fix something, which is how a real scroll modifier gets rewritten to chase a bug that was never there. The honest record was "open, and neither answer is trusted", carried into the next session as exactly that.

Intermediate Why every existing test passed

Home already had UI tests naming the exact element that was clipped:

composeTestRule.onNodeWithText("Settings").assertExists()

assertExists asks whether the node is in the semantics tree. A composable that was measured, placed and then clipped off the bottom of the window is in the semantics tree. Every test in the file passes against a Home that a user cannot scroll — they were written to check that Home renders its quick links, and they do check that, which is why nobody looked at them twice.

Contrast

Chapter 22 made the same point from the other direction: assertions about absence stay green against a feature that does nothing. This is the mirror image — an assertion about mere existence stays green against a feature the user cannot reach. Both are true statements about a broken screen.

Advanced The test that can fail

The bug needs content taller than the window. Rather than hope Home overflows at the default Robolectric size, shrink the window until it must — Robolectric takes screen qualifiers per test:

shared/src/androidUnitTest/kotlin/.../home/HomeScreenUiTest.kt
@Test
@Config(sdk = [34], qualifiers = "w411dp-h320dp")
fun `last quick link is off screen but reachable by scrolling`() {
    ...
    composeTestRule.onNodeWithText("Settings").assertIsNotDisplayed()
    composeTestRule.onNodeWithText("Settings").performScrollTo().assertIsDisplayed()
}

Three claims in two lines: the element is off-screen (so the test is exercising the overflow case rather than a window that happens to fit), scrolling to it is possible at all (performScrollTo fails outright when no scrollable ancestor exists), and it is genuinely visible afterwards.

The second test renders Home the way the app does — inside the navigation scaffold:

AdaptiveScaffold(windowSizeClass = WindowSizeClass.Compact, selectedIndex = 0, onNavigate = {}) {
    HomeScreen(...)
}

Home is never shown bare: the scaffold's NavigationBar takes the bottom of the window away from it. A screen that scrolls on its own and stops once something is docked underneath is a bug an isolated test structurally cannot see — the same lesson Chapter 20 draws about testing through the real entry point.

Gotcha

Inside the scaffold, onNodeWithText("Settings") becomes ambiguous — the NavigationBar has a tab with that label too. Matching by text alone would fail the test for a reason that has nothing to do with scrolling. The quick link is the one inside the scrolling area, so say that:

composeTestRule.onNode(hasText("Settings") and hasAnyAncestor(hasScrollAction()))
Verified

Both tests were run against a Home with contentModifier = Modifier — the scroll removed — and both failed. Then the modifier was restored and both passed. That is the only step that separates a regression test from a decoration, and Chapter 22 exists because the ones that skipped it stayed green against an inert feature for eight days.

Scope

What these tests do not prove: that Home scrolls at font_scale 2.0 on the razr. They shrink the viewport instead of enlarging the text, which produces the same condition — content taller than the window — through a different cause. That is a reasonable substitute and it is not the same experiment, so the README says so rather than claiming the hardware question closed.

Done when

  • No layout claim rests on reading a modifier chain
  • An observation made on a device that was failing at the time is recorded as unresolved, not as a result
  • Reachability assertions use assertIsDisplayed/performScrollTo, never assertExists
  • Overflow tests force the overflow with a window qualifier instead of assuming it
  • At least one test renders the screen inside the scaffold it ships in
  • Every new regression test has been watched failing against the unfixed code

Check Yourself

1. The scroll modifier was present and correctly applied. Why was that not an answer to "the home screen does not scroll"?

Because a modifier chain states intent, and layout bugs live in what surrounds it — an ancestor's constraints, a component docked over it, a font scale nobody tried. The reading was in fact correct here, which is the point: it would have read exactly the same if the bug had been real, so it could not distinguish the two cases. It is the same evidence available to whoever wrote the bug.

2. The screen was reproduced clipped on a device, and two swipes changed nothing. Why was that thrown out?

The emulator reported "System UI isn't responding" during the run and died shortly after. With input delivery itself suspect, a swipe that produced no change says nothing about the scroll container — it may never have arrived. A broken instrument yields no result rather than a weak one, and acting on it risks rewriting working code to chase a bug that was never there.

3. Home's existing tests assert onNodeWithText("Settings").assertExists(). What state of the screen do they fail to distinguish?

A quick link that was composed, placed, and then clipped off the bottom of an unscrollable window is still in the semantics tree, so assertExists passes on precisely the bug a user would report. The reachability assertions are assertIsNotDisplayed before scrolling and performScrollTo().assertIsDisplayed() after — the first proves the test is exercising the overflow case, the second fails outright if no scrollable ancestor exists.

4. Why does one of the two tests wrap HomeScreen in AdaptiveScaffold?

Because that is the composition the app ships: Home is never rendered bare, and the scaffold's NavigationBar takes the bottom of the window away from it. A screen that scrolls in isolation and stops scrolling once something is docked beneath it would pass a bare-screen test forever. It also forces a real disambiguation — "Settings" is a NavigationBar label too, so the assertion targets the node with a scrolling ancestor.

5. These tests pass. What question about Home is still open?

Whether Home scrolls at font_scale 2.0 on real hardware. The tests create the overflow by shrinking the window rather than by enlarging text — the same condition reached by a different cause, which is a reasonable substitute and not the same experiment. Saying so is the difference between a covered behaviour and one that is merely believed.

25The Manifest Promised What No Code Delivered

Chapter 20 is about code that ships and never runs. This chapter is about a declaration with no code behind it at all — two intent filters added to satisfy a platform check, which made the app volunteer for a job it had never implemented. It is also about what taking a platform role costs: ROLE_DIALER replaces the phone app, and this one replaced it with something that could not place a call.

Learning Objectives

  • Recognise inert configuration — the variant no audit of source code can find
  • Understand what a platform role takes away, not only what it grants
  • Tell ACTION_DIAL from ACTION_CALL, and why the difference is a safety property
  • Model "the same request, again" when value equality cannot express it
  • Give a notification a caller identity when no canonical key exists

Beginner The role is a trade, not a feature

Chapter 09 covers claiming RoleManager.ROLE_DIALER: Telecom hands the app the in-call UI and, with IN_CALL_SERVICE_RINGING, the ringing too. What went unsaid for eight months is the other half — the role replaces the user's phone app. Every screen this app built was about incoming calls. The only way to originate one was tapping a row that already existed in the call log:

androidApp/src/main/kotlin/.../MainActivity.kt
onCallBack = { number -> /* ACTION_CALL, from a call-log row */ }

So a number the user had never been called by could not be dialled at all. Becoming the default dialer had removed dialling.

Why

Nothing was broken in the sense a test can express. Every feature worked; the product had a hole where the platform expected a capability. When you take a role, enumerate what the app you displaced was doing for the user — that list is your new obligations, and it is not in your own backlog.

Advanced Inert configuration

The manifest had been advertising the missing feature the whole time:

androidApp/src/main/AndroidManifest.xml
<!-- ACTION_DIAL is a hard requirement for RoleManager.ROLE_DIALER eligibility -->
<intent-filter>
    <action android:name="android.intent.action.DIAL" />
    <category android:name="android.intent.category.DEFAULT" />
    <data android:scheme="tel" />
</intent-filter>

MainActivity had no onNewIntent and never read intent.data anywhere. The filters were written to pass a role-eligibility check and were never connected to anything. The consequence is not that a feature was missing — it is that the app claimed the feature to the whole device: Corta Spam appeared in the chooser for every tel: link, launched to Home, and dropped the number.

Gotcha

This is worse than not handling tel: at all, and it is invisible to every technique Chapter 20 uses. There is no unreachable function to find, no dead branch, no unused symbol — the "code" is four lines of XML that the platform reads and the codebase never does. Grep for what your manifest promises and confirm something answers each promise; a `<intent-filter>` with no reader is an inert feature with a marketing department.

Intermediate DIAL shows, CALL dials

Having found the number, the tempting fix is to place the call. That would be a bug with a blast radius: ACTION_DIAL means show this number and let the user decide, while ACTION_CALL is the one that dials — which is why only the latter needs CALL_PHONE. Auto-dialling on DIAL turns every tel: link on the web into a call placed without confirmation.

fun numberFrom(action: String?, data: Uri?): String? {
    if (action != Intent.ACTION_DIAL && action != Intent.ACTION_VIEW) return null
    if (data == null || !data.scheme.equals("tel", ignoreCase = true)) return null
    // Already percent-decoded: a '#' arrives as %23 and would otherwise read as a fragment.
    return data.schemeSpecificPart?.trim()?.ifEmpty { null }
}
Contrast

A pure function over (action, data) rather than one that takes an Intent: the decision that had never been made is now nine assertions at a desk, including the one nobody thinks of — ACTION_DIAL with no data is legitimate and means "open the dialer", so it must return null rather than a request to dial the empty string.

Advanced "Again" is not a value

The number then has to reach the keypad from an Activity callback, through Compose. Modelling it as String? looks obvious and is wrong twice over. Tapping the same tel: link a second time produces an identical value, so nothing recomposes and the keypad never re-opens; and navigating back to the tab later re-applies the old number over whatever the user has typed since.

data class DialRequest(val number: String, val id: Long)

var appliedRequestId by rememberSaveable { mutableStateOf(NO_REQUEST_APPLIED) }
LaunchedEffect(dialRequest) {
    val request = dialRequest ?: return@LaunchedEffect
    if (request.id == appliedRequestId) return@LaunchedEffect
    typed = request.number
    appliedRequestId = request.id
}
Why

The id is not a cache key, it is the identity of an event. State is "what is true now"; an intent arriving is "this happened". Squeezing an event into a state value loses the repeat, and keying the effect on the request alone loses the difference between a new request and the same one recomposing. Both failures were watched: deleting the guard turns "the same request is not applied twice" red.

Advanced A caller identity with no canonical form

The second complaint was notifications. Each finished call posts to an id derived from the number, so repeats already replaced each other — but nothing on the notification said so, and five calls from one spammer read as one call, five times. Adding a count needs a stable answer to "is this the same caller?", and the obvious move is a canonical key. Chapter 10 and Chapter 23 explain why there isn't one:

// sameNumber is asymmetric on purpose:
//   "+34611998877" vs "611 99 88 77"  -> same caller (one side has no country)
//   "+34611998877" vs "+51611998877"  -> different people (both do)

No single string expresses that, so nothing is canonicalised. Instead the first form seen becomes the caller's representative, and later forms are matched against it with the real comparator:

val existing = entries.firstOrNull { PhoneNumberParser.sameNumber(it.representative, number) }
Gotcha

Two details that only show up in use: a withheld number arrives blank and is indistinguishable from the next one, so blanks are never counted — otherwise every private caller feeds one shared, ever-growing tally. And the set of tracked callers is bounded, because this lives in a service that can stay up for days; an unbounded map keyed by every stranger who ever called is a leak with a slow fuse.

Verified

Asserted through the notifier with Robolectric's notification manager, not against the counter alone: five calls leave one active notification whose sub-text reads "5 attempts". A correct counter whose number never reaches a notification is exactly the inert shape this course keeps returning to. Breaking the count turned three of those tests red; breaking sameNumber back to string equality turned two more.

Advanced The screener was screening the user

Writing tests for "the calling scenario" turned up something the feature work had walked straight past. An InCallService receives every call — that is the price of owning the in-call UI — and onCallAdded gated only the ringing on direction:

if (call.state == Call.STATE_RINGING) { ringer.start(); /* notify */ }

state.evaluation = serviceScope.launch { // <-- not gated on anything
    val decision = evaluateIncomingCall.evaluate(number)
    if (decision.isBlocked) { ...; call.reject(false, null) }
}

So the rule engine ran against numbers the user dialled. Call someone on your own blocklist and your phone hangs up on you. Worse, a quiet-hours rule blocks everything not allowlisted, so inside that window every outgoing call the user placed would be terminated by their own dialer. With the auto-responder enabled it is not even a hang-up: the app answers the call and plays the user's greeting into it.

Why

The bug is as old as the service, but it needed a way to place a call to be reached often — and the previous chapter's keypad had just built one. A feature does not only add surface; it makes existing paths reachable. "This code has been fine for months" is a statement about traffic, not about correctness.

The fix is a direction check, and it goes where the untestable service cannot hide it:

fun isIncoming(sdkInt: Int, callDirection: Int, state: Int): Boolean =
    if (sdkInt >= Build.VERSION_CODES.Q) callDirection == Call.Details.DIRECTION_INCOMING
    else state == Call.STATE_RINGING
Contrast

Below API 29 there is no callDirection, and the state at onCallAdded is the only signal — Telecom adds an incoming call already ringing, an outgoing one connecting or dialling. Note which way the unknown case falls: an unrecognised state resolves to not incoming. Failing to screen one call is a nuisance; ending a call the user placed is the phone breaking. Defaults belong on the side of the smaller mistake, which is the opposite of the choice RingerPolicy makes for an unknown ringer mode — and for the same reason.

Gotcha

The early return goes after registerCallback(stateCallback) and after the in-call Activity is launched. An outgoing call still needs this app's UI and its "return to call" notification — the app owns those now. Only the screening is skipped.

Verified

Writing the call-back tests also caught a bug in code written an hour earlier: Uri.encode(number) escapes + to %2B, which breaks every international number. Uri.encode(number, "+") keeps the plus and still escapes the #. One assertion on a literal tel: string found it — the kind of check that feels too obvious to write.

Intermediate Two sources of truth for one tab bar

The keypad became the second navigation tab, which means every index after it moved. The bar builds its items from one list and decides which is highlighted from a separate when:

val sectionRoutes = listOf(HOME, KEYPAD, callLogRoute(), BLOCK_LIST, SETTINGS)

fun routeSection(route: String?): Int = when { ... }   // the other copy

Disagreement between them compiles, runs, and merely lights the wrong tab. So the test is the invariant rather than five hand-written cases:

sectionRoutes.forEachIndexed { index, route -> assertEquals(index, routeSection(route)) }

Done when

  • Every manifest declaration has a reader, and you have checked rather than assumed
  • Taking a platform role comes with a written list of what the displaced app did for the user
  • ACTION_DIAL never places a call
  • An external event carries an identity, so "again" is distinguishable from "unchanged"
  • Caller identity uses the project's real comparator, never a re-derived canonical key
  • Anything that grows per unknown caller inside a long-lived service is bounded
  • Two sources of truth that must agree are tested by the invariant, not by examples

Check Yourself

1. The app declared ACTION_DIAL intent filters and no Kotlin read them. Why is that worse than not declaring them?

Because the declaration advertises the capability to the entire device. Corta Spam was offered in the chooser for every tel: link, accepted the intent, launched to Home and discarded the number — a user who picked it got silence instead of a dialer. Not declaring it would simply have left the app out of the list. It is also invisible to source-level auditing: there is no dead function or unreachable branch, only four lines of XML that the platform reads and the codebase never does.

2. Why must an ACTION_DIAL intent not place the call?

Because DIAL means "show this number and let the user decide" — ACTION_CALL is the one that dials, and it is the one that requires CALL_PHONE. Dialling on DIAL would turn every tel: link on a web page into a call placed without confirmation. The distinction is a safety property of the platform, not a stylistic choice.

3. Why does the dialled number travel as a DialRequest(number, id) instead of a String??

Because an arriving intent is an event and a String? is a state. Tapping the same link twice yields an identical value, so nothing recomposes and the keypad never re-opens — value equality cannot tell "again" from "unchanged". The id also lets the screen record which request it has already applied, so returning to the tab later does not retype a number the user deliberately deleted.

4. Why is there no canonical key for "which caller is this notification about"?

Because the project's matching rule is asymmetric: a national number may match an international one, since only one side claims a country, while two international numbers with different country codes must never match even when their national parts are identical. A single canonical string cannot encode both. Reducing a number to one key is precisely what caused the contact-matching bugs of 2026-08-11 and 2026-08-13, so the counter keeps the first form seen as a representative and compares later forms with sameNumber.

5. Why are withheld (blank) numbers excluded from the attempt count?

Because one blank number is indistinguishable from the next. Counting them merges every private caller into a single tally, so the notification would tell the user that "the" withheld caller had tried eleven times when eleven different people had each called once. They still get a notification — they just do not get a count that would be a fabrication.

6. Inserting a tab in the middle of the navigation bar breaks nothing at compile time. What does it break, and what stops it?

It shifts every index after it, and the bar's item list and its routeSection lookup are two separate copies of the same ordering — so the app runs and highlights the wrong tab. A handful of example assertions would have to be remembered and updated one by one; the invariant test iterates sectionRoutes and asserts that each entry selects its own index, so it covers any future tab for free.

7. An InCallService receives outgoing calls too. What did this app do with them, and why did it matter more this week than last?

It ran them through the rule engine. Only the ringing was gated on state; the evaluation was gated on nothing, so a number on the user's own blocklist got call.reject() — the phone hanging up on the call its owner placed — and a quiet-hours rule, which blocks everything not allowlisted, would have ended every outgoing call inside the window. With the auto-responder on, the app answers instead and plays the user's greeting into their own call. The bug is as old as the service; what changed is that the keypad had just made placing a call from this app possible at all. A feature does not only add surface, it makes existing paths reachable.

8. Below API 29 there is no callDirection. Which way should an unrecognised call state resolve, and why?

To not incoming, so the call is left alone. The two mistakes are different sizes: failing to screen one call is a nuisance the user may not even notice, while ending a call they placed is the phone appearing to break. That is the mirror image of RingerPolicy, where an unknown ringer mode rings — and it is the same principle, since there the silent failure is the expensive one.

26The Data Was Already There, in the Wrong Shape

Chapter 25 gave the app a keypad. This chapter is about what a keypad is still missing — the address book it has been reading since the first release — and about a notification whose buttons worked while its body did nothing at all. Neither feature needed new data. Both needed the data that existed, in a shape a person can read.

Learning Objectives

  • Spot a gateway whose return type has already thrown away what the new caller needs
  • Design one input that searches and dials without asking the user which they meant
  • Rank search matches so the ordering is a decision, not an accident of iteration order
  • Give a notification body an action, and keep two callers' PendingIntents apart
  • Understand why a layout bug can only be found on hardware

Beginner The address book was already in memory

ContactsGateway has read the device's contacts since the allowlist needed them. It offered exactly two shapes:

shared/src/commonMain/kotlin/.../contacts/ContactsGateway.kt
suspend fun contactNumbers(): Set<String>          // normalized digits, for "is this a contact?"
suspend fun contactNames(): Map<String, String>    // every comparison key -> display name

Both are correct and both are useless for a list a human reads. A Set has no order. The map is keyed by comparison keys, so the number it remembers is 34611998877 — not the +34 611 99 88 77 the user typed into their contacts app and recognises on sight. The fix is a third shape, not a third data source:

data class Contact(val name: String, val number: String)

/** Every contact that has a number, name and number as saved, sorted by name. */
suspend fun contacts(): List<Contact>
Why

Normalisation is lossy and that is its job — matching must not care about punctuation. Presentation is the one place that loss is a bug, so the raw string survives to the UI and normalisation happens at comparison time instead. Sorting is the same story: ordering by DISPLAY_NAME in SQLite is bytewise, which files "Ángela" after "Zulema" in all four locales this app ships in, so the list is sorted with a Collator.

Intermediate One field that searches and dials

The obvious keypad design has a search box and a number display. It also makes the user decide which one they are using before they know which one they need. The platform dialer being replaced does not ask that, so neither does this one: the field is the query and the number, and both matchers always run.

shared/src/commonMain/kotlin/.../contacts/ContactSearch.kt
private fun rank(contact: Contact, query: String, queryDigits: String): Int {
    if (contact.name.startsWith(query, ignoreCase = true)) return NAME_PREFIX
    val numberDigits = PhoneNumberParser.normalizeForComparison(contact.number)
    if (queryDigits.isNotEmpty() && numberDigits.startsWith(queryDigits)) return NUMBER_PREFIX
    // Word-start, so "ana" matches "Maria Ana" but not "Susana".
    if (contact.name.split(' ', '-').any { it.startsWith(query, ignoreCase = true) }) return NAME_WORD_PREFIX
    if (queryDigits.isNotEmpty() && numberDigits.contains(queryDigits)) return NUMBER_CONTAINS
    return NO_MATCH
}

Three decisions hide in those six lines. Digits are compared as digits on both sides, so stored formatting is irrelevant. A number match is a contains, not sameNumber — Chapter 10's comparator answers "are these the same caller", and a half-typed prefix is by definition not one yet. And a name match is a word start, never a bare contains, because a syllable buried inside a word is a coincidence the user did not ask for.

Contrast

The tempting shortcut is to branch on the query: digits mean number search, letters mean name search. It is wrong on the first counterexample — a contact saved as "O2" is a name with a digit in it, and a name typed on a phone keypad is still a name. Running both matchers and ranking costs nothing and has no such edge.

Intermediate A cap you can see

The keypad is a single scrolling Column, not a lazy list, so every match becomes a real row. On the razr's 1,900-contact address book that matters:

matches.take(MAX_VISIBLE_MATCHES).forEach { contact -> ContactRow(contact) { onPick(contact) } }
if (matches.size > MAX_VISIBLE_MATCHES) {
    Text(stringResource(Res.string.keypad_more_matches))   // "Keep typing to narrow the list."
}
Why

A cap is a product decision and a silent cap is a lie: five results with nothing said reads as "these are all your matches", and the contact the user went looking for appears not to exist. Truncation is fine; unannounced truncation is a bug report waiting to be filed against search.

Advanced The notification body did nothing

Blocked, missed and repeat-caller notifications already carried buttons — Chapter 23 covers keeping their PendingIntents distinct. What none of them had was a contentIntent. Tapping the notification that told you about a call simply dismissed it, and the call log it was reporting stayed two navigation steps away.

androidApp/src/main/kotlin/.../ShowCallLogIntent.kt
fun forNumber(context: Context, number: String): Intent =
    Intent(context, MainActivity::class.java)
        .setAction(ACTION)
        .setData("cortaspam://call-log/${Uri.encode(number)}".toUri())   // identity, not payload
        .putExtra(EXTRA_NUMBER, number)                             // payload
        .addFlags(Intent.FLAG_ACTIVITY_NEW_TASK or Intent.FLAG_ACTIVITY_CLEAR_TOP or
            Intent.FLAG_ACTIVITY_SINGLE_TOP)
Gotcha

The number appears twice and neither copy is redundant. PendingIntent equality ignores extras, so two notifications built from intents differing only in their extra are the same PendingIntent — and FLAG_UPDATE_CURRENT would rewrite the first caller's notification to point at the second. The data URI is what makes them different objects; the extra is what gets read. This is the third time this project has paid for that rule.

Arriving at the call log is not the goal either. The tap was about doing something to that caller, so the screen opens with the caller's actions already up — and the request carries an id for exactly the reason DialRequest does:

LaunchedEffect(callLogRequest, entries, windowSizeClass) {
    val request = callLogRequest ?: return@LaunchedEffect
    if (request.id == appliedRequestId) return@LaunchedEffect      // dismissed stays dismissed
    if (windowSizeClass == WindowSizeClass.Expanded) {
        // Two-pane has no dialog: its detail pane needs an entry, so wait for the log to load.
        selectedEntry = entries.firstOrNull { sameNumber(it.number, request.number) } ?: return@LaunchedEffect
    } else {
        selectedNumber = request.number
    }
    appliedRequestId = request.id
}

Advanced What only hardware could say

Every unit test passed, the emulator looked right, and the feature was still broken on a phone. With the soft keyboard raised, the results list pushed the Call button below the bottom of the screen — so picking a contact hid the button that places the call. The Robolectric window is 320 × 470 px; the test that catches it had to scroll first, which is the honest reproduction of what the user faced:

// and the tap lands on nothing, which is exactly what a user would see too.
composeTestRule.onNodeWithText("Call").performScrollTo().performClick()

The fix is one line in the pick handler — focusManager.clearFocus(), which takes the keyboard down with the focus — and it was not visible to anyone reading the code.

Verified

On a motorola razr 50 ultra (API 36) against its real address book: Ana returns four contacts, one of them matched on a later word of the name rather than its start, 0000 matches four by number, and picking one fills the field with the number as saved. Outgoing calls were re-checked on the same handset with the dialled number on the manual blocklist and an all-day quiet-hours rule active: Telecom binds PassthroughInCallService, InCallActivity appears, the call reaches the network, and the call log stays empty — the rule engine never saw it. Knowing which half of your suite cannot run on the device in your hand is part of knowing what you have proven.

Advanced The log that remembered half the calls

The same shape again, one layer down. The call log had recorded incoming calls since the rule engine existed, because a row was a decision record — number, action, rule type, rule id. An outgoing call has none of those: the screener refuses to evaluate one on purpose (Chapter 25). So the app that had replaced the phone app showed a history with every call its owner had placed missing from it.

The data shape was wrong rather than absent, so the fix is a column, and the column is where the interesting part is:

shared/src/commonMain/sqldelight/org/carlospinan/bloqueador/app/db/3.sqm
CREATE TABLE CallLogEntry_new (
    -- ...every existing column, copied verbatim from AppDatabase.sq...
    direction TEXT NOT NULL DEFAULT 'INCOMING' CHECK (direction IN ('INCOMING', 'OUTGOING'))
);

SELECT id, number, ..., 'INCOMING' FROM CallLogEntry;
DROP INDEX idx_call_log_action_time;   -- see below
DROP TABLE CallLogEntry;
ALTER TABLE CallLogEntry_new RENAME TO CallLogEntry;
CREATE INDEX idx_call_log_action_time ON CallLogEntry(action, timestamp DESC);
Gotcha

SQLite would have accepted a plain ALTER TABLE ADD COLUMN here — a CHECK is legal in that form. The rebuild is chosen anyway because verifyMigrations diffs the migrated schema against the CREATE TABLE in the .sq file, and a table assembled by ADD COLUMN is not guaranteed to compare equal to one written out in full. Replaying the definition verbatim removes the question.

Two more, both of which cost a build: DROP TABLE takes the table's indexes with it, so the index has to be recreated or three Home-screen counters quietly become full table scans of a log only the user can shrink. And SQLDelight's migration compiler does not model that drop — without the explicit DROP INDEX, generation fails with Duplicate index name idx_call_log_action_time on a statement that is correct SQL.

The last decision is a labelling one. An outgoing row is stored ALLOWED because that is the only other value the action CHECK permits — and usefully, it keeps outgoing calls out of the blocked-call statistics. But the list must not say "Allowed call":

val isOutgoing = entry.direction == CallDirection.OUTGOING

    isOutgoing -> stringResource(Res.string.call_log_outgoing_label)
    isBlocked  -> stringResource(Res.string.call_log_blocked_label)
    // ...
}
Why

"Allowed" is a claim about screening, and this call was never screened. Storage constraints are allowed to force a value; they are not allowed to force a sentence. The moment a stored enum is rendered straight to the user, the database schema has become copywriting.

Check Yourself

1. The app already read every contact. Why did contact search still need a change to ContactsGateway?

Because both existing shapes had already discarded what a search result needs. contactNumbers() is a Set of normalized digits — no order, no formatting, no names. contactNames() is keyed by comparison keys, so the number it holds is bare digits rather than the punctuation the user saved and recognises. Normalisation is lossy on purpose; presentation is the one caller for which that loss is a defect, so it gets List<Contact> with the raw string intact and a locale-aware sort.

2. Why does the keypad have a single field rather than a search box and a number display?

Because two inputs make the user choose which one they are using before they know which one they need, and the platform dialer being replaced never asked that. One field runs both matchers on every keystroke: letters rank against names, digits against contact numbers as digits. Branching on the query's content instead would be wrong on the first counterexample — a contact saved "O2" is a name containing a digit.

3. Why is a number matched with contains here, when the rest of the app uses sameNumber?

Because they answer different questions. sameNumber answers "are these the same caller", which is what a rule decision needs and is asymmetric about country codes on purpose. A search query is a fragment the user is still typing — by definition not yet the same number as anything — so it is a substring match over digits on both sides. Using sameNumber would return nothing until the last character was typed.

4. The results list is capped at five. Why must the cap be visible in the UI?

Because a silent cap is indistinguishable from a complete result set. Five rows with nothing said reads as "these are all your matches", so a contact that exists appears not to — a bug report against search for behaviour that was a deliberate decision. The screen is one scrolling Column, so rendering 1,900 rows is not the alternative; announcing the overflow is.

5. A notification's buttons worked. Why was a missing contentIntent still a real defect?

Because the body is the biggest tap target on the notification and the one users hit first. With no content intent it only dismissed — the app deleted its own report of the call and left the user to find the call log, the caller and the actions by hand. It also silently broke the platform's convention: every other notification on the device opens something.

6. The show-call-log intent carries the number twice, in data and in an extra. Why?

Because PendingIntent equality ignores extras. Two notifications whose intents differ only by the extra resolve to one PendingIntent, and FLAG_UPDATE_CURRENT then repoints the older notification at the newer caller — tap the notification about caller A and get caller B's actions. The per-number data URI is the identity that makes them distinct objects; the extra is the payload that is actually read.

7. The two-pane layout waits for the call log to load before honouring a notification tap; the phone layout does not. Why the difference?

Because they need different things. The phone shows a dialog that only needs the number, which the request already carries. The expanded layout has no dialog — its detail pane is driven by a CallLogEntryData, so there is nothing to show until the entry for that caller has arrived, and the effect re-runs on entries until it can find one. Marking the request applied before that would silently swallow the tap.

8. Every test passed and the emulator looked fine, yet picking a contact was broken on a phone. What was it, and what class of bug is it?

With the soft keyboard up, the results list pushed the Call button off the bottom of the screen, so picking a contact hid the button that places the call — a layout bug that only exists at a real viewport with a real IME. It belongs with Chapter 22's warning cards and Chapter 24's clipped Home screen: assertExists is true of a node nobody can reach. The fix, focusManager.clearFocus(), is one line that no amount of code review would have produced, because the defect was in the geometry rather than the logic.

9. An outgoing call is stored with action = ALLOWED. Why must the call log not display it as "Allowed call"?

Because "allowed" is a claim about screening and the call was never screened — the engine refuses to evaluate calls the user placed. ALLOWED is what the column's CHECK constraint leaves available (and it usefully keeps outgoing rows out of the blocked-call counters), but a storage constraint is allowed to force a value, not a sentence. The row is labelled from its direction instead.

10. The direction migration drops and rebuilds the table. What two things must the migration do that SQLite does not do for you — and which of them is a compiler artefact rather than a runtime one?

It must recreate the index, because DROP TABLE takes indexes with it and losing idx_call_log_action_time silently turns three Home-screen counters into full table scans. And it must DROP INDEX explicitly first — that one changes nothing at runtime, since the drop already removed it; it exists because SQLDelight's migration compiler does not model that and otherwise refuses the file with "Duplicate index name".

27The Notification That Hung Up on the User

Four bug reports arrived together: the system's missed-call notification still appears; when the other person answers, the platform phone app takes over; the call log needs filters; the call screen should show the app's icon. Three of them were the same bug, and it was not in any of the code the reports pointed at.

Learning Objectives

  • Read a user-visible symptom back to a process death in logcat
  • Know which platform APIs refuse work by throwing, and what that costs on a callback thread
  • Understand what Telecom does when the default dialer dies mid-call
  • Suppress a platform notification the supported way, by declaration rather than by force
  • Separate filters that re-query from filters that narrow what is already loaded

Beginner Four symptoms, one stack trace

None of the four reports mentioned a crash — the phone kept working, it just stopped being this phone app. The device disagreed:

FATAL EXCEPTION: main
java.lang.IllegalArgumentException: 0|org.carlospinan.cortaspam|1002|null|10728 Not posted.
  CallStyle notifications must be for a foreground service or user initated job
  or use a fullScreenIntent.
    at IncomingCallNotifier.notifyOngoingCall(IncomingCallNotifier.kt:157)
    at PassthroughInCallService$stateCallback$1.onStateChanged(PassthroughInCallService.kt:156)
Process org.carlospinan.cortaspam (pid 24913) has died: fg TOP

Notification 1002 is the "return to call" notification, posted the instant a call goes ACTIVE. So the app died precisely when the other person picked up — and three of the four reports follow from that one line:

  • "The system phone app takes over." Telecom answers a dead default dialer by handing the live call to the preloaded one. It is documented behaviour, not a bug in the fallback.
  • "The call screen has no app icon." The screen drawing that icon went down with the process; what remained on screen belonged to another app entirely.
  • "The system's missed-call notification still shows." With this app's process gone, its own notification was never posted — only the platform's.
Why

Symptoms are reported from where the user is looking, which is rarely where the defect is. The cheapest possible first move on any Android report is adb logcat | grep -E "FATAL|died" — it cost thirty seconds here and collapsed four investigations into one.

Advanced APIs that refuse by throwing

From Android 14, CallStyle is restricted: the notification must belong to a foreground service, or a user-initiated job, or carry a full-screen intent. The restriction is reasonable — it stops any app dressing itself up as a phone call. What makes it dangerous is the mechanism: notify() throws, and this call site is on the main thread inside a Telecom callback, where nothing catches.

The ringing notification had been legal all along because it sets a full-screen intent, which is why months of testing never hit this: every test call was one that rings and is never answered.

// before — legal on API 33, fatal on API 34+
.setStyle(NotificationCompat.CallStyle.forOngoingCall(caller, hangUpPendingIntent))

// after — a plain ongoing notification does the same job with no restriction
.setContentText(context.getString(R.string.notification_ongoing_call))
.setContentIntent(contentPendingIntent)
.addAction(icon, context.getString(R.string.notification_action_hang_up), hangUpPendingIntent)
Gotcha

The second half of the fix is the catch clause. post() already swallowed SecurityException (permission revoked between check and post) but not IllegalArgumentException, and the two failures deserve identical treatment: a notification is never worth a live call. Widening it to RuntimeException means the next restriction the platform adds degrades to a missing notification instead of a dead phone app. That is only safe alongside a test that pins the shape — otherwise the swallow turns a loud bug into a silent one.

Verified

On a Pixel API 36 emulator, which enforces what the razr enforced: a simulated call answered, this app's InCallActivity still the resumed activity afterwards, the ongoing notification present with its Hang up action, the pid identical either side of the answer, and no FATAL EXCEPTION anywhere in logcat. Robolectric does not implement the restriction, so the unit test asserts the notification is not CallStyle rather than asserting a throw — restoring the old style turns it red.

Intermediate Suppressing a platform notification by declaration

The duplicate missed-call notification survived the crash fix, because it has a separate cause. Telecom decides in one line whether to post its own:

// MissedCallNotifierImpl
if (shouldManageNotificationThroughDefaultDialer(dialerPackage, userHandle)) {
    sendNotificationThroughDefaultDialer(...);   // and posts nothing itself
    return;
}
// ...which is true when queryBroadcastReceivers finds a receiver for
// ACTION_SHOW_MISSED_CALLS_NOTIFICATION in the dialer package.

The test is that the receiver exists. Declaring one in the manifest is the whole fix — and it is worth noticing that this app then never receives the broadcast, because Telecom sends it with READ_PHONE_STATE and this app deliberately does not hold that permission (Chapter 21). The declaration buys suppression; the notification the user sees is the one the app posts from the missed call itself.

Contrast

The alternatives are all worse. A NotificationListenerService that cancels the platform's notification asks the user for one of the most invasive permissions Android has, to undo something the framework offers to stop doing. Adding READ_PHONE_STATE to receive a broadcast this app does not need would reopen a Play-policy question already settled. When a platform posts something you do not want, look for the delegation hook before reaching for the override.

Intermediate Two kinds of filter

The fourth report — filters for the log — has no bug in it, but it does have a design decision. Three controls, deliberately not one mechanism:

// pure, over what is already on screen: runs on every keystroke
val visible = remember(entries, directionFilter, query, contactNames) {
    filterCallLog(entries, directionFilter, query, contactNames)
}

// a re-query, and also a navigation destination (Home links straight to "today")
onTimeFilter = { callLogViewModel.onIntent(CallLogIntent.SetFilter(it)) }
Why

Direction and outcome share one chip row rather than being independent filters, because "outgoing" and "blocked" together match nothing, ever — two rows would let the user assemble an empty screen and reasonably conclude the app was broken. For the same reason "Incoming" keeps blocked calls: a blocked call is an incoming call that was refused, not a third direction.

And an empty filter result gets its own message. The empty-log hint — "no calls yet, add a number to start blocking" — is advice when the log is empty and a wrong diagnosis when a search simply matched nothing.

Case Study: the test that could not have caught it

This bug lived behind three separate green signals. The unit tests posted the notification through Robolectric, which does not implement the platform restriction. The emulator in daily use was API 33, one level below where the rule starts. And every manual and scripted call test — ring_test.sh, rule_matrix_test.sh, every emulator scenario in this course — exercised calls that ring, get blocked, or get missed. Not one of them ever answered a call, because on an emulator there is nobody on the other end worth answering.

The gap was not in the assertions. It was in the state space: ACTIVE was a call state the suite had never entered. A blocked-call app can be forgiven for testing the blocking hardest, but it takes the dialer role, and the dialer role means the ordinary, boring, answered call is a first-class path.

The fix for that is not more tests of the same shape. It is asking, of any state machine the app is handed: which states has nothing ever put us into?

  • No platform call that can throw sits uncaught on a callback that a live call depends on

  • Filters that re-query and filters that narrow are visibly different code paths
  • You can name a state your test suite has never reached

Check Yourself

1. Three of the four reported symptoms had one cause. What was the chain from that cause to "the system phone app takes over"?

Posting a CallStyle notification without a foreground service, user-initiated job or full-screen intent throws on Android 14; the throw happened on the main thread inside a Telecom Call.Callback, so the process died the moment a call was answered. Telecom responds to a dead default dialer by handing the live call to the preloaded dialer — so the "takeover" was the documented fallback doing its job. The vanished app icon and the missing missed-call notification are the same death seen from two other angles.

2. Why had the ringing notification never crashed, when it uses CallStyle too?

Because it sets a full-screen intent, which is one of the three things the restriction accepts — it has to, in order to appear over the lock screen. The ongoing notification had no foreground service, no user-initiated job and no full-screen intent, and a full-screen intent is exactly what it must not have: it is a return-to-call affordance, not something that should seize the screen.

3. post() now catches RuntimeException. When is broadening a catch like that defensible, and what makes it dangerous?

Defensible when the operation is strictly less important than the context it runs in — a notification against a live phone call — and when the failure has a sane degraded state, here "no notification". Dangerous because it converts loud failures into silent ones: the same bug, swallowed, would have shown up as a mysteriously missing notification instead of a crash. That is why it ships with a test pinning the notification's shape; the swallow handles the unknown future rejection, the test handles the known one.

4. How do you stop Telecom posting its own missed-call notification, and what is the test it applies?

Declare a broadcast receiver for ACTION_SHOW_MISSED_CALLS_NOTIFICATION in the default dialer's manifest. MissedCallNotifierImpl.shouldManageNotificationThroughDefaultDialer runs queryBroadcastReceivers against the dialer package: if a receiver exists it delegates and posts nothing itself. The test is the receiver's existence, not what the receiver does — which is why this works even though the app never actually receives the broadcast.

5. Why does this app not receive the broadcast it declared a receiver for, and why is that acceptable?

Telecom sends it with sendBroadcastAsUser(..., READ_PHONE_STATE), and the app deliberately does not hold READ_PHONE_STATE — a Play-policy decision from Chapter 21. It is acceptable because the notification the user sees is the one the app already posts from handling the missed call itself; the declaration was only ever needed to stop the duplicate. Adding the permission to receive a broadcast the app does not need would trade a settled policy question for nothing.

6. The date chips go through the ViewModel while the direction chips and the search box do not. Why the split?

A date window changes which rows are loaded, so it is a re-query — and it is also a navigation destination, since Home's cards link straight into "today". Direction and text only narrow rows already in memory, and they change on every keystroke, so routing them through the data layer would put a database round-trip behind each character typed.

7. Three green signals hid this bug. Name them, and say what would actually have caught it.

Robolectric does not implement the CallStyle restriction; the day-to-day emulator was API 33, one level below where the rule begins; and every call test in the project — scripted or manual — covered calls that ring, get blocked or get missed, never one that was answered. What catches it is entering the state nothing had entered: answering a call on an API 34+ device. The defect was not in the assertions but in the state space they covered.

28The Fix That Was Only Half Applied

Three days after "contacts saved nationally are not allowlisted" was fixed, tested and shipped, the same complaint came back: sometimes a contact is blocked even though it is in the agenda. The comparison function was right. Its caller had quietly disarmed it.

Learning Objectives

  • Recognise a fix that is correct in isolation and inert in place
  • Write the contract a function needs from its callers where the callers can see it
  • Tell a fact about an event apart from a fact about current state, in data and in UI
  • Extract a pure function out of a cursor loop so a test can reach it at all
  • Spot a shell guard that can never execute under set -e -o pipefail

Beginner Two facts that look like one

A call log row carries two different claims, and the app had only ever shown the first:

  • What happened to this call — action = "BLOCKED", written once, at the moment the call arrived. History. It never changes.
  • Whether this number is on a list right now — a question about the rule set as it stands, which the user edits constantly.

They disagree all the time. A call blocked last week by a rule since deleted is still a blocked call. A call that rang through yesterday may be from a number blocked this morning. The log showed only the first and offered "Block this number" regardless — so blocking an already-blocked caller was a tap that did nothing anyone could see, which is indistinguishable from a broken button.

Intermediate The contract that lived in the wrong file

PhoneNumberParser.sameNumber decides whether the national form may bridge two numbers, and it decides it by looking for a leading +:

val aIsInternational = toE164OrNull(a) != null
val bIsInternational = toE164OrNull(b) != null
if (aIsInternational && bIsInternational) {
    // Both know their country; only the full E.164 digits can make them the same.
    return toE164OrNull(a) == toE164OrNull(b)
}

Meanwhile the address-book scan built the set it would be compared against like this:

numbers.add(PhoneNumberParser.normalizeForComparison(raw))  // digits only — the '+' is gone

So a contact saved +34611998877 reached sameNumber as 34611998877, which states no country. The function could no longer derive the national key 611998877 from it, and a call delivered in national form — ordinary for a domestic call — stopped matching. The contact was not allowlisted, and the next rule down the precedence list blocked someone the user has in their phone.

The cruel part: the contact's name displayed correctly throughout, because the name map is keyed by every comparisonKeys form and was never wrong. The user sees a familiar name on a blocked call and reasonably concludes the app is broken in some unfathomable way.

The fix is one line. The durable part is where the requirement now lives — on the interface every caller reads:

/**
 * Phone numbers from the user's local contacts, **exactly as saved on the card**.
 *
 * Not normalized, and not digits. RulePrecedenceResolver compares this set with
 * PhoneNumberParser.sameNumber, which reads the leading '+' ...
 */
suspend fun contactNumbers(): Set<String>

Advanced Making the untestable testable, then proving it on a phone

The broken mapping lived inside a ContentResolver cursor loop — a place no unit test in this project could reach, which is why nothing caught it. The loop was split: reading rows stays in the gateway, deciding what a row means moves to a pure function that takes rows and returns a snapshot. Ten unit tests now hold that boundary, with no Android framework class in sight.

@Test
fun contactSavedInE164IsMatchedByANationalFormatCall() {
    val snapshot = snapshotOf("+34611998877" to "Ana Torres")
    assertTrue(snapshot.numbers.any { PhoneNumberParser.sameNumber(it, "611998877") })
}

Watched failing first, against the old line: got [34611998877]. Then the same claim was made on a real call path, as phase F of rule_matrix_test.sh — a contact saved internationally, called from a domestic line, under a default action of BLOCK so only the contacts path can let it through. Reverting the fix, rebuilding and reinstalling produced the user's report verbatim:

=== phase F — a contact saved internationally, called from a domestic line ===
    FAIL contact '+34900123456' vs 900123456    expected ALLOWED/CONTACTS, got BLOCKED|-

Phase E — the 08-11 regression, the opposite direction — passed against that same broken build. That is the whole argument for adding F rather than trusting E.

Case Study: the guard that had never once run

Phase E looks for a national-format contact and skips itself politely when the address book has none. On an emulator whose contacts are all +34…, it did not skip. It killed the script:

NAT=$($ADB shell content query ... | sed -n 's/.*data1=//p' | grep -v '^+' | head -1 | tr -cd '0-9')

grep -v exits 1 when it filters everything out — which is precisely the condition this line exists to detect. Under set -e -o pipefail that ends the script on the spot: no result, no reason, no summary, exit 1. The if [ -n "$NAT" ] below it, and the friendly SKIP message inside it, had never executed in the script's life.

It joins a list this project keeps rediscovering — the ringer that never rang, the spam list that could never match, the permission warning nobody could reach. Code that only runs on the unhappy path is code that has probably never run at all. The fix is four characters (|| true); the lesson is that the unhappy path deserves a test as much as the happy one.

Intermediate Saying what a feature cannot do

"Call recording is not working" turned out to be three different truths at once. Recording only ever runs on a call the auto-responder itself answered, so with the auto-responder off the switch was inert — and the screen said nothing. That reason is now computed, and testable:

fun recordingReadiness(config: AutoResponderConfig, micPermissionGranted: Boolean = true) =
    when {
        !config.recordingEnabled -> RecordingReadiness.Off
        !config.enabled          -> RecordingReadiness.AutoResponderOff
        config.validate() !is ValidationResult.Ok -> RecordingReadiness.GreetingInvalid
        !micPermissionGranted    -> RecordingReadiness.MicPermissionMissing
        else -> RecordingReadiness.Ready
    }

The other two truths cannot be computed at all. Android reserves the real call-audio sources behind CAPTURE_AUDIO_OUTPUT, a signature|privileged permission the dialer role does not grant, so recording captures the microphone acoustically — and several manufacturers hand the microphone exclusively to the telephony stack during a call. Whether that happens is knowable only on that device, at that moment. So the screen says it in prose instead of pretending to predict it. A limitation the user can read is not a bug report.

Advanced Two escapes, one of them shipped for months

This project has two string tables that look identical and are not. Under androidApp/src/main/res, aapt2 parses the file and \' is the required spelling of an apostrophe. Under shared/src/commonMain/composeResources, the Compose loader reads plain XML, where a backslash means nothing — so it survives into the UI:

The greeting plays through your phone\'s loudspeaker

Found by screenshotting the screen on a device, which also revealed that blocklist_duplicate_blocked_body had been showing won\'t override the block for as long as it has existed. Nothing could have caught it: it compiles, the translation-completeness test only counts keys, and Android Lint cannot see that resource tree at all. Key Takeaways

  • A correct function with one normalising caller is a broken feature
  • Put the contract on the interface, not in the commit message
  • "What happened" and "what is true now" are two facts; a UI that merges them lies about one
  • Extracting a pure function out of an I/O loop is usually what makes the bug reachable
  • grep -v exiting 1 on an empty result will kill a set -e script at the exact moment its guard was meant to speak
  • State a platform limit in the UI; the alternative is a user reporting the platform as your bug

Check Yourself

1. sameNumber was already fixed and tested. How was the feature still broken?

Its caller normalised first. AndroidContactsGateway put normalizeForComparison(raw) into the set, stripping the + that sameNumber reads to decide whether the national form may bridge two numbers. Every existing test passed the function well-formed numbers directly, so the function was proven and the path through it was not.

The name map is keyed by every comparisonKeys form of each contact, so lookups by any spelling hit. Only the numbers set was digit-normalised. It tested the opposite direction: a contact saved nationally, called in E.164. That direction survives digit-normalisation, because a national contact has no + to lose. The broken direction is a contact saved in E.164 called nationally. Proven, not argued: phase E passed against the deliberately reverted build while phase F failed on it.

4. A row reads "Blocked call" and carries no "On your block list" badge. Is that a bug?

No — it is the design. The label is what happened to that call; the badge is whether the number is on a list now. A call blocked by the default action, or by a rule the user has since deleted, is exactly this combination. Merging them would either rewrite history or claim a rule that no longer exists.

5. Why does the block/unblock action carry a rule id rather than a phone number?

Unblocking has to delete a specific row, and the row's number may be spelled differently from the call's — matched by sameNumber, not equality. Passing the number back would force the data layer to re-derive which rule was meant, and get it wrong for exactly the numbers this chapter is about.

6. Under set -e -o pipefail, why did a pipeline ending in grep -v '^+' kill the script?

grep exits 1 when it selects no lines, and -v selects nothing when every line matches the pattern being inverted — here, an address book that is entirely international. pipefail propagates that as the pipeline's status and set -e exits. The condition the line was written to detect was the condition that stopped it reporting anything.

7. Recording is switched on and nothing is ever recorded. Which reasons can the app state, and which can it not?

It can state that the auto-responder is off, that the greeting fails validation, and that RECORD_AUDIO is not granted — all readable from config and permission state, and all covered by RecordingReadiness. It cannot state that this handset's telephony stack will refuse the microphone mid-call: that is knowable only on the device at the moment of the call. So it is documented in prose on the screen rather than predicted.

8. Why is \' right in one strings.xml and wrong in another?

Because two different parsers read them. aapt2 processes Android resources and requires the escape. Compose Multiplatform resources are read as plain XML, where a backslash is a literal character — so the escape reaches the user. A bare ' is valid XML, which makes the fix "delete the backslash" and the test "fail on any \' under composeResources".

29What Replacing the Phone App Actually Costs

Taking ROLE_DIALER is usually described as a permission. It is closer to an assumption of debt. Every capability the platform dialer had and yours does not is now a capability the user has lost — and they did not lose it to a bug, they lost it to your install. This chapter is about finding those, and about a related failure: a feature that was fully built, fully tested and reachable from four buttons, and still did nothing.

Learning Objectives

  • Audit a role-taking app by subtraction: list what the thing you replaced could do
  • Send DTMF correctly, and know why a tone stopped in the same frame may not arrive
  • Decide where transient in-call state lives when the activity can be recreated under it
  • Read a compiler warning as a bug report rather than as noise
  • Tell a version constant apart from a version reading, and know which one can lie
  • Separate a credit given as a courtesy from one given as a licence obligation

Beginner The audit that starts with a list of losses

The app had shipped a call screen with three buttons: Answer, Decline, Hang up. Everything on it worked. Nothing on it was wrong. And a user who set Corta Spam as their phone app could no longer ring their bank, because "press 1 for accounts" needs a keypad and there was not one anywhere on a connected call.

That class of defect does not show up in a bug list, because nothing is broken. It shows up in a subtraction: write down what the app you replaced could do, then tick off what yours does.

  • Answer / decline / hang up — present
  • Keypad during a call — absent
  • Mute, speaker, Bluetooth route, hold, merge, call timer — absent
  • Reject-with-message, silence-ringer — absent
  • Delete one call-log entry — absent (only "clear all")
  • Voicemail speed dial, favourites — absent
  • Dark mode — absent, on every screen, including the one that appears full-screen at 3am

Some of those are scope decisions and some are omissions, but you cannot tell which until the list exists. The list is the deliverable.

Intermediate DTMF is not "send a character"

Telecom exposes two calls, and they are a pair:

call.playDtmfTone(digit)   // starts a tone; ends any tone already playing
call.stopDtmfTone()        // ends it

The naive implementation calls both in the same frame. It compiles, it looks right, and on some networks it drops digits. ITU Q.24 only obliges a receiver to recognise a tone of roughly 40 ms or more; a tone whose stop is dispatched immediately may be shorter than that by the time it reaches the far end. A menu that loses every other digit is indistinguishable, to the user, from a keypad that does not work.

So the tone is held, and the pending stop is replaceable:

fun playDtmf(digit: Char) {
    val call = call ?: return
    val current = _state.value ?: return
    call.playDtmfTone(digit)
    dtmfHandler.removeCallbacks(stopDtmfTone)
    dtmfHandler.postDelayed(stopDtmfTone, DTMF_TONE_MILLIS)
    _state.value = current.copy(dtmfDigits = current.dtmfDigits + digit)
}

Cancelling the pending stop first is what makes fast typing work: playDtmfTone already ends whatever was playing, so without the cancel an earlier stop would cut the newer tone short. And the pad is offered only on an ACTIVE call, because Telecom discards a tone played on one that is still ringing or dialling — a keypad that is present but inert is worse than one that is absent, since the user blames themselves.

Trade-off

AOSP's own dialer plays on touch-down and stops on touch-up, which supports holding a key. A fixed hold is simpler, keeps TalkBack's synthesised click working, and cannot leave a tone stuck on if a release event is lost. The cost is that you cannot hold # for a menu that wants a long one. That is a real capability gap, and it is written down rather than hidden.

Intermediate Where transient in-call state belongs

The digits already sent look like local UI state. They are not, and the reason is a property of the medium: DTMF is fire-and-forget. Nothing on the line echoes a digit back. If the user is nine digits into a sixteen-digit card number and the activity is recreated, the only record of what has already gone is whatever the app kept.

So dtmfDigits lives on the object that outlives the activity, beside the call itself:

data class UiState(
    val number: String,
    val phase: CallUiPhase,
    val displayName: String? = null,
    /** The DTMF tones sent on this call so far, in the order they were pressed. */
    val dtmfDigits: String = "",
)

Whether the pad is open, by contrast, is genuinely local — losing it costs one tap. The test is not "is this UI?" but "what does the user lose if it disappears?"

Case Study: the cast the compiler had already rejected

Home has four tiles — Blocked today, This week, This month, Pending review. Each navigates to call_log/<filter>. All four showed the unfiltered list.

@Suppress("UNCHECKED_CAST")
val filter = (backStackEntry.arguments as? Map<String, *>)?.get("filter") as? String ?: "all"

NavBackStackEntry.arguments is a SavedState (a Bundle on Android). It has never been a Map. The compiler said so on every single build — w: This cast can never succeed — and three things conspired to make that harmless-looking:

  • A @Suppress("UNCHECKED_CAST") sitting above it, which reads like the warning had been considered.
  • as?, which converts an impossible cast into null instead of an exception.
  • ?: "all", which turns that null into a perfectly plausible value.

Every layer either side was fine. AdaptiveRoutes.callLogRoute("today") built the right route. CallLogViewModel.applyFilter handled "today", "week", "month" and "review" correctly, and its unit tests passed — because they call it directly. The dead step was the single line between the route and the ViewModel, which is exactly where a component test does not look.

val filter = backStackEntry.arguments?.read { getStringOrNull("filter") } ?: "all"

Two lessons, and the second is the durable one. A warning you have suppressed is a warning nobody will read again. And a defaulting operator — ?:, orEmpty(), getOrElse — makes a failure indistinguishable from the ordinary case. Use them where the fallback is genuinely correct, not to make a compiler complaint go quiet.

Advanced A version number that cannot lie

The app had no screen anywhere that said which build was installed. That is not cosmetic: this project has spent six Play version codes, several of them differing only in an answer on a Console form, and a bug report that does not establish the build costs a round trip before anyone can even ask whether the fix is in.

The tempting implementation is a constant in commonMain. It is also the wrong one, because it creates a second version number — one that is updated by remembering to, and that will eventually disagree with the artifact it is printed on. A version row that can disagree with its own build answers nothing.

Read it from the platform's own package metadata instead, and supply it through DI:

fun Context.readAppVersion(): AppVersion =
    try {
        val info = packageManager.getPackageInfo(packageName, 0)
        AppVersion(
            name = info.versionName.orEmpty().ifBlank { AppVersion.Unknown.name },
            // Not info.versionCode: from API 28 the code is a long, and the int field truncates.
            code = PackageInfoCompat.getLongVersionCode(info),
        )
    } catch (_: PackageManager.NameNotFoundException) {
        AppVersion.Unknown
    }

Both numbers are shown, 1.4.0 (6). A tester who says "I'm on 1.4.0" has not said whether they are on the upload that fixed anything — the code is what a store increments per upload and what settles which of two builds is newer. The iOS side reads CFBundleShortVersionString and CFBundleVersion from the bundle, with the same shape and the same fallback.

Advanced Two kinds of credit

The Credits screen had shipped reachable and empty for a release, saying "names are on the way". Filling it raised a design question that looks like formatting and is not: a person and a library are not owed the same thing.

  • A person is credited as a courtesy. You choose the wording, and you can leave it out.
  • An Apache-2.0 or MIT library is credited because its licence asks to be. The SPDX identifier is the part that discharges the obligation, and it is not optional.

Flattening both into one list would let a licence obligation read as a thank-you note, so they are separate sections with separate types. Two smaller decisions follow from the same reasoning:

  • Contribution lines are deliberately not localized. A resource key per person means a build failure every time someone is added without all four locales — and a credit is a factual attribution, not app copy.
  • Test-only and build-only dependencies are absent. Nothing of Robolectric or the Gradle plugins reaches a device, so listing them would misstate what is running.

The test that came with it is the one worth copying. The existing tests all passed lists in, so the covered state was the empty placeholder — precisely the shape that lets a screen keep saying "names are on the way" forever. The new test renders the defaults:

composeTestRule.setContent { CreditsScreen(onBack = {}) }

composeTestRule.onNodeWithText("Names are on the way", substring = true).assertDoesNotExist()

Done when

  • You can name, in writing, every capability the app you replaced had and yours does not
  • No compiler warning in the build is being suppressed rather than answered
  • Any number the app displays about itself is read from the artifact, not declared beside it
  • The state a test renders by default is the state users get, not the placeholder
  • Every shipped third-party licence is discharged on a screen the user can actually reach

30The Second Call, and Other States You Never Reach

Chapter 29 audited by subtraction — what could the app you replaced do that yours cannot. This chapter is what happened when that list was worked through. Four of the five findings were not missing features at all. They were states the code could reach and the developer could not, and every one of them had a passing test suite sitting beside it.

Learning Objectives

  • Recognise a single field standing in for a collection, and the family of bugs it produces
  • Extract logic out of an untestable platform type without pretending you have tested the type
  • Make an enum's default case safe when the default is "block the call"
  • Use exhaustiveness as a safety mechanism, not a style preference
  • Tell a theme that is missing from one that is merely wrong
  • Design a safety exemption around the signals you can get without a permission

Beginner One field pretending to be a list

The in-call state holder had this shape for its whole life:

private var call: Call? = null

Which is fine, right up until Telecom hands over a second call. Then:

  • attach(b) overwrites a. The screen now shows b.
  • detach(b) sees this.call === b, sets the state to null, and the activity finishes — while a is still connected.
  • The ongoing-call notification survives, but its Hang up action calls call?.disconnect() on a null field and does nothing.

The user is on a live call, with no call screen, and the app's own hang-up button is inert. And because this app is the default dialer, there is no second phone app to fall back to.

Three more bugs came out of the same field, and they are worth listing because they are the same mistake wearing different clothes:

  • The Call.Callback was registered on every call and wrote _state.value?.copy(phase = …) for whichever one changed — so a background call's state change rewrote the phase of the call on screen.
  • setDisplayName(number, name) compared against the on-screen call and dropped anything else. A name resolved for a call that had since been backgrounded was discarded forever, even when that call came back.
  • A DTMF tone is started and stopped by two separate calls. The stop was posted against "the current call", so a tone held when its own call ended was stopped against whatever call was on screen by then.

A nullable field is a collection with a capacity of one, and the platform decides the capacity.

Case Study: testing around a type you cannot construct

android.telecom.Call is final, has no public constructor, and ships no Robolectric shadow. The existing test file said so, in a comment that also explained why the whole file only tested the null-call paths:

* What is not covered, and why: attach/detach, the Call.Callback phase mapping, and
* answer/decline/hangUp actually reaching a call all need a real android.telecom.Call.

That comment was honest and correct, and it is also the reason the bug survived. The fix is not to mock the type — this project bans mocking libraries so its tests can run on Kotlin/Native — but to notice that none of the broken logic is about Call at all. "Which of these is on screen, and what happens when one ends" is a decision about a list.

internal class CallStack<T : Any>(
    private val isRinging: (T) -> Boolean,
) {
    fun remove(call: T): Removal {
        val wasPrimary = primary === call
        calls.removeAll { it === call }
        if (!wasPrimary) return Removal.Unchanged
        // A call the user must answer or decline outranks one they are already on.
        val next = calls.firstOrNull { isRinging(it) } ?: calls.lastOrNull()
        primary = next
        return if (next == null) Removal.Empty else Removal.Promoted
    }
}

Two details earn their keep. isRinging is a function, not a snapshot taken at add time — the state must be read at the moment the decision is made. And identity (===) is used throughout, because Call does not override equals and two distinct calls can describe the same number.

Be honest about what this buys. The promotion logic is now under test; registerCallback, disconnect and playDtmfTone still are not. Extracting a decision does not test the platform call around it, and a chapter that claimed otherwise would be teaching the same false confidence this book keeps documenting.

Intermediate When the default case is "block the call"

The screen mapped Telecom's states to four UI phases:

Call.STATE_RINGING -> CallUiPhase.RINGING
Call.STATE_DIALING, Call.STATE_CONNECTING -> CallUiPhase.DIALING
Call.STATE_ACTIVE -> CallUiPhase.ACTIVE
else -> CallUiPhase.OTHER

and rendered OTHER as Unit — no buttons. Which states land there? STATE_HOLDING, STATE_DISCONNECTING, STATE_SELECT_PHONE_ACCOUNT (every dual-SIM outgoing call), STATE_SIMULATED_RINGING, STATE_PULLING_CALL, STATE_AUDIO_PROCESSING. A caller's name, and nothing to press.

The fix is not "handle every state" — it is to decide what the unhandled case means. Here, ending the call is the escape hatch that is valid in every state, so OTHER keeps a hang-up button. Exactly one phase still shows nothing, and for a reason: DISCONNECTING, where the thing the button would do is already happening.

Advanced Exhaustiveness as a safety mechanism

The rule engine had this:

val isBlocked: Boolean
    get() =
        this !is Allowlist &&
            this !is DefaultAllow &&
            this !is PendingReview &&
            this !is AllowedAfterRepeatedAttempts

Read the failure mode: add a new RuleDecision variant and this compiles, runs, and classifies it as blocked. In a call blocker, the silent default is the destructive one. Adding an "allowed because the user just called an ambulance" decision to that chain is exactly the mistake it invites.

val isBlocked: Boolean
    get() =
        when (this) {
            is Allowlist, is DefaultAllow, is PendingReview,
            is AllowedAfterRepeatedAttempts, is EmergencyExempt,
            -> false

            is ManualBlock, is PatternBlock, is CountryBlock, is SpamHit,
            is ActionBlock, is ScheduleBlock, is DefaultBlock,
            -> true
        }

Same behaviour, more lines, and the build now stops until the next variant says which side it is on. Where the fall-through is dangerous, spend the verbosity.

Advanced A safety exemption built from the signals you can actually get

A callback from the emergency services arrives from a number that is not in the address book. With the default action set to BLOCK, or inside quiet hours, or under a country rule, this app blocked it — and with the auto-responder switched on it answered it, read a greeting, and hung up, with nothing to tell the user it had happened.

The obvious implementation is TelephonyManager.isEmergencyNumber, which reads the list the SIM and network actually provisioned. It also requires READ_PHONE_STATE, a permission this app deliberately does not declare and has a manifest comment explaining. Adding it for this would trade a documented permission posture for one feature — and this project has already been rejected twice by Play over permission questions.

So the design is built from what is available without one:

  1. Call.Details.PROPERTY_EMERGENCY_CALLBACK_MODE — the platform's own answer, read off the call. Authoritative, permission-free, and covers exactly this window.
  2. The last time this app saw the user dial a number it recognises as an emergency number. The fallback for networks that never enter callback mode, persisted rather than held in memory because the process can die between the emergency call and the callback.

Two constraints fall out and both are worth internalising. The number list is used in one direction only — recognising a number the user dialled, never classifying an incoming caller ID, because a callback rarely arrives from the number that was dialled and a blocker that trusted caller ID for this would be trivially spoofable. And a clock that has moved backwards must not close the window:

// Not `elapsed in 0 until WINDOW`. A clock that has moved backwards since the emergency
// call gives a negative elapsed, and the two ways to be wrong here are not the same size:
// a spam call let through is a nuisance, an ambulance silently rejected is not.
return nowMillis - lastEmergencyCallAtMillis < CALLBACK_WINDOW_MILLIS

What it does not cover is stated rather than hidden: a callback arriving after the window has closed cannot be identified without that permission, so the setting says "30 minutes" instead of implying open-ended protection.

Intermediate A theme that was missing, not wrong

Every screen in the app opened MaterialTheme { } with no arguments. That is not "the default theme" — it is Material 3's baseline palette: light, and purple, regardless of the system setting. So the app had no dark mode at all, on a screen that appears full-screen at whatever hour someone rings.

The interesting part is where the theme goes. The instinct is one wrapper at the root of the navigation graph. That would have been wrong here, and the reason generalises: InCallActivity draws CallScreen outside the nav host entirely, and every Robolectric screen test renders one screen with no host at all. A screen that themes itself is correct in all three settings.

Case Study: the test that agreed with itself

Proving that screens use the new theme turned out to be harder than writing it. The first attempt:

composeTestRule.setContent {

The obvious repair, rendering the screen under a night qualifier and reading a pixel, does not work either: captureToImage() times out under Robolectric because PixelCopy never redraws. So the invariant is checked where it can be checked — in the source:

val offenders = root.walkTopDown()
    .filter { it.isFile && it.extension == "kt" }
    .flatMap { file -> /* lines containing "MaterialTheme {" */ }
assertEquals(emptyList(), offenders,
    "these screens render on Material 3's baseline palette and have no dark mode")

Less elegant, and it genuinely fails against the reverted build — which the first one did not. This project already had two source-reading tests for the same reason (the apostrophe escape, the translation key sets). When the runtime cannot observe the invariant, checking the source is not a lesser test; it is the only one that is not a lie.

Done when

  • No single nullable field stands in for something the platform can hand you more than one of
  • Every state your UI can enter offers at least one action, or you can say why it should not
  • The fall-through branch of any safety-critical decision has been named and chosen, not inherited
  • A safety feature is built from signals you can obtain, and states in the UI what it cannot cover
  • Every test you kept has been watched failing against the bug it describes

Check Yourself

1. A second call arrives, the user declines it, and the call screen vanishes. What was the single line responsible?

`detach` checked `this.call === call` and, on a match, set the state to null. With one field, the second call had already overwritten the first, so declining it matched — and cleared the screen for a call that was still connected. The ongoing-call notification's Hang up then routed to a null field and did nothing.

2. Why extract CallStack as a generic type instead of mocking android.telecom.Call?

The type is final with no public constructor and no Robolectric shadow, and this project bans mocking libraries so the same tests run on Kotlin/Native. But none of the broken logic is about Call — "which of these is on screen, and what happens when one ends" is a decision about a list. Extracting it makes the decision testable without pretending the platform calls around it are.

3. Inside CallStack, why is isRinging a function parameter rather than a boolean captured when the call was added?

Because the decision happens later than the addition. A call that arrives outgoing is not ringing then and may be by the time another call ends and a promotion is needed. A snapshot would be stale exactly when it matters. Identity comparison is used for the same category of reason: Call has no equals, and two distinct calls can carry the same number.

4. CallUiPhase.OTHER rendered nothing. Why is "handle every Telecom state" the wrong fix?

Because the list grows with each platform release, so the fall-through will always exist — the question is what it should mean. Ending the call is valid in every state, so OTHER now offers it. Only DISCONNECTING deliberately shows nothing, because the action the button would trigger is already under way.

5. The !is chain and the exhaustive when compute the same value. What does the longer one buy?

A compile error when a new RuleDecision variant is added. The chain silently classified anything new as blocked, and in a call blocker the silent default is the destructive one. Verbosity is worth paying where the fall-through can drop a call.

6. Why is the emergency-number list used only for outgoing calls, never to recognise an incoming caller?

A callback almost never arrives from the number that was dialled, so matching incoming caller ID would rarely fire — and where it did fire it would be a spoofing hole, since caller ID is trivially forged. What the app can trust is what the user dialled on this device, plus the platform's own PROPERTY_EMERGENCY_CALLBACK_MODE.

31The Screen That Would Not Let Go

Chapter 30 ended on a sentence that reads differently now: "Exactly one phase still shows nothing, and for a reason: DISCONNECTING, where the thing the button would do is already happening." That reasoning is sound and it shipped a bug. The next report was three words long — calls cannot be hung up — and it was not about hanging up at all.

Learning Objectives

  • Separate "this control would do nothing" from "this screen has no exit"
  • Find every path by which a UI can outlive the thing it describes
  • Order a teardown method so a failure in the optional part cannot strand the essential part
  • Recognise a process-scoped singleton holding handles to a shorter-lived object
  • Render a platform toggle from the platform's report rather than from the last tap
  • Judge a new UI element by what it moves, not only by what it adds
  • State plainly which fixes an emulator can prove and which it structurally cannot

Beginner Two different questions about a button

"Should this state offer a hang-up button?" and "should this state offer a way off this screen?" look like the same question while there is exactly one button on the screen. They separate the moment the answer to the first is no.

The reported symptom was that ending a call left its screen up, with nothing to press. The user could not get back to the app, and could not get rid of the call screen. Three facts combined to produce it, none of them wrong on its own:

  • Telecom sets a call to STATE_DISCONNECTED and removes it later. How much later is the platform's business; on a real network it is seconds.
  • The state holder only cleared itself in onCallRemoved, so for that whole window the screen still had a call to render.
  • DISCONNECTING rendered no buttons — correctly, by the reasoning above — and BackHandler { moveTaskToBack(true) } deliberately refused to leave, because a previous chapter's bug was Back throwing away a live call's screen.

Each decision was defensible. Together they are a screen about a call that no longer exists, with no control and no exit, and Back explicitly declining to help.

A screen with no exit is a bug regardless of why it has no buttons. The two fixes are different in kind: the call control stays absent, and the screen gains a door.

// The call is already ending, so a hang-up button here would be a control
// for something the platform is doing anyway — but the screen still needs a door.
CallUiPhase.DISCONNECTING ->
    if (otherCallCount == 0) {
        TextButton(onClick = onDismiss) { Text(stringResource(Res.string.action_close)) }
    }

The otherCallCount == 0 guard is the interesting half. With a second call still on the line, leaving this screen takes away the only UI for the call that is still connected — which is the previous chapter's bug, re-entered through the new door.

Intermediate Counting the ways a screen outlives its call

One symptom, four independent routes to it. Fixing the one you can reproduce leaves three.

1. Waiting for permission to disappear. A disconnected call is over. Nothing is gained by asking the platform to confirm it:

override fun onStateChanged(call: Call, newState: Int) {
    if (newState == Call.STATE_DISCONNECTED) {
        detach(call)
        return
    }
    if (call !== primary) return
    _state.value = _state.value?.copy(phase = newState.toPhase())
}

2. The essential step scheduled behind the optional ones. InCallState.detach(call) — the single line that takes the screen down — was the last statement of onCallRemoved. Above it: stopping a MediaRecorder, cancelling two notifications, stopping the ringer. Any one of those throwing skips the line that matters.

override fun onCallRemoved(call: Call) {
    super.onCallRemoved(call)
    // First, before any of the bookkeeping below.
    InCallState.detach(call)
    // … recorder, notifications, ringer …
}

This is a general ordering rule and it is worth stating on its own: in a teardown method, put the step that restores the user's control first. Everything else — history rows, notifications, files — is bookkeeping, and bookkeeping must not be able to cost a person their phone.

3. A singleton outliving the objects it holds. InCallState is a Kotlin object: process-scoped. The Calls it holds are only usable through the InCallService's binding to Telecom, and the service is not process-scoped. Nothing cleared the state when that service was destroyed, so a teardown mid-call left a screen whose Hang up reached a dead adapter and did nothing — and left that dead call in the stack for the next call to promote back on to the screen when it ended.

override fun onDestroy() {
    super.onDestroy()
    InCallState.clear()
    // …
}

CallStack.clear() is deliberately not "remove them one at a time". Removing promotes the survivors; here every call became unreachable at the same instant, so there is no survivor to promote.

4. Back refusing to leave. Same handler, now asking which situation it is in:

val ending = current.phase == CallUiPhase.DISCONNECTING && current.otherCallCount == 0
BackHandler { if (ending) finish() else moveTaskToBack(true) }

Case Study: the emulator that answers too fast

The whole investigation ran on Pixel_8_Pro_API_36, and the bug never appeared once. Placing an outgoing call and reading dumpsys telecom a second later always showed state=ACTIVE: the emulator's fake modem answers immediately and tears the call down immediately. There is no observable STATE_DIALING and no call that lingers in STATE_DISCONNECTED — which is to say, the emulator cannot enter the state the bug lives in. Calling a second emulator does not help; it connects instantly too. Nor can it hold two calls: adb emu gsm call during an active call creates nothing at all, so call waiting is equally unreachable.

Every scripted suite passed on that device — schema and migration, ringing and silence, all fourteen rule-engine branches through real calls. Answering, muting, DTMF, hanging up, Back-and-return: all verified, all green. And none of it touched the defect.

The honest report separates the two claims, and the README says so in as many words: the fix is covered by Robolectric, the emulator proves the happy path, and the disconnecting state still needs a real phone and a call cancelled mid-dial. "Every test passed" and "the bug is fixed" are different sentences, and a chapter that let a green device run stand in for the second one would be repeating the mistake this book has documented since Chapter 20.

Advanced A toggle must show the world, not your last request

The same screen gained mute, speaker and a call timer — the things a phone app cannot ship without once it holds ROLE_DIALER, because anything missing here is missing from the phone. Mute and the audio route are not properties of a Call; they belong to the whole audio session, so Telecom puts them on the InCallService.

The tempting implementation keeps a local var muted and flips it on tap. It is wrong, and not subtly:

  • The auto-responder moves the route to the loudspeaker by itself, so a blocked caller can hear the greeting through the handset's microphone.
  • Plugging in a headset moves it back.
  • The platform can refuse a route that does not exist on the device.

In all three cases a locally-guessed button shows the opposite of the truth. The state comes from Telecom's own callback instead:

@Suppress("DEPRECATION", "OVERRIDE_DEPRECATION")
override fun onCallAudioStateChanged(audioState: CallAudioState) {
    super.onCallAudioStateChanged(audioState)
    InCallState.onAudioStateChanged(audioState)
}

The third bullet was visible immediately on the emulator, which has no earpiece: asking to leave the loudspeaker was refused, and the chip stayed selected. From a local flag that would read as a broken button. From Telecom's report it is the button working — the request was made and declined, and the UI says what is true.

Two details in the toggle itself. Leaving the speaker asks for ROUTE_WIRED_OR_EARPIECE, not ROUTE_EARPIECE: with a headset plugged in, naming the earpiece specifically sends the call to a handset nobody is holding. And the deprecation is real — CallAudioState gives way to CallEndpoint in API 34 — but minSdk here is 26, so the deprecated callback is the one that fires on the devices this ships to, and carrying both paths would gain nothing on any of them.

The timer looks trivial and has one decision in it. It follows the phase rather than starting once at connect, because a call that goes on hold and comes back is the same call, and a timer left running through the hold counts time the user was not on it. The formatting is a pure function in commonMain, unit-tested at the boundaries that make a timer look broken — 59 to 60 seconds, and the hour that must not appear before it exists:

@Test
fun `an hour appears only once there is one`() {
    assertEquals("59:59", formatCallDuration(3599))
    assertEquals("1:00:00", formatCallDuration(3600))
}

And one because connectTimeMillis is wall clock — the monotonic field is @hide — so a clock moving backwards mid-call can hand the formatter a negative number. -00:03 is a bug report; zero is merely wrong for a moment.

Case Study: the feature that moved the button

The same batch added "Create new contact" to the keypad, because taking ROLE_DIALER removed the app people used to save a number from. The intent is three lines and needs no WRITE_CONTACTS — the platform's own editor does the writing, with the user's accounts and sync.

The first attempt put the row among the contact search results, where the platform dialer puts it. Five existing tests failed immediately — not the new one, five old ones, all of the form "type a number, press Call, assert the callback fired". The callback had not fired. The taps were landing on nothing, because one extra row above the pad had pushed the Call button past the bottom of a scrolling screen.

That is the same bug already recorded in Chapter 26, where the soft keyboard pushed the results list up and hid the button that places the call. It came back through a feature that had nothing to do with layout.

// Below the Call button, not among the search results, and that placement is the
// whole point: anything added above the pad pushes Call towards the bottom of the
// screen. Nothing above this line moves.
if (typed.isNotBlank()) {
    TextButton(onClick = { onAddContact(typed) }) { … }
}

Review a new UI element by what it moves, not only by what it adds. The tests that caught this were not testing the new feature; they were testing that the old one was still reachable, which is what a regression suite is actually for.

Intermediate The lookup the codebase had already documented as wrong

The last of the batch: an outgoing call showed a bare number where the app it replaced showed a name. resolveCallerName asked ContactsContract.PhoneLookup, which matches through the provider's data4 column — normalized from the device's region at save time. A contact saved nationally does not match an E.164 call unless the phone's region agrees, and with no SIM data4 is null and every contact in the address book reads as a stranger.

None of that was news. It is written on this project's own isKnownContact, in Chapter 23, and it is the reason the call log gets names right. The call screen simply asked a different oracle than the rest of the app.

When a codebase already documents an API as unreliable, every remaining caller of it is a bug that has not been reported yet. Grep for the API, not for the symptom.

The fix keeps PhoneLookup first and falls back to the gateway, for a reason worth naming: the fallback is the slower question. It runs on the call-setup path, and the gateway's five-minute cache is cold on the first call after any change.

Advanced A condition with two halves that move separately

The same screen later gained the thing every phone app has and this one did not: it turns off while the handset is against an ear. That mattered more after the previous section than before it — a screen carrying one button can survive a cheek; a screen carrying Mute, Speaker and Hang up cannot.

PROXIMITY_SCREEN_OFF_WAKE_LOCK is worth knowing precisely because of what it is not: it can only blank the display, never keep it awake, and it is sensor-driven, so holding it costs nothing while the phone is on a table. The decision about when to hold it goes where every other decision in this package goes — a pure function, because the activity cannot be constructed in a test and blanking at the wrong moment takes the screen away from someone trying to press something:

fun shouldBlankScreen(phase: CallUiPhase, speakerOn: Boolean): Boolean {
    if (speakerOn) return false
    return phase == CallUiPhase.ACTIVE || phase == CallUiPhase.DIALING
}

RINGING is absent deliberately, and it is the case worth testing explicitly: Answer and Decline are the screen for an incoming call, and a phone that rang in a pocket must not arrive at the ear already unanswerable.

The interesting bug was not in the policy. The lock was taken and released from a LaunchedEffect keyed on that function's answer, which is correct while the screen is in front of the user and wrong the moment it is not:

  • Home → onPause releases the lock. Correct: the launcher must not blank when a hand passes over it.
  • Return to the still-connected call → the effect does not re-run, because its key never changed while the screen was away. The lock is gone and nothing asks for it back.

The condition had two halves moving independently — what the call is doing, and whether this screen is what the user is looking at — and only one of them was keyed. The fix remembers the policy's answer and re-applies it on resume, so the lock is held exactly when both halves are true.

One detail on the way out: releasing with RELEASE_FLAG_WAIT_FOR_NO_PROXIMITY, so hanging up with the phone still at the ear does not flash the screen on against the user's face.

None of this was reachable on the emulator by ordinary means — it has a proximity sensor but no earpiece, so Telecom refuses to leave the loudspeaker and the shipping build correctly never takes the lock there. It was verified by A/B: a throwaway build with the speaker guard removed, dumpsys power showing PROXIMITY_SCREEN_OFF_WAKE_LOCK 'CortaSpam:InCallProximity' held by the app's uid, and then — the step that matters — the same probe with the onResume fix deleted again, to watch the lock stay released on return rather than merely reasoning that it would.

Quiz

1. DISCONNECTING deliberately shows no hang-up button, and that reasoning was correct. What was missing?

An exit. "This control would do nothing" and "this screen has no way off it" are different questions, and they only look identical while the screen has exactly one button. The call control stayed absent and the screen gained a Close button — plus Back finishing instead of backgrounding, but only when no other call is live.

2. Why does clearing the state on STATE_DISCONNECTED matter when onCallRemoved already does it?

Because Telecom decides how long a disconnected call sits there before it is removed, and on a real network that is seconds. The screen was rendering a finished call for that entire window. Waiting for the platform to confirm what it has already told you is a gap with no upper bound you control.

3. InCallState.detach(call) moved from the last line of onCallRemoved to the first. What class of bug does that ordering prevent?

A failure in optional teardown — a MediaRecorder that will not stop, a notification the platform rejects — skipping the one line that gives the user their phone back. In a teardown method, restore the user's control first and do the bookkeeping afterwards; a history row must never be able to cost someone their call screen.

4. InCallState is a Kotlin object holding android.telecom.Call instances. Why is that a leak and a correctness bug?

The object is process-scoped; the Calls only work through the InCallService's binding, which is not. A service destroyed mid-call left a screen whose Hang up reached a dead adapter and did nothing, and left the dead call in the stack for the next call to promote back on screen when it ended. clear() drops them all at once — no promotion, because none of them is reachable any more.

5. The emulator refused to leave the loudspeaker and the Speaker chip stayed selected. Why is that the button working rather than failing?

The chip renders onCallAudioStateChanged, which is Telecom's report of the live route — not a local flag flipped on tap. The device has no earpiece, so the request was declined and the route did not change; the UI said what was true. A locally-guessed flag would have shown "earpiece" while the audio came out of the speaker, which is worse than having no button.

6. Every scripted device suite passed and the reported bug was still unreproduced. What made the emulator structurally unable to show it?

Its fake modem answers and tears down calls instantly, so no call is ever observably DIALING and none lingers in STATE_DISCONNECTED — the exact state the bug lives in. It also refuses to hold two calls, so call waiting is unreachable too. Green suites proved the happy path; they were not evidence about the defect, and the README says which is which rather than reporting one number.

7. The proximity wake lock was taken from a LaunchedEffect keyed on the policy's answer, and released in onPause. Why did returning to a live call leave the screen unprotected?

Because the condition has two halves that move independently — what the call is doing, and whether this screen is in front of the user — and only the first was keyed. onPause released the lock behind the effect's back; on return the key was unchanged, so nothing re-ran. The answer is now remembered and re-applied in onResume. It was reproduced on a device by deleting the fix again and watching the lock stay released, not inferred.

Design Decisions Recap

  • KMP over Flutter: Native Android APIs (Telecom) accessible without plugins
  • Koin over Dagger: Works in Kotlin/Native — essential for iOS compatibility
  • StateFlow over LiveData: Pure Kotlin — works in commonMain, not Android-only
  • Fakes over MockK: Works in Kotlin/Native — same test runs on Android and iOS
  • Pure ResolveContext: Stateless rule engine — trivially testable, no side effects
  • Instant UI in InCallService: Wins the race against system incoming-call UI
  • Phone normalization: Strips formatting — matches contact numbers to raw incoming calls
  • Glob patterns over regex: Simple enough for iOS CallDirectory expansion
