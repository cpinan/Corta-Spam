Call Blocker, from an empty directory

Nine steps to an Android app that is your phone's dialer, sees an incoming call before it rings, and refuses the calls you told it to. Every step ends in a command to run and a specific thing you must see.

  • 9 steps
  • ~2 hours
  • JDK 17 · Android SDK 36
  • emulator required from step 3

What this is, and how it differs from the other course

The Corta Spam course documents a finished app: 28 chapters written after the code shipped, tracing subsystems and post-mortems. It is a reference. You cannot follow it and end up with a working app, because it never asks you to type anything.

This is the other document. You start with an empty directory and end with an Android app that is your phone's dialer, sees an incoming call before it rings, and refuses the calls you told it to refuse. Every step has a CHECKPOINT — a command to run and a specific thing you must see. If you do not see it, stop; the next step will not save you.

Honesty about provenance. Every file in steps 1–8 was written into an empty directory on a Pixel 8 Pro emulator (API 36) while this was written, compiled, installed, and exercised with real emulated calls. The code blocks are those files, not paraphrases of them, and the traps are failures that actually happened in the order shown. The one exception is step 9's harness script, which is assembled from checks that were each run by hand but was never executed end to end as a single file — it says so where it appears.

What you need

  • JDK 17. Everything here sets jvmToolchain(17); a different JDK is the most common first failure.
  • Android SDK with API 36 installed, and sdk.dir in local.properties.
  • An emulator, or a phone you are willing to make the default dialer. Emulator strongly preferred — from step 3 onwards you need to place real calls, and adb emu gsm call is the only way to do that without a second phone.
  • A Gradle wrapper. Copy gradlew, gradlew.bat and gradle/wrapper/ from any recent project, or run gradle wrapper --gradle-version 8.14.3 if you have Gradle installed.

An empty directory that compiles

No app yet. A green build, so every later failure is readable.

No app yet, no UI, nothing to look at. The goal is a green build, because every later failure is easier to read when you know the build itself is sound.

You will be able to

  • Lay out a two-module KMP project: a shared module and an Android app
  • Pin every version in one place with a version catalog
  • Understand why the root build file declares plugins it does not apply

basics Five files

Create these, and nothing else. Paths are relative to your project root.

The catalog is the single place a version number appears. Without it you get versions scattered across build files, and the failure mode is not a clear error — it is two modules resolving different copies of the same library and a cryptic crash at runtime.

WHY apply false. The root project is not itself a Kotlin or Android module — it has no source. Declaring the plugins here puts them on the classpath once, at a single version, so the module build files can alias(...) them without repeating a version. Applying them at the root would try to make the root an Android module, which it is not.

SCOPE One target, androidTarget(). A real KMP project adds iosArm64() and friends here, and Corta Spam does. Adding iOS now buys you nothing and costs you a Kotlin/Native toolchain download plus a second class of build error to debug while you are still trying to get one platform running.

Checkpoint

You must see BUILD SUCCESSFUL. First run downloads a lot and takes a minute or two. There is no app to install yet — that is correct.

"plugin not found" on the first sync

Almost always pluginManagement missing google(). The Android Gradle Plugin does not live on Maven Central, and the error names the plugin rather than the repository, so it reads like a version problem.

basics Adding Compose to the catalog

Add to [versions]: compose-multiplatform = "1.11.1" and androidx-activityCompose = "1.9.3". Add the plugins compose-multiplatform (org.jetbrains.compose) and compose-compiler (org.jetbrains.kotlin.plugin.compose, version.ref kotlin), plus the library androidx-activity-compose. Declare both new plugins apply false in the root build file.

WHY two Compose plugins. org.jetbrains.compose supplies the multiplatform artifacts — the compose.runtime, compose.material3 accessors. kotlin.plugin.compose is the compiler plugin that rewrites your @Composable functions. Since Kotlin 2.0 the second is versioned with Kotlin, not with Compose, which is why its version.ref is kotlin. Getting this pair wrong produces "This version of the Compose Compiler requires Kotlin version ...", which names versions that both look correct.

going deeper The app module

1 — the app module is not a KMP module

Step 03ran from zero

Becoming the phone app

Take the dialer role now, while there is nothing to lose.

This is the step that decides whether the project is possible. Android does not let an ordinary app watch incoming calls. To see a call before it rings you must be the dialer, and taking that role costs you the whole in-call experience — you now owe the user an answer screen, a ringtone, and a call log. Do it now, while there is nothing to lose.

You will be able to

  • Know what ROLE_DIALER actually requires of your manifest
  • Bind an InCallService and confirm Telecom is talking to yours
  • Grant the role from adb so you can iterate without tapping through system dialogs

going deeper Eligibility is decided by your manifest

The role is not something you ask for and receive. AOSP's roles.xml lists required components, and an app missing any of them is not offered in the "Phone app" picker at all — with no error explaining why. You need both ACTION_DIAL activity filters (with and without the tel scheme) and an InCallService.

WHY exported="true" on a service you never want another app to call: Telecom is another process and must be able to bind it. The android:permission line is what makes that safe — only a caller holding BIND_INCALL_SERVICE, which is system-only, can connect.

Also declare the hardware you now depend on: <uses-feature android:name="android.hardware.telephony" android:required="true" />. A device with no telephony has no calls to screen.

the hard part Taking the role without touching the screen

In the finished app you request the role properly, through RoleManager.createRequestRoleIntent(ROLE_DIALER), because that is the only way a real user can grant it. While developing, do it from adb:

Checkpoint

What must appear:

state=2 is Call.STATE_RINGING. You are now seeing a call before the user does, which is the entire premise of the app.

the role says you, the calls go elsewhere

There are two mechanisms and they can disagree. cmd role get-role-holders can name your package while Telecom keeps binding a different app, because telecom set-default-dialer sets a separate override that wins. Symptom: no log line, and Telecom's own log naming somebody else:

Set both, and read Telecom's log rather than the role list when they disagree: adb shell telecom set-default-dialer dev.example.callblocker.

What you now owe the user

Declaring IN_CALL_SERVICE_UI means the platform dialer's in-call screen no longer appears — yours is expected instead, and you do not have one yet. Until step 7 the emulator will ring with no answer UI. That is the debt this step takes on deliberately, and it is why taking the role early is right: discovering it after building a settings screen would mean rebuilding around it.

The number, and what it is not

A string chosen by the network, in whatever shape it felt like.

You have a number in a log line. Before building anything on it, be clear about what it is: a string chosen by the network, in whatever format the network felt like, which may be empty.

You will be able to

  • Read the handle off a Call safely
  • Know the three shapes an incoming handle really arrives in
  • Reject the assumption that two numbers are the same when their strings are equal

basics Reading the handle

Both details and handle are genuinely nullable. A withheld or private caller arrives with no handle at all, and orEmpty() turning that into "" is a decision you are making — that an unknown caller is a caller with an empty number, not a crash and not a null to thread through everything downstream.

going deeper Three shapes, one subscriber

CONTRAST The obvious move is to strip everything that is not a digit and compare. It is wrong, and the wrongness is not academic: +34611998877 becomes 34611998877, the national form stays 611998877, and they are not equal — so a person in your contacts is treated as a stranger. Corta Spam shipped that bug, fixed it in the comparison function, and then shipped it again three days later because one caller normalised its input before handing it over.

The whole of step 8 is this problem. For now, only take away the rule: never compare phone numbers with ==.

basics Catalog and plugin

WHY packageName in the sqldelight {} block has to match where you want the generated AppDatabase to appear. Get it wrong and the class exists but your import does not resolve, which reads like a build failure and is a typo.

going deeper The schema

WHY no join across a blocklist and an allowlist here. A single clever query would be untestable without a database and unreadable the moment a third rule type arrives. In code it is a pure function over data a test can construct in two lines — which is step 6.

SCOPE The CHECK on action is worth having from the first day. It is the difference between a typo failing at insert time and a call log quietly containing three spellings of "blocked".

the hard part One driver per platform

In a JVM unit test you swap this for the JDBC driver and get a real SQLite engine with no emulator — which is how the persistence layer gets tested at all.

Checkpoint

Green, and AppDatabase now resolves in Kotlin. The database file itself does not exist yet — it is created on first use, which is step 6.

Your first blocked call

The app stops observing and starts acting. The cost of error changes.

Everything so far has been observation. Now the app acts, and the cost of being wrong changes: a missed spam call is an annoyance, a missed real one can be an emergency.

You will be able to

  • Write a rule engine that is pure, and therefore testable
  • Reject a call through Telecom

basics The engine

Nothing here knows about Android, SQLite or Telecom, so a test constructs its inputs directly. Precedence is the order of the ifs and nothing else — contacts before the blocklist, deliberately, so that adding your mother to a blocklist by accident is recoverable and adding her to your contacts is authoritative.

going deeper Wiring it to the call

WHY ring first, decide second. Evaluation touches a database. If you wait for it before ringing, a slow query drops a legitimate caller into silence; ringing immediately and stopping a few hundred milliseconds later costs a blocked spammer a quarter-second of ringtone.

WHY CancellationException is rethrown before the general catch. Swallowing it breaks structured concurrency — the coroutine keeps running after its scope is gone. Everything else fails open.

Step 08ran from zero

Phone numbers are not strings

The step that decides whether the app is usable.

The step that decides whether the app is usable. Everything else can be wrong and merely annoying; this one blocks people the user knows.

You will be able to

  • Compare two numbers without guessing a region
  • See why a digit-suffix match is a security problem, not a shortcut
  • Understand how a correct comparison is disarmed by one careless caller

basics The problem, concretely

The third line is what makes this hard. Spain's 611998877 and Peru's 611998877 are different people who share a national number.

going deeper Two approaches that look right

CONTRAST 1 — compare the last 7–9 digits. What PhoneNumberUtils.compare does, and it makes all three lines pass. It also lets a stranger who shares a tail match your allowlist. This function guards blocking; trading a correctness bug for a security-shaped one is a bad trade.

CONTRAST 2 — canonicalise to E.164 with a default region. Now you need the SIM or locale region, an ISO-to-dialling-code table, and a trunk-prefix rule that differs per country: dropping a leading zero is right for the UK and wrong for Italy, whose E.164 keeps it. Three new failure modes for a guess you did not have to make.

the hard part Let the number state its own country

WHY candidate sets rather than one canonical string per side: the trunk zero must be available both stripped and intact, because the UK drops it in E.164 and Italy keeps it. Reducing each side to a single string satisfies one country and breaks the other.

the fix that was only half applied

The real app got this function right, tested it, shipped it — and users kept reporting blocked contacts. The function was never called with what it needed:

A contact saved +34611998877 reached sameNumber as 34611998877, which states no country — so the asymmetry could no longer split off 611998877, and a domestic call stopped matching. Their name still displayed correctly, because the name lookup used a different key set, which made the symptom look impossible.

The rule: a comparison that depends on the shape of its input must say so where its callers read it, and any normalisation upstream disables it silently. Put it on the interface, not in the commit message.

Checkpoint

Three real calls against one blocked number, +34611998877:

Then prove the test can fail: replace sameNumber(it, number) with it == number and watch the first line flip to Allowed. A regression test never seen failing is a test of nothing.

Step 09checks ran, script did not

Proving it, on calls a machine places

A harness, and the two ways a green suite lies.

You have a call blocker. What you do not have is any reason to believe it works, because every check so far was you watching one call at a time.

You will be able to

  • Drive a matrix of real calls from a script
  • Assert on the database rather than the screen
  • Recognise the two ways a green suite lies

going deeper The harness

The emulator's fake modem is the whole reason this is automatable. Save as scripts/matrix.sh:

WHY poll for a row with id > baseline rather than reading the newest row. "This call was never logged" is a real finding, and it must not be able to masquerade as an old row carrying the wrong verdict — which is exactly what reading ORDER BY id DESC LIMIT 1 alone would do.

WHY more than half the rows assert ALLOWED. A blocker that blocks everything passes every BLOCKED row.

the hard part Two ways a green suite lies

1. It asserts absence. A test that a blocked call produces no ringtone passes against an app with no ringtone code whatsoever. The real app had six such tests and a ringer that never rang. Prefer positive assertions — assert the player started, not that nothing happened.

2. It never reaches the state. Every call test in that project covered calls that ring, get blocked, or get missed — never one that was answered. An Android 14 restriction crashed the app the instant any call was answered, and the suite stayed green because nothing had ever entered that state.

Both are the same defect: not in the assertions, but in the state space they cover. When a suite is green and a user is unhappy, ask which state the suite has never entered.

Checkpoint

Four passes, no failures. Then break something deliberately — change sameNumber(it, number) to it == number in RuleEngine, rebuild, reinstall — and confirm the first row goes red while the others stay green. A suite that cannot fail has told you nothing.

You have an app that is your phone's dialer, sees calls before they ring, blocks by rule, rings when it should and stays silent when it should not. What it does not have: an in-call screen worth using, a call log, notifications, quiet hours, contacts integration, more than one language, or an iOS target.

All of those exist, built on exactly this skeleton, in the Corta Spam course — 28 chapters of what happened after this point, including the bugs. Read chapter 20 ("Code That Ships But Never Runs") before you write your next feature, and chapter 28 before you write your next fix.

What was actually run, and what was not

  • Executed from an empty directory, on a Pixel 8 Pro emulator (API 36), while writing this: steps 1 through 8. Every source file shown is the file that was compiled and installed. The checkpoints are real terminal output, including step 8's three calls against one blocked number — 611998877 and +34611998877 both Blocked(reason=MANUAL), +51611998877 Allowed — and step 7's ringtone player, read out of dumpsys audio with the app's own pid on it. All four gotchas in steps 1–3 are failures that actually occurred, in the order shown, including the blank screen diagnosed with uiautomator dump.
  • Not executed as written: step 9's matrix.sh. Each of its four checks was run by hand against this app and produced the result shown, but the script was never run as a single file, so treat it as a starting point rather than something known to run first time.
  • Borrowed rather than derived: the war stories. The ringer that never rang, the fix that was only half applied, the suite that stayed green through a crash — those are from Corta Spam, a shipping app with 571 tests and a 14-scenario device suite. The code here is a minimal reimplementation built for this tutorial, not a copy of that app.

That distinction is the point of the document. A tutorial that does not say which of its steps were run is asking you to trust prose over evidence, which is the habit every chapter here argues against.
